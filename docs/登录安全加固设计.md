# 登录安全加固设计

> 版本：v1（设计稿，待评审）
> 范围：`/api/auth/login`、`/api/auth/login/sms`、`/api/auth/sms/send` 及其前端调用链

## 一、现状盘点

| # | 现状 | 代码位置 | 风险 |
|---|---|---|---|
| 1 | 请求体仅 `@NotBlank`，用户名/密码无长度、无字符集约束 | `LoginRequest.java` | 超长串可打满 BCrypt；脏数据进日志 |
| 2 | 登录 = 查用户 + `passwordEncoder.matches`，无失败计数、无限流、无锁定 | `AuthService#loginByPassword` | **可无限次爆破/撞库**，脚本零成本 |
| 3 | 用户不存在时短路跳过 BCrypt（`user == null \|\| !matches`） | 同上 | **时序侧信道**：错误文案虽已统一，但响应耗时差异可枚举账号是否存在 |
| 4 | 短信验证码发送无任何频控 | `AuthService#sendSmsCode` | 短信轰炸（接真实网关即直接烧钱）；验证码校验也无尝试上限，6 位码可被反复试 |
| 5 | access token 无状态、30 分钟有效，登出/改密只吊销 refresh | `JwtAuthenticationFilter` | 改密后旧 access 仍可用最长 30 分钟 |
| 6 | 无登录日志 | — | 出事无法追溯；用户看不到"谁在登我的号" |
| 7 | 注册密码仅 `@Size(6,32)`，`123456` 可注册 | `RegisterRequest.java` | 弱口令 |
| 8 | 前端表单零校验，直接提交；无密码可见切换、无锁定态倒计时 | `LoginView.vue` | 体验差；错误只能靠 toast 一闪而过 |
| 9 | Redis starter 已引入但代码零使用；`ResultCode.TOO_MANY_REQUESTS(42900)` 已预留 | `pom.xml` / `ResultCode.java` | 基础设施就位，只差实现 |

**结论**：真正的短板不是"校验太少"，而是**没有成本模型**——攻击者试错成本为 0，且缺少事后追溯能力。

## 二、设计原则

1. **纵深防御，不靠单点**：输入校验、频控、认证加固、会话管理、审计，各自独立生效，任一层失效不导致全盘失守。
2. **注册严、登录松（不对称原则）**：密码强度只卡注册/改密，登录侧只做"长度上限 + 非法字符"拦截。
   ⚠️ 这条是硬约束：`demo/123456` 是所有健康检查脚本的入口（`GET /api/orders/count` 验证链），登录侧一旦加复杂度校验，全部回归脚本失效。
3. **可用性优先**：锁账号会被人用来恶意锁死他人账号，因此**优先"验证升级"，其次"短时锁定"**，锁定粒度取「IP + 账号」组合而非全局账号。
4. **失败信息对外模糊、对内精确**：客户端统一文案，服务端日志记录精确原因（`BAD_CREDENTIAL` / `LOCKED` / `DISABLED` / `CODE_ERROR`）。

## 三、五道闸门

```
请求 → ① 输入校验 → ② 频控闸门 → ③ 认证加固 → ④ 会话签发 → ⑤ 审计留痕
                    (Redis)      (BCrypt/验证升级)   (JWT+refresh)
```

### ① 输入校验层（成本最低，先做）

**后端**（`LoginRequest`）：
- `username`：`@Size(min=4, max=20)` + `@Pattern("^[a-zA-Z0-9_]+$")` —— **与注册口径完全一致**。
  注册侧只允许这个范围，登录侧放宽到 1~50 位没有意义：那些输入注定查不到账号，
  却仍要走一次查库 + BCrypt，白耗资源。（收紧前已核对库内账号：
  `admin` 5 / `demo` 4 / `zzxh` 4 / `uploader67232` 13，全部合规）
- `password`：`@Size(min=1, max=32)`。上限 32 与注册对齐；**下限不设 8、不校验复杂度** ——
  否则 `demo/123456` 这类 6 位纯数字的历史账号登不进来。
- 拒绝含控制字符/空白的输入。

**前端**（`LoginView.vue`）：
- 失焦即时校验 + 提交前拦截，错误显示在**输入框下方红字**（替代一闪而过的 toast）。
- 密码框加「显示/隐藏」切换（眼睛图标）。
- 提交按钮 `disabled = loading || locked`，防重复提交。
- 记住**用户名**（localStorage），绝不记密码。

> 前端校验只是体验优化，**不是安全边界**，后端必须独立校验。

### ② 频控闸门（核心，防爆破）

存储用 Redis（starter 已在，无新依赖）。固定窗口 + 阶梯惩罚，够用且实现简单。

**Key 设计**

| Key | 含义 | TTL |
|---|---|---|
| `auth:fail:acct:{username}` | 账号维度失败次数 | 15 min |
| `auth:fail:ip:{ip}` | IP 维度失败次数 | 15 min |
| `auth:lock:acct:{ip}:{username}` | 组合锁定标记 | 按轮次 |
| `auth:lock:ip:{ip}` | IP 封禁标记 | 30 min |
| `auth:gate:acct:{username}` | 惩罚轮次（24h 内不清） | 24 h |
| `auth:sms:send:{phone}:60s / :10m / :1d` | 短信三档发送计数 | 对应 |
| `auth:sms:fail:{phone}` | 验证码校验失败次数 | 10 min |

**策略表**

| 维度 | 阈值 | 动作 |
|---|---|---|
| 账号 | 15 min 内失败 3 次 | 要求**验证升级**（见 ③），不锁定 |
| 账号 | 15 min 内失败 5 次 | 锁定 15 min |
| 账号 | 24h 内第 2 轮触发 | 锁 1 h |
| 账号 | 24h 内第 3 轮触发 | 锁 24 h |
| IP | 15 min 内失败 20 次 | 429，封 30 min |
| IP | 登录接口 > 5 QPS | 429（令牌桶） |
| 短信 | 同号 60s 1 次 / 10min 3 次 / 日 10 次 | 429 |
| 短信 | 同 IP 日 50 次 | 429 |
| 验证码 | 同号校验失败 5 次 | 作废当前码，需重新获取 |

- **成功登录只清账号维度计数，不清 IP 计数**（否则"一次成功"可洗白整段爆破）。
- IP 取 `X-Forwarded-For` 首段（生产走 Nginx），开发环境回退 `getRemoteAddr()`。
- IP 限流同时是 **CPU 防护**：BCrypt cost=10 约 50–100 ms/次，100 QPS 即可打满 4 核，这层比防爆破更救命。

**降级决策（需拍板）**：Redis 不可用时建议 **fail-open（放行 + 告警日志）**。理由是商城登录不可用的损失远大于短时爆破风险；若选 fail-close，Redis 抖动会导致全站无法登录。

### ③ 认证加固层

**a. 常数时间比对（必做，10 行代码）**
```java
// 用户不存在时也跑一次 BCrypt，消除时序差异
String hash = (user != null) ? user.getPassword() : DUMMY_HASH; // 启动时生成一次
boolean matched = passwordEncoder.matches(raw, hash);           // 必须无条件执行
if (user == null || !matched) throw BizException.unauthorized("用户名或密码错误");
```

**b. 验证升级（替代硬锁定）**
失败达 3 次后，响应体返回 `needVerify: true` + 一次性 `verifyToken`（Redis，5 min），后续登录必须携带图形码/短信码：
- 真人只多一步，脚本成本翻倍；
- 不锁账号，规避"恶意锁死他人账号"；
- 对明确异常（同 IP 高频）仍走硬限流。

本项目无第三方验证码组件，二选一：**算术题 Canvas 图形码**（无依赖，~150 行）或 **短信码兜底**（复用现有链路，但每条有成本）。

**c. 密码策略（仅注册/改密）**
长度 ≥ 8、不得包含用户名、不得为纯数字、命中弱口令字典 top-200 直接拒绝。**种子账号 `demo` 豁免**（迁移脚本不校验）。

**d. BCrypt cost**
当前默认 10。提到 12 会使单次校验约 200–300 ms，登录接口需配合限流；建议维持 10 + 频控，性价比更高。

### ④ 会话层

**问题**：登出/改密后旧 access token 仍可用 30 分钟。

两个方案（**需拍板**）：

| 方案 | 实现 | 代价 | 适用 |
|---|---|---|---|
| A. Redis 黑名单（推荐） | JWT 加 `jti`，登出/改密时把 jti 写入黑名单，TTL = token 剩余有效期；过滤器查一次 Redis | 无表结构变更；每请求多一次 Redis 读（<1ms） | 本阶段 |
| B. token version | `sys_user` 加 `token_version`，JWT 带 `tv`，过滤器比对（配 Redis 缓存 5 min） | 需改表 + 每请求缓存查询 | 后续做"全员踢下线"时 |

**会话管理**：`sys_refresh_token` 补 `ip` / `user_agent` / `last_used_at` 三列后，即可做"登录设备列表 + 单设备下线"，用户端在「个人信息」页展示。

### ⑤ 审计层

新增 `sys_login_log`（**需拍板**）：

```sql
CREATE TABLE `sys_login_log` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`     BIGINT UNSIGNED DEFAULT NULL COMMENT '账号不存在时为空',
  `username`    VARCHAR(50)     NOT NULL     COMMENT '输入的用户名快照，防改名后无法追溯',
  `ip`          VARCHAR(45)     NOT NULL,
  `user_agent`  VARCHAR(255)    DEFAULT NULL,
  `login_type`  TINYINT         NOT NULL     COMMENT '1账密 2短信',
  `success`     TINYINT         NOT NULL     COMMENT '0失败 1成功',
  `fail_reason` VARCHAR(32)     DEFAULT NULL COMMENT 'BAD_CREDENTIAL/LOCKED/DISABLED/CODE_ERROR',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user_time` (`user_id`, `created_at`),
  KEY `idx_ip_time` (`ip`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='登录日志';
```

- 写入：MVP 同步 insert（单行 <1 ms）；量大后切 MQ 异步（项目已有 RabbitMQ）。
- 用途：用户端「登录记录」、管理端失败 TOP/IP 聚合、事后追溯。

## 四、接口契约变化

```jsonc
// 失败：账号不存在 / 密码错误（对外完全一致）
{ "code": 40100, "message": "用户名或密码错误" }

// 失败：需要验证升级
{ "code": 40101, "message": "请完成安全验证", "data": { "needVerify": true, "verifyToken": "..." } }

// 失败：锁定（带剩余秒数，前端做倒计时）
{ "code": 42900, "message": "尝试过于频繁，请 12 分钟后重试", "data": { "retryAfter": 720 } }
```

前端处理：`40100` → 输入框红字；`40101` → 弹验证码；`42900` → 按钮禁用 + 倒计时，不清空已填内容。

## 五、分阶段落地（每阶段可独立验收）

| 阶段 | 内容 | 改动面 | 验收标准 |
|---|---|---|---|
| **P0** | 输入校验 + 常数时间比对 + 登录/短信频控 + 429 语义 | 仅后端，**无表结构变更** | 连打 6 次错误密码，第 4 次要求验证、第 6 次返回 429 带 `retryAfter`；短信 60s 内二次发送被拒；`demo/123456` 仍可正常登录 |
| **P1** | 登录日志表 + 用户端「登录记录」页 + 管理端失败统计 | 新增 1 表 | 成功/失败均留痕，用户端可见最近 10 条 |
| **P2** | Redis 黑名单即时吊销 + 设备会话列表 | `sys_refresh_token` +3 列 | 登出后旧 access 立即 401 |
| **P3**（可选） | 图形验证码 / 异常登录提醒 / 蜜罐字段 | 前后端 | — |

**P0 建议作为下一步**：不碰表结构、不动业务逻辑，只加防护，风险最低且收益最大。

### C.2 实施中修掉的两个问题

**① 作废动作被事务回滚**

第一版把 `markUsed()` 和 `throw BizException` 放在同一个 `@Transactional` 方法里，
业务异常触发回滚 → 提示「已作废」但数据库 `used` 仍是 0，用户还能继续试。

修法：新增 `SmsCodeExhaustedException`，在 `loginBySms` / `registerBySms` / `resetPassword`
上声明 `@Transactional(noRollbackFor = SmsCodeExhaustedException.class)` ——
只让这一个异常不回滚，其他业务异常的回滚行为不变。

**② 作废后旧码「复活」**

原来查询条件是「最新一条**未使用**」，最新码被作废后会回退到更早那条仍有效的码，
等于作废没作干净。改为取「最新一条」，再显式判断 `used`：

```
最新一条 used=1 → 验证码已失效，请重新获取
```

## 附录 D：会话吊销实施记录（2026-10-17）

### D.1 T1 登出即时失效 + T2 改密全端下线

**方案：Redis 双维度吊销，不改表结构。**

| 维度 | key | 写入时机 | TTL |
|---|---|---|---|
| 单令牌 | `auth:revoked:jti:{jti}` | 登出 | 该令牌剩余有效期 |
| 按用户 | `auth:invalid-before:{userId}` | 改密 | access token 有效期（30min） |

`JwtTokenProvider.createAccessToken` 增加 `jti`（UUID）；`JwtAuthenticationFilter`
验签通过后再查这两处，命中则按未登录处理。

实测：

| 场景 | 结果 |
|---|---|
| 登出前 `GET /api/auth/me` | ✅ 200 |
| 登出后同一 token | ✅ 401「未登录或登录已过期」 |
| 改密后改密前的 token | ✅ 401 |

### D.2 实施中修掉的一个连带问题

**`/api/auth/me` 在令牌被吊销后返回 404「用户不存在」而非 401。**

原因：`/api/auth/**` 整体 `permitAll`，未认证请求照样进 controller，
`UserContext.getUserId()` 返回 null，`selectById(null)` 查空 → 抛 `NOT_FOUND`。

影响：前端 `request.ts` 只在 401 时清本地令牌，404 会让用户卡在
「显示已登录、但拉不到资料」的状态。

修法：`getUserInfo` 开头显式判断 `userId == null` 抛 401。

### D.3 设计取舍

- **fail-open**：Redis 不可用时视为未吊销。Redis 一抖就全站 401，比「旧令牌多活几分钟」严重得多。
- **严格小于**：`iat < invalidBefore` 才算失效，避免改密后同一秒内重新登录拿到的新令牌被误杀；代价是同一秒内签发的旧令牌有 1 秒漏网窗口，实际影响可忽略。
- **失效时间点只增不减**：并发改密取较晚的值，防止后到的请求把已失效的令牌「复活」。
- **无 jti 的旧令牌**：功能上线前签发的令牌没有 jti，按未吊销处理（30 分钟内自然淘汰）。
