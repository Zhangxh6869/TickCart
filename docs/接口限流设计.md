# A3 · 接口限流设计

> 对应阶段：**3A / A3**（缺口 P0-4）
> 状态：**设计待确认**
> 前置阅读：`TickCart项目阶段划分.md`「阶段 3 前置 · 高并发能力补齐（3A）」

---

## 1. 现状与目标

**现状**：只有登录与短信两条链路有频控（`RedisLoginGuard` / `RedisSmsCodeGuard`），
业务接口（商品列表 / 详情 / 搜索 / 下单 / 支付）**完全裸奔**。

有意思的是，**基建其实已经齐了**：

| 已有 | 位置 | 能直接复用 |
|---|---|---|
| 429 异常 | `RateLimitedException(retryAfterSeconds)` | ✓ 带剩余秒数，前端能倒计时 |
| 429 响应体 | `GlobalExceptionHandler` → `{code:42900, data:{retryAfter}}` | ✓ |
| 客户端 IP | `ClientIpResolver.resolve(request)` | ✓ 处理了 X-Forwarded-For |
| 登录用户 | `UserContext.getUserId()` | ✓ |
| fail-open 先例 | `RedisLoginGuard` 在 Redis 故障时放行 + WARN | ✓ 照抄这个决策 |

**目标**：给业务接口加一层闸门，挡脚本刷单/爬虫/误用；阈值**可配置**，不写死在代码里。

---

## 2. 为什么用 Interceptor，不用 Filter / AOP

| 方案 | 问题 |
|---|---|
| Servlet Filter | 在 Security 之前执行，拿不到 `UserContext`；要自己解析 JWT 才能按用户限流 |
| AOP 注解 | 项目**没有** `spring-boot-starter-aop` 依赖；为一个限流引一个切面框架不划算 |
| **HandlerInterceptor** | Spring MVC 自带；在 Security 之后、Controller 之前执行，`UserContext` 已就绪；能拿到请求路径/方法 |

> 注意：`preHandle` 里抛出的异常会走 `DispatcherServlet` 的异常解析链，
> 因此 `@RestControllerAdvice` 里的 429 处理器照常生效，不需要额外 try-catch。

## 3. 算法：令牌桶 + Lua 原子执行

选令牌桶而不是「固定窗口计数」，理由：

- **固定窗口有边界突刺**：59.9s 打满 100 次 + 60.1s 再打满 100 次 = 0.2 秒内 200 次。
- **滑动窗口（ZSET）精确但内存 O(N)**：每请求一个成员，热门 IP 下开销明显。
- **令牌桶内存 O(1)**（只存 `tokens` + `ts`），允许合理突发，是网关层的主流选择。

脚本（单次 RTT、原子）：

```lua
-- KEYS[1] = 桶 key
-- ARGV[1] = 容量  ARGV[2] = 每毫秒补充速率  ARGV[3] = 当前毫秒  ARGV[4] = TTL(ms)
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local ttl      = tonumber(ARGV[4])

local data   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])
if tokens == nil then tokens = capacity end
if ts     == nil then ts     = now end

tokens = math.min(capacity, tokens + math.max(0, now - ts) * rate)

if tokens < 1 then
  redis.call('HSET', KEYS[1], 'ts', now)
  redis.call('PEXPIRE', KEYS[1], ttl)
  return math.ceil((1 - tokens) / rate)      -- 还需等待的毫秒数
end

redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'ts', now)
redis.call('PEXPIRE', KEYS[1], ttl)
return 0                                     -- 0 = 放行
```

约定：**返回值 0 放行，>0 表示还要等多少毫秒**。`RateLimitedException` 只收秒，向上取整。

Key：`limit:{rule}:{dim}:{value}`，例 `limit:search:ip:0:0:0:0:0:0:0:1`。
TTL 取 `max(2 × window, 60s)`：桶补满只需一个窗口，留 2 倍余量即可；空闲 60s 后 key 自动消失。

## 4. 维度与规则

| 规则 | 路径 | 方法 | 维度 | 令牌桶 | 为什么 |
|---|---|---|---|---|---|
| `product-read` | `/api/products/**`、`/api/categories/**` | GET | IP | 60 / 秒 | 已加缓存，成本低；一屏页面会连发数个请求，阈值要给宽 |
| `search` | `/api/search/**` | GET | IP | 10 / 秒 | 每次 `LIKE` 全表 + 同步写 `search_log`，是最贵的读接口 |
| `order-create` | `/api/orders`、`/api/orders/buy-now` | POST | USER | 5 / 秒 | 防脚本刷单；幂等只管「同一请求不重复」，管不了「换个幂等键狂下单」 |
| `payment` | `/api/payments/**` | POST | USER | 5 / 秒 | 发起支付要落流水 + 投 MQ |

**维度选择原则**：
- 匿名可访问的接口按 **IP**（没有 userId 可用）。
- 需要登录的接口按 **USER**（同一 NAT 出口下多个用户不会互相挤占）。
- 规则声明 `dimension: USER` 但请求未登录时，**回退到 IP** —— 否则所有匿名请求共享同一个空 userId 的桶，会互相误伤。

**阈值一律是「宽值」**：A3 只负责把闸门装上去，真实阈值要等 A4 修完 N+1、定下池子基线后，
用压测数据回填（这正是执行顺序里 A3 排在 A4 之前的原因）。现在的值只保证「正常用户碰不到、脚本一定被挡」。

## 5. 配置形态

```yaml
tickcart:
  rate-limit:
    enabled: ${RATE_LIMIT_ENABLED:true}
    rules:
      - name: product-read
        patterns: ["/api/products/**", "/api/categories/**"]
        methods: ["GET"]
        dimension: IP
        permits: 60
        window-seconds: 1
      - name: search
        patterns: ["/api/search/**"]
        methods: ["GET"]
        dimension: IP
        permits: 10
        window-seconds: 1
      - name: order-create
        patterns: ["/api/orders", "/api/orders/buy-now"]
        methods: ["POST"]
        dimension: USER
        permits: 5
        window-seconds: 1
      - name: payment
        patterns: ["/api/payments/**"]
        methods: ["POST"]
        dimension: USER
        permits: 5
        window-seconds: 1
```

- **没命中任何规则的接口不限流**（如 `/api/health`、`/api/cart/**`、`/api/admin/**`）。
- `patterns` 用 Spring 的 `AntPathMatcher`；多条命中时取**路径最长**的那条（最具体优先），不叠加计数。
- 阈值是运营参数，改完重启即可生效 —— 满足 AGENTS.md「禁止硬编码」。
- 秒杀接口（B 阶段）在这里加一条独立规则，**绝不复用 `product-read` 的 60/秒**：
  抢购流量本来就该被 MQ 削峰，限流阈值要按活动库存量级单独定。

## 6. 降级：fail-open

Redis 异常 → **放行 + WARN 日志**，与 `RedisLoginGuard` 保持一致。

理由：限流是保护手段，不是正确性依赖。Redis 抖动时如果 fail-close，等于把全站打成 503 ——
比短时被刷更伤业务。真正的兜底是数据库的行锁与条件 UPDATE。

---

## 7. 与幂等的分工（别混淆）

| 机制 | 管什么 | 例子 |
|---|---|---|
| 幂等（A1） | **同一笔请求**只执行一次 | 连点两次提交 → 只有一笔订单 |
| 限流（A3） | **同一主体**单位时间最多 N 次 | 脚本每秒换 50 个幂等键下单 → 挡在第 6 次 |

两者互补：幂等防「重复」，限流防「高频」。缺任何一个都有漏洞。

## 8. 验证方案

### 8.1 单元测试

| 用例 | 断言 |
|---|---|
| 路径无匹配规则 | 放行，不调用限流器 |
| 方法不匹配（如 GET 打 `order-create`） | 放行 |
| IP 维度超限 | 抛 `RateLimitedException`，`retryAfter` 向上取整 |
| USER 维度且已登录 | 用 userId 作为桶标识 |
| USER 维度但未登录 | 回退 IP，不与空 userId 共桶 |
| 总开关关闭 | 全部放行 |
| Redis 抛异常 | 放行（fail-open）+ WARN |

Lua 脚本本身不做单测（需要真 Redis），靠运行时验证覆盖。

### 8.2 运行时验证

```powershell
# ① 搜索接口：连打 30 次（阈值 10/秒），应看到 429 且带 retryAfter
1..30 | ForEach-Object {
  try { Invoke-RestMethod 'http://localhost:8080/api/search/hot?limit=8' }
  catch { $_.Exception.Response.StatusCode.value__ }
}

# ② 恢复：等 1 秒后再打，应恢复 200
Start-Sleep -Seconds 1
Invoke-RestMethod 'http://localhost:8080/api/search/hot?limit=8'

# ③ 下单接口：同一账号 1 秒内打 10 次 POST /api/orders（阈值 5/秒）
#    期望 5 个进入业务（成功或 409/400），其余 429

# ④ 降级：停掉 Redis 后连打，应全部 200（fail-open），日志有 WARN
docker stop tickcart-redis
# 验证完立刻 docker start tickcart-redis
```

### 8.3 与缓存/幂等的联动检查

- 限流不应影响 A2 的缓存命中（429 发生在 Controller 之前，根本不进业务）。
- 限流不应破坏 A1 的幂等：被 429 拒绝的请求**没有**创建幂等记录（在拦截器层就返回了）。

## 9. 本切片不做

- **全局限流**（所有接口合计 QPS）：需要独立的全局桶，与按接口限流叠加计数，复杂度翻倍；
  单机部署下 Tomcat 线程数本身就是硬上限，收益有限。
- **分布式限流的一致性**：多实例部署时令牌桶按实例共享 Redis，本身是一致的；但「集群总 QPS」
  需要额外聚合，MVP 不做。
- **后台接口限流**：`/api/admin/**` 只有管理员能访问，人数可控。
- **按接口动态调整（热更新）**：改配置需重启，够用。
