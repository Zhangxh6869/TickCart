# 电商搜索：业界主流做法参考

> 用途：给 TickCart 的搜索迭代做参照。**本文只做调研，不含代码改动。**
> 关联：《搜索功能实现方案.md》（TickCart 现状与已实施方案）
> 调研时间：2026-10-13
> 可信度标注：**【官方】**= 平台公开口径；**【共识】**= 从业者/卖家社区广泛验证但平台未证实；**【实现】**= 技术实现层面的通用做法

---

## 0. 一句话结论

业界搜索**不是**「拿关键词去商品名里做模糊匹配」，而是一条四段流水线：

```
① 多字段召回（标题/卖点/类目/品牌/属性 一起搜，标题权重最高）
② 相关性算分（BM25 + 字段 boost，中文先分词）
③ 业务加权排序（销量/转化率/评价/价格/店铺分… 叠加到相关性分上）
④ 体验层（联想补全 / 纠错 / 热搜 / 高亮 / 筛选 / 无结果兜底）
```

底层几乎都是**倒排索引**（Elasticsearch / OpenSearch / Solr 系），不是 SQL `LIKE`。
DB-Engines 2026 年 5 月排名中 Elasticsearch 已连续 8 年居搜索引擎类目第一，全球 52%+ 企业在生产环境使用。**【实现】**

## 1. 搜哪些字段（这是与 TickCart 差距最大的一环）

### 1.1 京东公开口径 **【官方】**

文本相关性 = 商品的文本描述信息与搜索关键词的匹配程度，参与匹配的字段明确列出：

> **商品标题、商品标名、类目名称、品牌名、商品参数**（图书类还有作者、出版社等）

并特别强调：**商品标题与关键词的相关度最重要**；类目放错会直接负面影响排序。

### 1.2 Amazon A9 **【共识】**（Amazon 未公开确切公式）

字段权重排序（从业者实测共识，非官方公布）：

| 权重档 | 字段 | 说明 |
|---|---|---|
| 最高 | **标题 Title** | 尤其**前 60~80 字符**，移动端搜索结果只展示这一段 |
| 次高 | **五点描述 Bullet Points** | 自然融入关键词，靠前的 bullet 略重 |
| 中 | **后台搜索词 Search Terms** | 用户看不到；放同义词/缩写/别称，上限 ~250 **字节**（不是字符） |
| 低 | 商品描述 / A+ 内容 | 仍被索引，但权重低 |
| 可变 | **类目与类目属性** | 放错类目是"常见且难诊断"的排名问题 |

几条明确的规则 **【官方】**：

- **不重复**：标题里已有的词不用再写进后台搜索词（已索引，重复纯浪费）
- **不写错拼**：系统自动纠正常见拼写错误，写 `excercise` 是浪费
- **不堆砌**：A9 **忽略关键词频次**——"yoga mat" 写 5 次没有额外收益
- **忽略停用词**：搜 "mat for yoga" 能匹配按 "yoga mat" 优化的商品

### 1.3 对照 TickCart

| 字段 | 业界 | TickCart 现状 |
|---|---|---|
| 商品标题 `name` | ✅ 权重最高 | ✅ 唯一被搜的字段 |
| 副标题 / 卖点 `subtitle` | ✅ | ❌ |
| 类目名 | ✅ | ❌ |
| 品牌 | ✅ | ❌（表里没有品牌字段） |
| 属性 / SKU 规格 | ✅（商品参数） | ❌ |
| 同义词 / 别称 | ✅（后台词/同义词表） | ❌ |

## 2. 怎么搜（技术实现）

### 2.1 中文必须分词 **【实现】**

`LIKE '%手机%'` 与全文检索的本质差别：

| | 正排（`LIKE`） | 倒排（ES） |
|---|---|---|
| 索引方向 | 文档ID → 内容 | 词条 → 文档ID 列表 |
| 复杂度 | 全表扫描 O(N) | 按词条查，毫秒级 |
| 能否分词 | ❌ 只能整串包含 | ✅ |
| 能否算相关性分 | ❌ | ✅ |

分词器选型（ES + IK 中文分词）**【实现】**：

- 索引时用 `ik_max_word`（最细粒度），**查询时用 `ik_smart`**（最粗粒度）
- ★ **黄金准则：索引与查询的分词器必须配套**，不一致会直接匹配失败
- 拼音：`pinyin` 分词器 + `keep_first_letter: true`，支持全拼与首字母搜索
- 同义词 filter：`苹果手机 = iPhone`

### 2.2 相关性算分 **【实现】**

- ES 5.x 之后默认 **BM25**（替代 TF-IDF）
- BM25 的核心改进：**词频饱和 + 文档长度归一化** —— 某个词出现 10 次和 100 次，得分差距不会线性放大，更符合"关键词出现几次就够了"的直觉
- 字段级 `boost`：如标题 `boost: 2.0`、拼音 `boost: 1.0`
- 查询结构（ES Query DSL 示意）：`bool.should(标题 match, 拼音 match, 内容 match)` + `minimumShouldMatch(1)`；品牌/价格这类**过滤**用 `filter`（不参与算分，可走缓存）

## 3. 排序怎么排（"综合排序"的本质）

### 3.1 京东公开的排序因子 **【官方】**

1. **文本相关性**（见 §1.1，标题最重）
2. **类目相关性**（关键词与类目也要匹配）
3. **商品综合人气**：近期销量（**不同时间段的销量加权**）、销售额、消费者评价、商品属性完整度与一致性、关注度/加购/分享
4. **用户搜索反馈**：该关键词下的**点击量、成交量、平均停留时长、分享、关注、加购率、搜索点击转化率**
5. **店铺风向标**：评价、客服 30 秒应答率、物流 48h 揽件及时率、售后退换货率、交易纠纷率、放心购、影响因子（开店时长等）
6. **京东好店**认证（各二级类目评分前 10%）
7. **个性化（千人千面）**：按用户前一天的浏览/加购/购买/搜索/咨询行为加权；新用户主要看商品本身的销量/评价/浏览量；**用户所在地区无货的商品降权**
8. **反作弊**：虚假交易、关键词堆砌、错放类目 → 降权或屏蔽

几条实用的官方问答 **【官方】**：

- 标题里关键词**放前面不会更靠前**——真正影响权重的是「该关键词的搜索成交占比」
- **首次**上架时间影响"新品"权重；**最近**上架时间不影响
- 排名**每天**按实时数据更新；新商品实时可搜，最晚 60 分钟
- 非默认排序（价格/销量/评论）会**先过滤掉相关性差的类目**再排

### 3.2 Amazon A9 的两根支柱 **【共识】**

- **相关性**（可控，改完 24~48h 生效）：字段权重见 §1.2
- **表现**（难直接优化，是竞争词的分水岭）：
  - **销量速度 Sales Velocity** —— 最强信号之一，"卖得好→排得高→卖得更多"的正循环
  - **转化率 CVR** —— 曝光多但不成交会被判为"不匹配"而掉排名
  - **点击率 CTR** —— 主图、标题、评分、价格、Prime 标志决定
  - **评价数量与星级** —— 200 条 4.5 星通常稳压 20 条 4.7 星
  - **价格竞争力** —— 明显高于类目均价会被压制
  - **卖家账号健康度**（ODR<1%、迟发率<4% 等阈值）作为**乘数**作用在所有 listing 上

### 3.3 工程上怎么落地 **【实现】**

- 先用相关性**召回**，再用 `function_score` 把业务分（销量、热度、时间）**叠加**到相关性分上
- 对 Top 200 做**二次重排 rescore** 精细调权
- 把用户点击日志写回，做个性化加权（点得多的商品排名更靠前）
- 权重示例（文章给的示意，非平台官方）：`销量×0.4 + 好评率×0.3 + 价格竞争力×0.2 + 用户画像×0.1`

### 3.4 对照 TickCart

| | 业界 | TickCart 现状 |
|---|---|---|
| 相关性算分 | BM25 + 字段 boost | ❌ 无（`LIKE` 只有命中/不命中） |
| 业务加权 | 销量/转化/评价/价格/店铺 多维 | ❌ 只有单一维度排序（综合/销量/价格） |
| 排序维度 | 综合 + 价格 + 销量 + 评论 + 新品… | 综合 / 销量 / 价格↓ / 价格↑ |
| 个性化 | 千人千面 | ❌ |
| 地区有货降权 | ✅ | ❌ |

## 4. 体验层（搜索好不好用，一半在这）

### 4.1 搜索联想 / 补全（Suggester）**【实现】**

- **前缀匹配**是主流：用户从左到右输入，优先按前缀召回
- 数据结构：前缀 trie 树 / **AC 自动机**（多模匹配，可同时做前中后缀召回）/ Redis ZSet（`ZADD suggest:手 1000 手机`，取 `ZREVRANGE suggest:手 0 9`）
- 排序依据：历史 query 的 **qv（搜索量）** + 点击转化 + 商业价值；短 query 召回太多时**离线召回粗排 + 写 Redis**供线上直查
- **拼音**：全拼 + 首拼都要支持（`pinguo` / `pg` → 苹果）；多音字是难点（乐 le/yue）
- ES 原生 `Completion Suggester`（需 `completion` 类型字段）
- 指导原则：联想词**有限（约 10 个）**、要贴近用户意图、**99% 能搜到商品**、能纠错
- 一个容易忽略的点：**搜索建议要跟商品在售状态脱钩**（否则下架商品会污染联想词）

### 4.2 纠错 **【实现】**

- 拼音纠错（`xioami` → `xiaomi`，`pinguo` → 苹果）、编辑距离（一般 >5 个字母才纠）、形近字（`祙`→`袜`）、繁体归一（`蘋果`→苹果）
- 输入归一化：全角/半角、大小写、去停用词

### 4.3 热搜榜 **【实现】**

- 统计真实搜索词频：Redis `ZINCRBY hot:search:20240612 1 手机`，按天建 key、保留 30 天，取 `ZREVRANGE ... 0 19`
- ★ **必须做衰减**（如每天凌晨 score × 0.5），否则头部词分数奇高、长尾永远上不了榜
- 加人工干预位（运营置顶）

### 4.4 搜索日志闭环 **【实现】**

- 记录每次搜索 + 后续行为，给关键词打分：
  - 用户点了商品/进详情/加购 → 说明满足预期 → **+1**
  - 用户改词重新搜 → 说明不满足 → **−1**
  - 一段时间内无任何动作（跳出）→ 同上
- 聚合分数 → 筛选合格词进建议词库
- ★ **监控「无结果搜索词 TOP10」**是关键指标——搜不到东西是最伤的体验

### 4.5 其他

- **高亮**：命中词在标题里标红（ES `highlight`）
- **筛选**：品牌 / 价格区间 / 属性（走 `filter`，不参与算分）
- **意图识别**：识别"200元以下"自动套用价格筛选
- **场景化聚合**：搜"面膜"自动出"补水面膜榜"这类入口
- **深分页**：`from+size` 翻深了会内存爆炸，生产用 `search_after` 游标
- **数据同步**：Canal 监听 MySQL binlog + MQ 异步写 ES，保证最终一致

## 5. TickCart 的差距与可选路径

### 5.1 现状（见《搜索功能实现方案.md》）

- 匹配：**只搜 `name`**，`LIKE '%关键词%'`（已转义 `%` `_`）
- 排序：单一字段（createdAt / sales / price），无相关性分
- 体验：搜索历史（localStorage）+ 热搜（现取热销商品名）+ 排序 + 空态兜底
- 缺失：联想、纠错、同义词、高亮、多字段、相关性算分、无结果词监控

### 5.2 三档路径（代价递增，**均需你确认后再做**）

**档 1 · 纯 SQL 能扛（改动小，无新中间件）**

| 项 | 做法 | 收益 |
|---|---|---|
| 多字段匹配 | `WHERE (name LIKE ? OR subtitle LIKE ?)` | 搜「柔软亲肤」能命中（实测现在是 0） |
| 关键词高亮 | 前端把命中片段包 `<em>` | 一眼看出为什么命中 |
| 同义词表 | 新增 `search_synonym` 表（需建表确认） | 「苹果手机」↔「iPhone」 |
| 真·热搜词 | 落搜索日志表，按词频统计（需建表确认） | 替换现在"热销商品名"的权宜做法 |
| 无结果词监控 | 记录 0 结果的关键词 | 直接反映"搜不到东西"这类问题 |

**档 2 · 引入 Elasticsearch（技术栈变更，需你确认）**

IK 分词 + 多字段 boost + BM25 相关性 + `function_score` 业务加权 + Completion Suggester 联想 + 拼音搜索 + 高亮。
**这是"懂搜索"的分水岭，也是面试加分项**；但要新增中间件（docker 里加一个 ES 容器）。

**档 3 · 工程化（作品项目一般不必做到）**

Canal/binlog 同步、`search_after` 深分页、LTR 个性化、AB 测试、多路召回（关键词 + 向量语义）。

### 5.3 一个务实的提醒

TickCart 现在**上架商品只有 60 件、只分布在 3 个分类**。这个量级下：

- 用 ES 属于**杀鸡用牛刀**——性能收益为零，收益全在"演示/学习价值"
- 真正影响体验的是**数据覆盖**（17 个分类是空的），而不是检索算法
- 所以建议顺序是：**先把档 1 做掉（尤其是多字段 + 无结果词监控）→ 再决定要不要上 ES**
