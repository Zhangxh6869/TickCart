# 后台运营看板（Dashboard）设计方案

> 项目代号：TickCart | 模块：admin 数据看板
> 定位：**数据看板 / 运营分析** 的落地设计
> 原则：功能优先、样式克制、面试能讲；**不引 echarts**，沿用项目自写 `SparkLine.vue` 的轻量 SVG 路线。

---

## 1. 为什么做 & 做到什么程度

### 1.1 现状（排查确认，非臆测）

后台**已经有"看板零件"，缺的是"总览聚合 + 趋势"**：

| 已有零件 | 位置 | 说明 |
|---|---|---|
| 订单 KPI（状态分布/积压/客单价） | `AdminOrderController#overview` → `OrderOverviewVO` | 一次 `GROUP BY status` 算全，刻意不含"今日 N 单" |
| 秒杀战报 KPI | `AdminSeckillController#overview` → `SeckillOverviewVO` | 进行中/待开始/已售/成交额 |
| 分类库存 KPI | `AdminProductController#categories/overview` → `CategoryOverview` | 分类商品数、低库存数（按 SKU） |
| 搜索迷你看板 | `AdminSearchController` → `SearchStatsVO` + `SearchTrendPoint` | **已是带趋势线的看板样板** |
| 图表组件 | `components/SparkLine.vue` | `data: number[], color?, width?, height?`，纯 SVG |

### 1.2 缺的三件事

1. **跨域总览入口**：统计散在 5 个管理页页头，缺一个登录后台第一眼看到的总览页，也缺后台菜单入口。
2. **趋势维度**：订单页只有"当前积压"，没有"近 N 天订单/成交额曲线"——这是运营最想看、面试最能讲的部分。
3. **聚合接口**：缺一个 `admin/dashboard` 一次拉齐所有域。

### 1.3 定位：克制版看板，不是 echarts 大屏

- **做**：一页总览 + KPI 数字卡 + 2~3 条轻量趋势线 + 库存告急/秒杀战报精简区。
- **不做**：彩色渐变大屏、旋转 3D 图表、实时 websocket 刷新、图表库引入。
- **为什么**：违背项目"功能优先、样式克制、面试能讲清"的原则；轻量 SVG 趋势线足够表达，且不新增依赖（沙箱不能 `pnpm add`，不引 echarts 也避开依赖变更）。

---

## 2. 页面设计（做成什么样子）

后台新增菜单项「数据看板」，路由 `/dashboard`，插到导航**第一位**（总览入口）。

### 2.1 页面分区（自上而下）

```
┌────────────────────────────────────────────────────────┐
│ 数据看板                      （右上角：时间范围切换）      │
├────────────────────────────────────────────────────────┤
│  [核心 KPI 卡 × 4]                                      │
│  累计成交额   累计成交单数   进行中秒杀   库存告急 SKU      │
├────────────────────────────────────────────────────────┤
│  [近 7/30 天订单趋势]    [近 7/30 天成交额趋势]           │
│   SparkLine 扩展的迷你柱状/折线                          │
├────────────────────────────────────────────────────────┤
│  [秒杀战报] 在场场次 | 进行中 | 已售件数 | 成交额          │
│  [库存告急清单] 低库存 SKU 前 N（link 到商品管理）          │
└────────────────────────────────────────────────────────┘
```

### 2.2 具体内容

**① 核心 KPI 卡（4 个数字）**
- 累计成交额：`paidAmount`（待发货+待收货+已完成，复用 `OrderOverviewVO` 口径）
- 累计成交单数：`paidOrderCount`
- 进行中秒杀：`ongoing`（复用 `SeckillOverviewVO`）
- **库存告急商品**：从 `CategoryOverview` 累加 `lowStockCount`

> ⚠️ 口径说明：`CategoryOverview.lowStockCount` 由 `StockWarnService.isLow(product.getStock(), …)` 算出，
> 是**商品级**（商品总库存低于分类阈值），不是 SKU 级。因此 KPI 文案用「库存告急商品」，
> 不能写成「SKU」；SKU 级清单在商品管理页的「补货清单」抽屉里（`/admin/products/low-stock`）。

**② 趋势区（2 条，时间范围 7/30 天可切换）**
- 近 N 天订单量：按 `t_order.created_at` GROUP BY 天
- 近 N 天成交额：按 `t_order.pay_time` GROUP BY 天（**成交 = 已付款单**）
- 前端用 `SparkLine` 渲染折线；如要柱状，可在组件旁扩展一个 `MiniBars.vue`（同样纯 SVG，不引库）

**③ 秒杀战报区**
- 直接复用 `SeckillOverviewVO` 已返回的字段，纯展示 + 时间倒计时文案

**④ 库存告急区**
- 复用 `CategoryOverview`（含 `effectiveThreshold`），列出低库存分类及数量
- 每行文案：「N 个商品低于预警线 (阈值)」+「去补货 →」
- 点击跳 `/products?lowStock=1`，商品管理页在 `onMounted` 读该参数并置 `query.stockLow = true`（只看库存告急，商品级口径与看板数字一致）
- **刻意不画进度条**：`lowStockCount`（商品个数）与 `effectiveThreshold`（库存数量阈值）量纲不同，相除没有业务含义

## 3. 后端接口设计

新增一个**聚合接口**，避免前端对每个管理页发 N 个请求：

```
GET /api/admin/dashboard?days=7
```

返回 `DashboardVO`（聚合各域已有 overview + 新增趋势）：

```
DashboardVO {
  // KPI（复用现有口径，后端直接调各域 service）
  OrderOverviewVO     order;      // 复用 adminOverview()
  SeckillOverviewVO   seckill;    // 复用 activityService.overview()
  List<CategoryOverview> category; // 复用 categoryService.overview()，前端算告急合计

  // 趋势（新增）
  List<DailyPoint>    orderTrend;   // 近 days 天每日订单数
  List<DailyPoint>    amountTrend;  // 近 days 天每日成交额
}

DailyPoint { String day; long count; BigDecimal amount; }
```

### 3.1 实现落点

- **位置**：`admin/dashboard/`（对齐现有"admin 只做编排、数据归属各域"的分层——`admin` 目录目前是纯编排，无独立 Controller）。
  但注意：现有 admin 接口分散在 `AdminOrderController`/`AdminSeckillController`/`AdminProductController` 各域下。
  **方案 A（推荐，贴合现有结构）**：新增 `admin/DashboardController` 只做编排，内部调 `orderService.adminOverview()`、`activityService.overview()`、`categoryService.overview()` 各域现有方法，再加一个新 `DashboardQueryService` 算趋势。
  **方案 B**：趋势查询放 `trade` 域（订单趋势归属订单域），`DashboardController` 调它。
  → 采用 **B 的趋势归属 + A 的编排聚合**：趋势 SQL 放 `trade`（`OrderMapper`），聚合编排放 `admin/DashboardController`。这也贴合"跨模块走 Service 接口"的既有约定。

### 3.2 趋势查询（SQL 口径）

近 N 天订单量（走 `idx_created_at` 索引）：
```sql
SELECT DATE(created_at) AS day, COUNT(*) AS cnt
FROM t_order
WHERE created_at >= #{since} AND deleted = 0
GROUP BY DATE(created_at)
ORDER BY day;
```

近 N 天成交额（走 `idx_created_at`，成交=已付款，`pay_time` 非空即付款）：
```sql
SELECT DATE(pay_time) AS day, SUM(pay_amount) AS amt, COUNT(*) AS cnt
FROM t_order
WHERE pay_time >= #{since} AND deleted = 0
GROUP BY DATE(pay_time)
ORDER BY day;
```

- **空天补 0**：前端对缺失日期补 0（后端只返回有数据的天），减少后端复杂度。
- **date 生成**：后端不硬编码 `LocalDate`，用 `LocalDate.now().minusDays(days-1)` 算起点。

### 3.3 性能

- 数据量（演示库订单不多）直接扫 `idx_created_at`/`idx_status` 即可，无需新索引。
- 不缓存（看板低频访问，实时准更重要）；若后续量大，按天缓存一个 key `dashboard:{date}`，但这轮不做。

## 4. 前端实现

### 4.1 改动点

| 文件 | 改动 |
|---|---|
| `views/DashboardView.vue` | **新增**：页面主体，4 KPI 卡 + 2 趋势区 + 秒杀战报 + 库存告急 |
| `layout/AdminLayout.vue` | `el-menu` 首位加 `<el-menu-item index="/dashboard">数据看板`（带 icon） |
| `router/index.ts` | 加 `/dashboard` 路由（挂在 layout 下，auth 守卫自动生效） |
| `api/` | 新增 `dashboard.ts`：`fetchDashboard(days)` 调聚合接口 |
| `components/MiniBars.vue` | **新增**（可选）：极简 SVG 柱状图（对齐 SparkLine 风格，~40 行）；如趋势只用折线则 SparkLine 够用，可省 |

### 4.2 时间范围切换

`days` 用 `el-radio-group`（7 / 30），切换重新拉接口，趋势区标题显示"近 7 天 / 近 30 天"。

### 4.3 视觉约定（沿用现有后台）

- 页头不重复 h2 标题（顶栏已有），只放时间切换控件。
- KPI 卡用现有 `kpi__` 风格（订单/秒杀页已有）。
- 颜色：成交额/订单趋势用品牌蓝 `rgb(107,163,200)`；库存告急用 `#f56c6c`（对齐 SparkLine 默认红）；秒杀进行中用 danger 弱化（对齐 `SeckillOverviewVO` 页头）。
- 趋势线 `stroke` 只认具体色值（CSS 变量对 SVG 无效，SparkLine 注释已说明）。

## 7. 明确不做（避免范围蔓延）

- 不做 echarts / 图表库引入（沙箱禁 `pnpm add`，且违背项目风格）。
- 不做实时 websocket 刷新（刷新即重新拉接口即可）。
- 不做数据缓存（看板低频，实时更准）。
- 不做"今日 N 单"类以今天为基准的指标（演示数据可能停在几天前，会全 0 像坏，`OrderOverviewVO` 已明确此取舍）。
- 不做移动端适配（后台是 PC 端）。

## 8. 实施记录（as-built）

### 8.1 落地文件

| 层 | 文件 |
|---|---|
| 后端 VO | `trade/vo/DailyPoint.java`、`admin/vo/DashboardVO.java` |
| 后端 Service | `trade/service/DashboardTrendService.java`（趋势查询 + 补 0 天） |
| 后端 Controller | `admin/controller/DashboardController.java`（`GET /api/admin/dashboard?days=N`，纯编排） |
| 后端测试 | `DashboardTrendServiceTest`(6) + `DashboardControllerTest`(3) |
| 前端类型 | `packages/shared-types/src/index.ts` 追加 `DailyPoint` / `DashboardVO` |
| 前端 API | `apps/admin/src/api/dashboard.ts` |
| 前端页面 | `apps/admin/src/views/DashboardView.vue` |
| 前端接线 | 路由 `/dashboard`（并设为默认落地页）、侧边栏首项、登录后跳转 |
| 前端复用 | `components/SparkLine.vue`（用 CSS 覆盖固定 width 实现自适应） |

### 8.2 与方案的偏差

1. **秒杀战报改为汇总数字**：`SeckillOverviewVO` 只提供汇总（进行中/待开始/已售/成交额），**没有活动明细列表**，所以不做 Demo 里的"逐场活动行"，改为 4 个数字格。
2. **库存告急去掉进度条**：量纲不一致（商品个数 vs 库存阈值），见 §2.2 ④。
3. **KPI 文案「库存告急商品」**：口径是商品级，不是 SKU 级。
4. **趋势图自适应**：`SparkLine` 的 `width` 是固定像素属性，用 `:deep(svg){width:100%;height:auto}` 覆盖，靠 `viewBox` 等比缩放。

### 8.3 验证结果

- 后端全量单测 **461 个**（新增 9 个），仅 `RedisFaultInjectionTest.cacheDegradesWithinSingleTimeout` 因机器负载时序 flaky 失败，**单独重跑 5/5 通过**，与本次改动无关。
- 变异验证 **2/2 被抓住**：①去掉补 0 天 → 3 个用例失败；②成交额不赋值 → 1 个用例失败。
- 前端 `vue-tsc --noEmit`：admin / mall 均通过；`vitest` 58/58 通过。
- 真实页面验证（Playwright + Chrome，admin/admin123）：菜单首位「数据看板」；KPI `¥116652.50 / 72 / 0 / 1` 与接口一致；7 天趋势 `13 单 / ¥538.70`，切 30 天变 `184 单 / ¥116652.50`；无横向溢出；点击「去补货」跳 `/products?lowStock=1` 且列表被筛到 1 行。
- 权限：无 token → **401**；普通用户 demo → **403**；admin → 200。
