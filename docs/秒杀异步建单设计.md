## 2. 一个必须先定的缺口：收货地址从哪来

B2 的抢购请求只有 `quantity`，**消息里没有 `addressId`**。而 `t_order.receiver/receiver_phone/receiver_addr`
都是 `NOT NULL` —— 建单必须有地址。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 用默认地址**（推荐） | 消费者调 `AddressService.getDefault(userId)` | 无默认地址的用户抢到了也建不了单 |
| B. 抢购时带 addressId | 改 B2 的请求体与消息体 | 抢购多一次「选地址」交互，违背「一键抢」 |
| C. 先建单后补地址 | 地址字段允许 NULL | 改表结构 + 全链路空值处理，成本最高 |

**推荐 A**，理由：秒杀的核心是「快」，让用户先选地址再抢会显著降低成功率；
电商秒杀普遍是「默认地址下单、支付前可改」。没有默认地址的用户会在结果里收到
「请先设置收货地址」，库存当场回补 —— 这不是故障，是明确的业务引导。

### 2.1 这个代价到底有多大（查了代码与数据）

**「无默认地址」几乎不会出现**：`AddressService.create()` 里有这么一段 ——

```java
// 首个地址自动成为默认，避免结算页选不出默认地址
boolean asDefault = existing == 0 || Integer.valueOf(1).equals(req.getIsDefault());
```

也就是说，**用户只要添加过任意一条地址，就一定有一条默认地址**。
真正会踩到的只有「一个地址都没加过」的用户，而不是「有地址但没设默认」。

而且这个代价可以在前端几乎完全消除 —— **三层防御**：

| 层 | 做法 | 效果 |
|---|---|---|
| 前端（B4） | 秒杀页加载时查 `/api/addresses`，无地址则禁用抢购按钮并引导添加 | 用户根本走不到「抢到了却建不了单」 |
| 后端兜底 | 消费者建单失败 → 回补库存 → 结果 FAILED「请先设置收货地址」 | 拦住脚本/直接调接口/并发边界 |
| ~~抢购接口前置校验~~ | 在 B2 的 buy 里查一次地址，没有直接 409 | **不做**：每次抢购多一次 DB 查询，破坏「抢购链路不查 DB」的设计目标 |

结论：**代价存在但可控**，且只在「零地址用户直接调接口」这一种情况下才会暴露；
正常用户会被前端拦在抢购之前。

> 如果你更希望「抢购时选地址」，我改 B2 的契约（请求体加 `addressId`，消息体透传），
> 但前端就得多一步交互。

## 3. 消费者流程

```
SeckillOrderConsumer.onMessage(message)
  │
  ├─ 1. 解析消息（失败 → ack 丢弃 + ERROR，不重试）
  ├─ 2. OrderService.createSeckillOrder(...)   ← 幂等在这里
  │       ├─ 成功 → 3
  │       └─ 抛异常 → 4
  ├─ 3. 写结果凭据 SUCCESS(orderNo) → ack
  └─ 4. 判断可重试性
          ├─ BizException（无地址/商品下架/活动不存在）→ 不可重试
          │     → 回补库存 → 写 FAILED 结果 → ack
          └─ 其他异常（DB/网络）→ 可重试
                ├─ 重试次数 < 3 → 重投重试队列（10s 后回到本队列）
                └─ 达到上限 → 回补库存 → 写 FAILED 结果 → ack + ERROR
```

**关键：重试期间绝不回补库存**。否则重试成功后库存会多出来 —— 只有「最终失败」才还回去。

重试机制完全复用 `OrderTimeoutConsumer` 的做法：重投到 `trade.seckill.order.retry`，
队列 TTL 10s 后死信回 `trade.seckill.order`，消息头 `x-retry` 计数。

## 4. 建单入口：`OrderService.createSeckillOrder`

```java
/**
 * 秒杀建单：由 MQ 消费者调用，不读购物车、不扣 SKU 库存。
 */
@Transactional
public OrderVO createSeckillOrder(SeckillOrderMessage message);
```

| 项 | 值 | 说明 |
|---|---|---|
| 幂等 | `claim(userId, "seckill.buy", requestId)` | 重复消费直接返回已有订单 |
| 地址 | `addressService.getDefault(userId)` | 无地址 → 抛 BizException |
| 商品 | `requireProduct(productId)` + SKU 归属校验 | 活动期间可能被下架 |
| 金额 | `message.seckillPrice × quantity` | 用消息里的快照，不回查活动 |
| `channel` | `1` | 秒杀订单 |
| `activityId` | 写入 `t_order.activity_id` | 取消时要回补正确活动 |
| 订单号 | `SK` + 17 位时间戳 + 4 位随机 | 与普通订单 `NO` 区分 |
| **库存** | **不扣 `product_sku.stock`** | 秒杀库存在 B2 的 Lua 里已扣 |
| 超时关单 | 照常投递 | 15 分钟后未付款自动关闭 |

建单成功后 `activityMapper.increaseSoldCount(activityId, quantity)`：

- 返回 1 → 正常
- 返回 0（`sold_count + n > seckill_stock`）→ **记 ERROR 但不回滚订单**。
  订单已经建了、用户已经抢到，宁可多卖一单也不能让他白抢；这是 Redis 与 DB 不一致的告警信号。

## 5. 结果凭据

`seckill:result:{requestId}`，TTL 24h（比活动 TTL 长，用户可能第二天才回来查）：

```json
{
  "requestId": "a1b2c3...",
  "userId": 2,
  "status": "SUCCESS",
  "orderNo": "SK202610191730001234",
  "message": "抢购成功",
  "updatedAt": "2026-10-19T17:30:00"
}
```

失败时 `status = FAILED`，`message` 写清原因（如「请先设置收货地址」）。

**存 `userId` 是为了查询时校验归属** —— 虽然 requestId 是 32 位随机串不可猜，
但结果里带订单号，多一道归属校验没有成本。

### 结果查询接口

```
GET /api/seckill/result/{requestId}
```

| 情况 | 响应 |
|---|---|
| 命中且属于当前用户 | `{status, orderNo, message}` |
| 命中但属于别人 | 404（不暴露存在性） |
| 不存在/已过期 | 404「结果不存在或已过期」 |

> 前端轮询策略（指数退避）在 B4 实现，接口本身这里就绪。

## 6. 秒杀订单的回补路径（容易漏）

`OrderService.restoreStock(orderNo)` 目前无条件回补 `product_sku.stock`。
**秒杀订单不能走这条路**：它的库存记在 Redis + `sold_count`，回补到 SKU 上等于凭空多出库存。

改法：`restoreStock` 改为接收 `Order`，按渠道分流：

```java
if (order.getChannel() == 1 && order.getActivityId() > 0) {
    seckillStockService.restore(activityId, userId, quantity);   // Redis + bought
    activityMapper.decreaseSoldCount(activityId, quantity);      // sold_count - n
} else {
    inventoryService.restore(productId, skuId, quantity);        // SKU
}
```

影响两处调用方：`cancel(userId, orderNo)` 与 `closeTimeout(orderNo)`。

> `SeckillStockService.restore` 已经会判 `hasKey`：活动结束 key 过期时跳过 Redis 回补，
> 但 `sold_count` 仍然要减 —— 否则统计会一直偏高。

## 7. MQ 声明

在 `SeckillMqConfig` 里补：

| Bean | 值 |
|---|---|
| `trade.seckill.order` | 已存在（B2 声明） |
| `trade.seckill.order.retry` | 新增，TTL 10s，死信回 `trade.seckill.order` |

消费者用 `@RabbitListener(queues = QUEUE_SECKILL_ORDER)`，手动 ack（与 `OrderTimeoutConsumer` 一致）。

**prefetch**：秒杀建单是重操作（DB 写 + 事务），`prefetch` 建议 5（A4 全局是 10）。
可用 `@RabbitListener(... properties = "prefetch=5")` 单独覆盖。

## 8. 与 A1 幂等的复用

`IdempotentService` 增加场景常量：

```java
public static final String SCENE_SECKILL_BUY = "seckill.buy";
```

幂等键 = `requestId`（B2 生成，32 位 hex）。这天然满足「一次抢购一个键」：
- 消息重复投递 → 同键 → 命中 → 返回首次订单号，不重复建单
- 用户重试抢购 → 新 requestId → 新键 → 正常新建（但限购会挡住）

## 9. 验证方案

### 9.1 单元测试

| 用例 | 断言 |
|---|---|
| 建单成功 | `channel=1`、`activityId` 落库、订单号 `SK` 前缀、**未调用 `inventoryService.deduct`** |
| 无默认地址 | 抛 BizException，消息「请先设置收货地址」 |
| 幂等命中 | 同 requestId 第二次 → 返回首次订单号，不新建 |
| `sold_count` 累加 | 成功后调用 `increaseSoldCount` |
| `sold_count` 达上限 | 记 ERROR 但不抛异常（订单保留） |
| 取消秒杀订单 | 回补 Redis + `decreaseSoldCount`，**不回补 SKU** |
| 取消普通订单 | 仍回补 SKU（回归） |
| 结果查询 | 命中返回、他人 404、不存在 404 |

### 9.2 端到端脚本 `scripts/verify-seckill-order.mjs`

```
1. 建活动（库存 5，限购 1）→ 5 个用户并发抢
2. 轮询 GET /api/seckill/result/{requestId} 直到 SUCCESS（最多 10 秒）
3. 断言：5 个 requestId 都拿到 orderNo，且订单号互不相同
4. 断言：t_order 里 channel=1 的订单恰好 5 条，activity_id 正确
5. 断言：sold_count = 5，Redis 剩余 0
6. 取消其中 1 单 → 断言 Redis 剩余变 1、sold_count 变 4、SKU 库存未变
7. 无默认地址用户抢购 → 结果 FAILED，库存回补
```

### 9.3 需要观察的异常场景

- 消费者重启后消息重投 → 不重复建单（幂等生效）
- 建单过程中 Redis 挂掉 → 回补失败只记 ERROR（不能因为回补失败卡住消息）
