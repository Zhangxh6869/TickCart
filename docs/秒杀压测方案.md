> 对应阶段：**3B / B5**
> 状态：**设计待确认**
> 前置：B1~B4 已完成（活动管理 → 预热/扣减 → 异步建单 → 专场页）

---

## 1. 目标与边界

**目标**：用可复现的脚本证明三件事，并给出数字：

1. **不超卖**：库存 100、1000 并发 → 恰好 100 单
2. **削峰有效**：MQ 消费者停掉时，抢购接口仍然秒回（DB 写入速度不影响抢购成功率）
3. **性能有数**：QPS、P95、成功率，以及瓶颈在哪

**边界（必须写进报告，避免数字被误读）**：

- 单机部署：MySQL / Redis / RabbitMQ / 后端 / 压测客户端**都在同一台机器**
- 无网络延迟、无网关、无 TLS
- 数据量小（647 个商品、几千条订单）
- 因此这些数字**只能横向对比「改造前 vs 改造后」**，不能当成生产容量

---

## 2. 指标口径

| 指标 | 定义 | 说明 |
|---|---|---|
| **受理成功率** | `200` 数 / 总请求 | 429（限流）、409（售罄/限购）不算失败，是**预期内的拒绝** |
| **QPS** | 总请求数 / 墙钟耗时 | 客户端并发发起，不含 token 预取 |
| **P95 / P99 延迟** | 仅统计 `200` 响应 | 被拒的请求本来就快，混进去会把延迟算得过于乐观 |
| **超卖数** | `max(0, 成功数 - 活动库存)` | 必须为 0 |
| **账目一致性** | Redis 剩余 == 0 且 `sold_count` == 成功数 | 两者都对才算过 |
| **削峰验证** | 停消费者时 QPS 与 P95 不下降 | 说明 DB 写入不在抢购关键路径上 |

## 3. 场景矩阵

| # | 场景 | 配置 | 断言 |
|---|---|---|---|
| S1 | **核心：不超卖** | 库存 100，1000 用户并发抢 | 成功 == 100；Redis 剩 0；`sold_count` == 100 |
| S2 | **全成功吞吐** | 库存 1000，1000 用户并发 | 成功 == 1000；记录 QPS / P95 |
| S3 | **单用户连点** | 库存 10，1 个用户 50 并发（限购 1） | 成功 == 1；其余 429（请求锁）或 409（限购） |
| S4 | **削峰对照** | 同 S1，但**停掉消费者** | 抢购仍秒回；`trade.seckill.order` 积压 == 100 |
| S5 | **对照：普通下单** | 同一批用户走 `POST /api/orders`（有库存） | 记录 QPS / P95，与 S2 对比 |

> S5 是「为什么需要秒杀架构」的证据：普通下单要在事务里扣库存 + 建单，
> 吞吐会被 DB 写死；秒杀接口只做 Redis + 投递 MQ。

## 5. 数据准备与清理

### 5.1 账号

压测需要 **N 个不同用户**（限购 1 件/人，且同一用户会被 3 秒请求锁挡住）：

- 用 demo 的密码哈希批量插入 `sku0001..sku1000`
- 每个用户配一条默认地址（建单需要）
- **token 缓存到本地文件**（`.workbuddy-ai/tmp/seckill-tokens.json`，不进 git）：
  登录要走 BCrypt，1000 次约 1~2 分钟，缓存后重复压测只需几秒

### 5.2 清理

压测会产生 N 笔订单，必须能一键清干净：

```sql
DELETE FROM order_item      WHERE order_no LIKE 'SK%';
DELETE FROM payment_record  WHERE order_no LIKE 'SK%';
DELETE FROM t_order         WHERE order_no LIKE 'SK%';
DELETE FROM idempotent_record WHERE scene = 'seckill.buy';
DELETE FROM seckill_activity WHERE id = ?;
DELETE FROM user_address    WHERE user_id IN (SELECT id FROM sys_user WHERE username LIKE 'sku%');
DELETE FROM sys_user        WHERE username LIKE 'sku%';
```

外加 Redis `seckill:*` 与 MQ 队列 purge。**SKU 库存不需要回补**（秒杀不动它）。

## 6. 压测脚本

`scripts/bench-seckill.mjs`（新增，与 `verify-seckill-stock.mjs` 分开：
前者验正确性，后者出性能数字）

```
用法：STOCK=100 USERS=1000 CONCURRENCY=1000 node scripts/bench-seckill.mjs
可选：SKIP_CONSUMER=1  先停消费者（S4 用）
```

输出：

```
=== S1 不超卖验证 ===
并发 1000 / 库存 100
  成功 100 · 售罄 900 · 其他 0
  QPS 1832 · P95 512ms · P99 890ms
  Redis 剩余 0 · sold_count 100 · 超卖 0
  ✓ 通过
```

实现要点：

- 每个请求记录 `start/end`，结束后统一排序算分位
- token 与地址 ID 预取完成后再开始计时
- 失败分类：`429` / `409-售罄` / `409-限购` / `503` / `其他`，分别计数
- 结束后可选自动清理（`CLEANUP=1`）
