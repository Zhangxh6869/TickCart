# TickCart 数据库设计说明

> 本文档对应《TickCart详细设计-架构与模块.md》中「数据库表结构另篇专述」的补篇，记录库、表、字段口径与执行方式。
> 数据库迁移统一由 **Flyway** 管理，脚本位于 `backend/src/main/resources/db/migration/`。

---

## 1. 基本信息

| 项 | 口径 |
|---|---|
| 数据库名 | `tickcart` |
| 字符集 | `utf8mb4` / `utf8mb4_general_ci` |
| 存储引擎 | `InnoDB` |
| 迁移工具 | Flyway（脚本命名 `V{版本}__{描述}.sql`） |
| 主键 | 统一 `BIGINT UNSIGNED AUTO_INCREMENT` |
| 审计字段 | `created_at`、`updated_at`（`datetime`，`updated_at` 自动 `ON UPDATE`） |
| 逻辑删除 | `deleted`（`tinyint`，0 未删 / 1 已删），配合 MyBatis-Plus 全局逻辑删除 |
| 状态字段 | `tinyint` + 列注释声明枚举含义 |
| 表总数 | **19 张**（由 V1~V25 中的 10 个建表脚本创建，详见第 2 节） |

## 3. 表结构说明

### 3.1 用户与认证（V1）

**`sys_user` 用户表**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT UNSIGNED | 主键 |
| username | VARCHAR(50) | 登录名，唯一 |
| password | VARCHAR(100) | BCrypt 加密后的密码 |
| phone | VARCHAR(20) | 手机号，唯一，可空 |
| nickname | VARCHAR(50) | 昵称 |
| avatar | VARCHAR(255) | 头像 URL |
| gender | TINYINT | 0 未知 / 1 男 / 2 女 |
| role | TINYINT | 0 普通用户 / 1 管理员 |
| status | TINYINT | 0 正常 / 1 禁用 |
| deleted | TINYINT | 逻辑删除 |

唯一键：`uk_username`、`uk_phone`；普通索引：`idx_role`。

**`sys_refresh_token` 刷新令牌表**

字段：`user_id`、`token`（唯一）、`expires_at`、`revoked`（0 有效 / 1 已吊销）。
用途：支撑 access + refresh 双令牌方案。

**`sys_sms_code` 短信验证码表（V5）**

| 字段 | 类型 | 说明 |
|---|---|---|
| phone | VARCHAR(20) | 手机号 |
| code | VARCHAR(10) | 验证码（6 位随机，首位非 0） |
| scene | TINYINT | 1 注册 / 2 登录 / 3 重置密码 |
| used | TINYINT | 0 未使用 / 1 已使用 |
| expires_at | DATETIME | 过期时间 |

索引：`idx_phone_scene(phone, scene)`。

> 表结构按真实短信形态设计，接真实网关无需改表。**频控不落库**（同号 30 秒 / 10 分钟 3 次 / 日 10 次 / 同码错 5 次作废）走 Redis，避免高频写库。


### 3.2 商品域（V2）

**`product_category` 分类表**（树形）：`parent_id`（0 为顶级）、`name`、`icon`、`level`、`sort`、`status`（0 禁用 / 1 启用）。

**`product` 商品表**：`category_id`、`name`、`subtitle`、`main_image`、`detail`、`price`、`stock`、`sales`、`status`（0 下架 / 1 上架）、`is_seckill`（0 否 / 1 是，秒杀标记）。

**`product_sku` 规格表**：`product_id`、`spec_name`、`spec_value`、`sku_image`、`price`、`stock`。

**`product_image` 图集表**：`product_id`、`url`、`sort`。

**`user_favorite` 收藏表**：唯一键 `uk_user_product(user_id, product_id)` 防重复收藏。

### 3.3 交易链路（V3）

**`user_address` 收货地址表**：`receiver`、`phone`、`province`/`city`/`district`/`detail`、`is_default`（0 否 / 1 是）。

**`cart_item` 购物车项表**（MVP 用 MySQL，ADR-S1）：`product_id`、`sku_id`、`quantity`、`checked`；唯一键 `uk_user_product_sku(user_id, product_id, sku_id)`。

**`t_order` 订单主表**

| 字段 | 说明 |
|---|---|
| order_no | 订单号，唯一；渠道前缀：普通 `NO`、秒杀 `SK` |
| channel | 0 普通订单 / 1 秒杀订单 |
| total_amount / pay_amount | 订单总额 / 实付金额 |
| status | 0 待付款 / 1 待发货 / 2 待收货 / 3 已完成 / 4 已取消 / 5 已超时关闭 |
| receiver / receiver_phone / receiver_addr | 收货信息快照 |
| pay_time / ship_time / finish_time / cancel_time | 各状态节点时间 |
| express_company / tracking_no | 快递公司（VARCHAR 32）/ 运单号（VARCHAR 64），发货时登记；**均可空** —— 历史订单无从回填，批量发货刻意不采集单号 |

索引：`uk_order_no`、`idx_user_status(user_id, status)`、`idx_status`、`idx_created_at`。
状态机流转的合法性由 Service 层校验，DB 不做硬约束（保留灵活性）。

> ★ 物流两列由 **V25**（`V25__order_express.sql`）追加，是 V3 之后对 `t_order` 的唯一一次结构变更。
> 取值口径：单笔发货走 `ship(orderNo, ShipRequest)` 可填，批量发货走 `ship(orderNo)` 不填。

**`order_item` 订单明细表**：商品名/图/规格/单价均以**快照**保存，`subtotal = price * quantity`；冗余 `order_no` 便于查询。

**`payment_record` 支付记录表**（模拟支付，预留真实回调形态）：`order_no`、`pay_no`（唯一）、`channel`（0 模拟 / 1 微信 / 2 支付宝）、`amount`、`status`（0 待支付 / 1 成功 / 2 失败）、`callback_time`。

### 3.4 搜索域（V13 / V14 / V15）

**`search_log` 搜索日志表（V13）**

| 字段 | 类型 | 说明 |
|---|---|---|
| keyword | VARCHAR(64) | 搜索词（写入前已 trim） |
| result_count | INT | 本次命中商品数，**0 即「无结果搜索」** |
| user_id | BIGINT UNSIGNED | 未登录为 NULL |
| created_at | DATETIME | 搜索时间 |

索引：`idx_created_at`、`idx_keyword`。

> 用途有二：① 无结果搜索词监控（后台「搜索分析」页）；② 真实热搜词统计 ——
> 日志为空时兜底取「热销商品名首段」，保证 `/api/search/hot` 任何情况下都能返回一组点了搜得到的词。
> 写入走内存缓冲批量落库（`SearchLogBuffer`，1 秒一刷），不逐次写库。

**`search_synonym` 同义词表（V14）**：`group_id`（同组内的词互为同义词）、`word`（唯一）。
唯一键 `uk_word`、索引 `idx_group`。用于「手机 ↔ 智能手机」这类改写，避免召回为 0。

**`product.search_keywords`（V15 改表）**：英文逗号分隔的补充关键词（品类词 / 别名，如「手机,智能手机,苹果手机」），与商品名一起参与匹配。

### 3.5 用户行为（V16）

**`user_view_history` 浏览记录表**

字段：`user_id`、`product_id`、`view_time`（最近一次浏览）、`created_at`（首次浏览）。

唯一键 `uk_user_product(user_id, product_id)`；索引 `idx_user_time(user_id, view_time)`、`idx_product_id`。

> ★ 重复浏览走 `INSERT ... ON DUPLICATE KEY UPDATE view_time = NOW()`：只刷新时间、**不产生新行**，
> 所以「浏览记录」天然按最近一次浏览排序，也不会被同一商品的反复点击刷屏。

### 3.6 秒杀（V18）

**`seckill_activity` 秒杀活动表**

| 字段 | 说明 |
|---|---|
| title | 活动标题 |
| product_id / sku_id | 商品与规格；无规格商品 `sku_id = 0` |
| seckill_price / seckill_stock | 秒杀价 / 秒杀总库存（**独立于 `product.stock`**） |
| sold_count | 已成交数量，建单成功后原子累加 |
| limit_per_user | 每人限购数量 |
| start_time / end_time | 活动时间窗 |
| enabled | 0 下线 / 1 上线 |

索引：`idx_time(start_time, end_time)`、`idx_product`、`idx_enabled_start(enabled, start_time)`。

> ★ **两套库存账，别混**：本表的 `seckill_stock` / `sold_count` 与 Redis 计数是一套，
> `product_sku.stock` 是另一套；秒杀扣减只动前者，退款/关单也只回补前者（`restoreStock` 按 `channel` 分流）。
> ★ **活动状态不落库**：由 `enabled` + 时间窗实时推导（未开始 / 进行中 / 已结束），避免定时任务改状态。

### 3.7 售后（V21 / V22）

**`refund_record` 退款单表**

| 字段 | 说明 |
|---|---|
| refund_no | 退款单号，唯一，前缀 `RF` |
| order_id / order_no | 关联订单（`order_no` 冗余，便于按单号查） |
| user_id | 申请人，越权校验用 |
| type | 1 未发货退款 / 2 仅退款（已发货）/ 3 退货退款。**由后端按订单状态判定**，不接受前端传 |
| amount | 退款金额快照，取**支付成功流水** |
| reason_code / reason | 1 不想要了 / 2 信息填错 / 3 商品问题 / 4 其他 + 补充说明 |
| status | 0 待审核 / 1 已退款 / 2 已拒绝 / 3 已撤销 / 4 待寄回 / 5 待收货 |
| origin_status | 申请前的订单状态，拒绝 / 撤销时的回退目标 |
| active_key | **进行中 = `order_no`，终态 = `NULL`** |
| audit_remark / audit_time | 审核意见（拒绝必填）/ 审核时间 |
| refund_time | 退款完成时间 |
| V22 追加 | `return_company`、`return_tracking_no`、`return_time`、`receive_time`、`receive_remark`（退货物流与入库验收） |

唯一键：`uk_refund_no`、**`uk_active_order(active_key)`**；索引：`idx_order_no`、`idx_user_id`、`idx_status`、`idx_created_at`。

> ★ **`uk_active_order` 是「一单只能有一张进行中的退款单」的唯一防线** —— 靠唯一索引兜底，
> 而不是「先查一次再插」（并发下必漏）。终态必须把 `active_key` 置 NULL，否则该订单永远不能再申请售后。
> ★ **4 待寄回 / 5 待收货不是终态**：只有 1 已退款 / 2 已拒绝 / 3 已撤销会释放 `active_key`。
> ★ 库存回补时点按 `type` 分：1 同意时回补、2 永不回补、3 商家确认收货时回补；销量统一在「退款完成」回退。

### 3.8 基础设施（V17）

**`idempotent_record` 幂等记录表**

| 字段 | 说明 |
|---|---|
| scene | 业务场景：`order.create` / `order.buyNow` / `seckill.buy` |
| user_id | 幂等键按用户隔离，防止回放他人订单 |
| idem_key | 客户端生成的 UUID |
| biz_no | 业务单号；**非空即代表该次请求已成功完成** |
| expire_at | 过期时间，定时任务（`IdempotentCleanupTask`）按此清理 |

唯一键 `(scene, user_id, idem_key)`。

> ★ **没有 `status` 字段是刻意的**：记录与业务**同事务**写入，业务失败整体回滚、记录一并消失，
> 所以「行存在」等价于「该次请求已完成」。插入成功 = 抢到执行权；插入撞唯一键 = 重复请求，回查 `biz_no` 回放首次结果。

## 4. 关键设计要点

1. **快照原则**：订单与明细保存商品名、图、成交单价，以及收货人信息快照，避免商品/地址后续变更污染历史订单。
2. **唯一键防重**：用户名、手机号、订单号、支付流水号、收藏、购物车同规格项、退款单 `active_key`、幂等键 `(scene,user_id,idem_key)` 均由唯一键兜底 —— 并发下「先查再插」必漏，唯一索引是唯一可靠的防线。
3. **秒杀库存独立**（V18 建表，已完成）：`seckill_activity` 的库存字段与 `product.stock` 物理隔离，防止秒杀与普通售卖互相影响；回补时按 `t_order.channel` 分流到各自那本账。
4. **逻辑删除**：业务表统一 `deleted`，查询默认过滤已删数据。

## 6. 执行方式

**方式一：由应用自动迁移（推荐）**
启动 Spring Boot，Flyway 在应用启动时自动创建 `tickcart` 库下的所有表并执行种子数据。数据源与 Flyway 配置见 `backend/src/main/resources/application.yml`。

**方式二：连接已运行的 MySQL 后手动执行**
按版本顺序执行 `V1 → V25` 全部 25 个脚本（需先手动 `CREATE DATABASE tickcart`）。
★ 顺序不能打乱：V8 依赖 V4 的商品、V11 依赖 V6/V9 建的 SKU、V22 依赖 V21 的 `refund_record`、V25 依赖 V3 的 `t_order`。

**连接参数**（`application.yml` 默认值，可用环境变量覆盖）：
`MYSQL_HOST`（默认 localhost）、`MYSQL_PORT`（3306）、`MYSQL_DATABASE`（tickcart）、`MYSQL_USERNAME`（root）、`MYSQL_PASSWORD`（root）。
