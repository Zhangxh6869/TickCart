## 0. 结论先行

**可行，且地基比预想的好。** 退款需要的东西，项目里已经有三样现成的：

| 需要的能力 | 现状 | 位置 |
|---|---|---|
| 库存回补（含秒杀分流） | ✅ 已有 | `OrderService.restoreStock:898` → `InventoryService.restore:94` |
| 状态流转的并发收口范式 | ✅ 已有（条件 UPDATE 抢占） | `ship:775` / `markPaid:802` / `closeTimeout:856` |
| 支付流水的"哪条算数"口径 | ✅ 已有（优先取支付成功那条） | `OrderService.loadLatestPayments:638` |
| 退款表 / 退款状态 / 退款接口 | ❌ 全无 | 迁移只到 `V20`，grep 不到任何 refund |

**推荐分期**（详见 §2）：

- **P0（建议先做）**：待发货「取消并退款」—— 一次 DDL + 状态机加 2 个状态 + 3 个接口，形成完整闭环
- **P1**：待收货「仅退款」（货已发出，不回补库存）
- **P2**：已完成「退货退款」（退货物流 + 入库，本质是仓储子域，单独排期）

**P0 工作量约 2.5 人日**（后端 1 + 前台 0.5 + 后台 0.5 + 测试 0.5）。

## 1. 现状盘点（代码事实）

### 1.1 订单状态机（`OrderStatus.java:61`）

```java
TRANSITIONS.put(PENDING_PAYMENT, EnumSet.of(PENDING_SHIPMENT, CANCELLED, TIMEOUT_CLOSED));
TRANSITIONS.put(PENDING_SHIPMENT, EnumSet.of(PENDING_RECEIPT));   // ← 已付款后唯一出路是发货
TRANSITIONS.put(PENDING_RECEIPT,  EnumSet.of(COMPLETED));
TRANSITIONS.put(COMPLETED, Collections.emptySet());
```

**已支付之后是一条单行道**：只能发货 → 收货 → 完成。`doCancel:740` 第一行就 `assertTransitionTo(CANCELLED)`，所以用户点取消直接 409，`restoreStock` 根本走不到。

### 1.2 用户可做的动作

| 订单状态 | 前台动作 | 后台动作 |
|---|---|---|
| 0 待付款 | 取消（`OrderController:84`）、去支付 | 关闭（`AdminOrderController:75`） |
| 1 待发货 | **无** | 发货 / 批量发货 |
| 2 待收货 | 确认收货（`:91`） | 无 |
| 3 已完成 | **无** | 无 |

### 1.3 支付与资金的现状

支付是**模拟渠道**，但通信结构完整照搬真实支付的三段式（`PaymentService` 类注释）：

```
createPayment（落"待支付"流水，不动订单）
   → MockChannelService.submitResult（投延迟 MQ）
   → PaymentNotifyConsumer → PaymentService.apply（落终态 + markPaid 推进订单）
```

关键点：**`payment_record` 记的是「收款」，退款事实不该写回这张表**（收到过钱是历史事实，退款是另一笔业务）。所以退款需要独立的 `refund_record`。

另一个关键点：同一订单可能有多条支付流水（重试支付），`loadLatestPayments:638` 已经处理了「优先取支付成功那条」。**退款金额必须走同一个口径**，不能直接用 `order.pay_amount` 拍脑袋。

### 1.4 库存回补已有能力

`restoreStock(order)` 按 `channel` 分流：

- 普通订单 → `InventoryService.restore(productId, skuId, qty)`（SKU 真账 + 商品汇总派生账同步）
- 秒杀订单 → `seckillStockAccounting.restore(activityId, userId, qty)`（Redis 计数 + `sold_count`，`decreaseSoldCount` 有 `GREATEST(..., 0)` 下溢保护）

**这套逻辑可以直接复用，不需要新写库存代码。**

## 2. 范围与分期

「退款」不是一件事，是一组能力。按「库存是否干净」和「是否依赖物流」切三期：

| 期 | 能力 | 触发状态 | 库存处理 | 依赖 | 复杂度 |
|---|---|---|---|---|---|
| **P0** | 未发货退款（取消并退款） | 1 待发货 | 立即回补，最干净 | 无 | **低** |
| **P1** | 仅退款（已发货未收货） | 2 待收货 | **不回补**（货在路上/在用户手里） | 无 | 中低 |
| **P2** | 退货退款 | 3 已完成 | 退货入库时回补 | 退货物流 + 入库 + 质检 | **高** |

**为什么 P0 必须先做**：覆盖最高频场景（买错 / 地址错 / 不想买了，绝大多数发生在发货前），且是唯一能复用现有回补逻辑、不引入新概念的切口。做完即形成「付款后也有出口」的完整闭环，P1/P2 都是在它之上加边。

**P2 明确不建议本轮做**：退货退款本质是仓储子域（退货地址、物流单号、入库质检、二次上架），与支付退款是两件事。硬塞进本轮会把一个 2.5 人日的功能拖成两周。

### 2.1 P1 仅退款（已实施）

**范围**：待收货（已发货）订单，用户不要了 / 拒收，退款后订单直接进「已退款」终态。

| 项 | P1 口径 | 理由 |
|---|---|---|
| 状态机 | 加 `PENDING_RECEIPT → REFUNDING` 与 `REFUNDING → PENDING_RECEIPT`（回退边） | 拒绝/撤销后回到「待收货」 |
| 退款类型 | `refund_record.type = 2`（仅退款） | 与未发货退款区分，后台据此决定库存动作 |
| **库存** | **不回补** | 货已出库，可能拒收退回、也可能用户留下了 —— 回补会让库存虚高，是超卖的源头 |
| 销量 | 仍回退 | 用户没拿到货，销量不该计入 |
| 发货守卫 | 无需额外代码 | 订单进「退款中」后 `ship()` 的 `WHERE status=1` 自然挡住 |

**P1 的已知限制（不修，留给 P2）**：

1. **库存永久少 1 件**。仅退款成功后没有「退货入库」动作，货即便真退回来也不会加回 `product_sku.stock`。这是业务正确的（货确实不在仓里），但后台需要对账手段 —— P2 做退货入库时补上。
2. **无法区分「拒收」与「签收后仅退款」**。两者在 P1 走同一条路径，都不回补库存。真实系统靠物流状态区分，本项目没有物流对接。
3. **退款成功后订单进终态，货的归属无人跟踪**。这是 P1 刻意接受的信息损失。

## 3. 核心设计决策（需审批）

> 下面 6 个是真正的岔路口。每条给「推荐 / 备选 / 理由」，请逐条拍板。

### 决策 1 · 订单状态要不要新增「退款中 / 已退款」

**推荐：加。`OrderStatus` 新增 `REFUNDING(6, "退款中")`、`REFUNDED(7, "已退款")`。**

| | 方案 A：加订单状态（推荐） | 方案 B：订单状态不动，只靠 refund_record |
|---|---|---|
| 用户看到的状态 | 「退款中」——与淘宝一致，语义正确 | 仍是「待发货」，但钱已经退了 → **语义错误** |
| 后台防误发货 | 状态机天然挡住（REFUNDING 不能 → 待收货） | 要在 `ship` 里加额外校验，容易漏（批量发货是另一个入口） |
| 列表筛选 | `status=6` 直接筛 | 要 join refund_record，或加冗余字段 |
| 改动面 | `OrderStatus` + `countByStatus` + `adminOverview` + 前端 3 处映射 | 小 |
| 部分退款 | 订单级状态表达不了（但本轮本来就不做） | 天然支持 |

**代价是真实存在的**：新增状态后必须同步 4 处统计/映射（见 §8 影响面清单），漏一处就会出现「订单数对不上」。这个代价我认为值得付 —— 让订单状态撒谎，后面每一处展示都要打补丁。

**配套**：`REFUNDING` 需要两条**回退边**（拒绝退款 / 用户撤销）：

```
REFUNDING → PENDING_SHIPMENT   （拒绝或撤销，回到申请前的状态）
REFUNDING → REFUNDED           （同意并退款成功，终态）
```

回退目标不写死，取 `refund_record.origin_status` —— 这样 P1（待收货发起）不用改代码。

### 决策 2 · 退款金额取哪个字段

**推荐：取「支付成功」那条流水的 `amount`，取不到才回退 `order.pay_amount`，并校验 > 0。**

理由：同一订单可能有多次支付尝试（`createPayment` 每次都新落一条），直接用 `pay_amount` 会在「部分支付/失败重试」的历史数据上算出与实际收款不符的金额。项目已经为此踩过坑（`loadLatestPayments` 的注释：「旧逻辑只取 id 最大，会把已取消订单的失败流水当已付款展示」）。

**并且：退款金额落库为快照**（`refund_record.amount`），不随后续订单改动而变。

### 决策 3 · 库存回补时点

**推荐：按「货在哪」决定，不做统一口径。**

| 场景 | 回补时点 | 理由 |
|---|---|---|
| P0 未发货退款 | **同意退款时立即回补** | 货没出库，回补即正确 |
| P1 仅退款 | **不回补** | 货已发出，可能拒收退回，也可能用户留下了 —— 回补会让库存虚高 |
| P2 退货退款 | **收到退货并入库时回补** | 需要「入库」这个动作存在 |

P1 阶段库存会永久少 1 件，这是**业务正确**的（货真的不在仓里），不是 bug。后台需要能看到「有 N 件货在退款流程中未回仓」的待办 —— 建议 P1 时在库存告急页加一行提示，不新做表。

### 决策 4 · 退款是同步落终态，还是走渠道异步回调

**推荐：P0 同步落终态，但保留 `REFUNDING` 中间态。**

- `REFUNDING` 的真实语义是**「等商家审核」**，不是「等渠道回调」—— 所以它不是摆设，异步与否都不影响状态机的合理性
- 模拟渠道没有真实资金流，硬套 MQ 延迟回调只会让「退款中」多等 1 秒、测试要多等消息，收益为零
- 将来接真实渠道时，只需把 `RefundService.doRefund()` 从「直接置终态」改成「发起渠道退款 + 等回调」，状态机与前端一行不用动

**备选**：复用 `PaymentMqConfig` 的延迟交换机新增 `refund.notify`。不建议 —— 属于「为了对称而对称」。

### 决策 5 · 退款后商品销量要不要回退

**推荐：回退。** `markPaid:813` 在抢到状态流转后调 `accumulateSales` 累加 `product.sales`，退款成功时按明细减回去（`GREATEST(sales - n, 0)` 防下溢，与 `decreaseSoldCount` 同款写法）。

**备选**：不回退，销量只增不减（「累计成交」语义），退款率另做统计。

**这条必须拍板**：它决定商品详情页「已售 N 件」是净销量还是累计销量。我倾向净销量 —— 否则退款后销量虚高，而销量是前台展示字段，用户能直接看到。

### 决策 6 · 部分退款（按商品行）要不要做

> **✅ 已确认（2026-10-29）：延后，本轮不排期。** 排在 P2 之后，用真实退款数据决定是否要降粒度。

**推荐：本轮不做，只支持整单退款。** 但 schema 上留余地（`refund_record` 已有 `amount`，将来加 `refund_item` 子表即可，不动主表）。

理由：部分退款会把「订单状态」这套模型直接打穿（一个订单同时处于「部分退款 + 待发货」），需要引入「退款单驱动、订单状态派生」的重构。**这是另一个量级的设计**，不该混在 P0 里。

#### 6.1 什么是部分退款

**一个订单里只有一部分商品被退掉，剩下的商品继续履约。**

判据不是「退了多少钱」，而是「退款后这笔订单还有没有没履行完的义务」。一个 ¥50 的订单退 ¥50 是整单退款（订单终结），一个 ¥336 的订单退 ¥99 是部分退款（还剩 2 件要发）。

| 形态 | 例子 | 粒度 |
|---|---|---|
| 整单退款 | 三件全退，订单进入终态 | 订单 |
| 部分退款 · 按行 | 买 T恤/裤子/袜子，只退 T恤 | 订单行 |
| 部分退款 · 按件 | 同一商品买 5 件，退 2 件 | 行内数量 |
| 部分退款 · 按金额 | 少发一件补钱、破损补偿、运费不退 | 纯金额 |

★ 注意第二种：**订单里只有一行商品，也可能是部分退款** —— 粒度是「件」不是「行」，所以不能用「明细行数 > 1」来判断。

#### 6.2 P0 的实际限制

用户点「申请退款」，退的是整单 `pay_amount`；`refund_record` 只有 `amount` 一个金额字段，没有「退哪几行、退几件」的位置。想「只退 T恤」→ **没有入口**，这是明确接受的限制。

#### 6.3 为什么这个限制必须延后而不是顺手做

| 崩在哪 | 具体 |
|---|---|
| 库存回补的幂等锚点没了 | `restoreStock:898` 是整单全量遍历，幂等靠「抢到订单状态流转」。部分退款只能补几行，锚点降级成「每行一个标记」 |
| 金额要按行分摊 | 还要处理 `total_amount` 与 `pay_amount` 的差额（运费/优惠）怎么摊到行，并加「已退金额 ≤ 实付金额」的累计校验 |
| 销量回退粒度不够 | `accumulateSales:825` 按 productId 聚合，退款要按行减 |
| 统计口径退化 | `adminOverview:518` 的 `SUM(pay_amount)` 要减掉已退部分 |
| 前端按钮从订单级变行级 | `OrderDetailView:48` 的 `canCancel` 是 `status === N`，要改成按行判断 |
| **部分退款必然带来部分发货** | A 退了但 B 要发 → 需要 `order_item.shipped_quantity`、物流单号按行拆，从「退款」蔓延到「履约」 |

**何时该做**：多件订单占比高、且「我只想退一件」的工单占比超过约 20%；或引入运费/优惠券后金额必须按行分摊。那时代价是**重构订单状态模型**（`status` 从「人写进去的」改成「从行状态聚合出来的」），约 5~8 人日，且要全量回归所有读 `status` 的地方。

## 4. 数据模型（`V21__refund.sql` 草案）

```sql
CREATE TABLE `refund_record` (
    `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    `refund_no`     VARCHAR(32)     NOT NULL                COMMENT '退款单号（唯一，前缀 RF）',
    `order_id`      BIGINT UNSIGNED NOT NULL                COMMENT '关联订单ID',
    `order_no`      VARCHAR(32)     NOT NULL                COMMENT '订单号（冗余，便于查询）',
    `user_id`       BIGINT UNSIGNED NOT NULL                COMMENT '申请用户ID（越权校验用）',
    `type`          TINYINT         NOT NULL DEFAULT 1      COMMENT '1未发货退款 2仅退款(已发货) 3退货退款',
    `amount`        DECIMAL(10,2)   NOT NULL                COMMENT '退款金额（快照，取支付成功流水）',
    `reason_code`   TINYINT         NOT NULL                COMMENT '原因码 1不想要了 2信息填错 3商品问题 4其他',
    `reason`        VARCHAR(255)    DEFAULT NULL            COMMENT '补充说明',
    `status`        TINYINT         NOT NULL DEFAULT 0      COMMENT '0待审核 1已退款 2已拒绝 3已撤销',
    `origin_status` TINYINT         NOT NULL                COMMENT '申请前的订单状态（拒绝/撤销时回退目标）',
    `active_key`    VARCHAR(32)     DEFAULT NULL            COMMENT '进行中标记：进行中=order_no，终态=NULL',
    `audit_remark`  VARCHAR(255)    DEFAULT NULL            COMMENT '审核意见（拒绝时必填）',
    `audit_time`    DATETIME        DEFAULT NULL            COMMENT '审核时间',
    `refund_time`   DATETIME        DEFAULT NULL            COMMENT '退款完成时间',
    `deleted`       TINYINT         NOT NULL DEFAULT 0      COMMENT '逻辑删除 0未删 1已删',
    `created_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_refund_no` (`refund_no`),
    UNIQUE KEY `uk_active_order` (`active_key`),
    KEY `idx_order_no` (`order_no`),
    KEY `idx_user_id` (`user_id`),
    KEY `idx_status` (`status`),
    KEY `idx_created_at` (`created_at`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT '退款单';
```

### 4.1 `active_key` 这个设计为什么要这么绕

需求是「同一订单同时只能有一个进行中的退款单，但历史退款单可以有多条」。MySQL 的**唯一索引允许多个 NULL**，所以：

- 进行中：`active_key = order_no`（占位，第二笔申请撞唯一键 → 拒绝）
- 终态（已退款/已拒绝/已撤销）：`active_key = NULL`（不参与唯一约束）

比「先 select 再 insert」可靠 —— 后者在并发下会插出两条。这是本项目 `idempotent_record` 唯一键思路的同款用法。

### 4.2 为什么加 `origin_status` 而不是写死回退到「待发货」

P1 从「待收货」发起退款、P2 从「已完成」发起，拒绝后要回退到**各自的原状态**。写死就得到时候改代码，加一个 TINYINT 就一劳永逸。

### 4.3 `t_order` 不新增字段

退款单状态通过 `refund_record` 批量 IN 查（复用 `loadItemsGrouped:1056` 的现成范式），不加 `refund_status` 冗余列 —— 订单状态 6/7 已经表达了「有没有退款」，冗余列会和状态机打架。

## 5. 状态机

### 5.1 订单状态机（`OrderStatus.java` 改动）

```java
// 新增枚举
REFUNDING(6, "退款中"),
REFUNDED(7, "已退款");

// ★ P0 只开「待发货」这一个入口，P1/P2 的入口边留到对应阶段再加
TRANSITIONS.put(PENDING_SHIPMENT, EnumSet.of(PENDING_RECEIPT, REFUNDING));   // 新增
TRANSITIONS.put(REFUNDING,        EnumSet.of(REFUNDED, PENDING_SHIPMENT));   // 回退边
TRANSITIONS.put(REFUNDED,         Collections.emptySet());                   // 终态

// P1 再加：PENDING_RECEIPT → REFUNDING、REFUNDING → PENDING_RECEIPT
// P2 再加：COMPLETED → REFUNDING、REFUNDING → COMPLETED
```

**为什么不一次把 P1/P2 的边都声明好**：提前声明有两个实际问题 ——
① 边存在但没人走，读代码的人会以为功能已支持；② `COMPLETED` 一旦有出边就不再是
`isFinal()`，语义被悄悄改掉（现有 `OrderStatusTest.finalStates` 就会红）。

### 5.2 退款单状态机

```
0 待审核 ──同意──▶ 1 已退款（终态）
   │
   ├──拒绝──▶ 2 已拒绝（终态，订单回退 origin_status）
   └──用户撤销──▶ 3 已撤销（终态，订单回退 origin_status）
```

### 5.3 两条状态机的关系

```
订单: 待发货 ──用户申请退款──▶ 退款中 ──商家同意──▶ 已退款
                              │
                              ├──商家拒绝──▶ 待发货（回退）
                              └──用户撤销──▶ 待发货（回退）

退款单:      ──创建(0待审核)──▶       ──审核通过(1)──▶
```

**必须成对推进**：订单进 `REFUNDING` 与退款单落 `0 待审核` 在**同一个事务**里；任一失败整体回滚。

### 13.6 P1 暴露的一个问题（已修）

加了 `REFUNDING → PENDING_RECEIPT` 回退边之后，`ship()` 里的
`assertTransitionTo(PENDING_RECEIPT)` 会把**退款中的订单放行**，一直走到条件 UPDATE
才因 `WHERE status=1` 影响 0 行而失败，报「订单状态已变更，请刷新后重试」——
管理员会以为是自己手慢。

修法：`ship()` 与 `batchShip()` 都先过一道 `assertShippable(status)`，对「退款中」
直接给准确提示。**教训：状态机里的「回退边」和「业务动作边」长得一样，不能只靠转移表判断。**
