## 1. 背景与目标

### 1.1 现状（已实测，非推测）

| 位置 | 现状 | 实测结果 |
|---|---|---|
| 首页搜索框 | `van-search` 带 `readonly`，整块点击 `@click="goList"` | 点它只跳 `/products`，**不携带任何关键词**，用户无法输入 |
| `/products` 页 | 页内有可输入的 `van-search` | **商品区永远是 0 张卡片**，一直显示「加载中...」（van-list 死锁，根因见 §4.1） |
| `/products?keyword=手机` | 页内有输入框，但**不从 URL 读 keyword** | 输入框为空、结果 0 条 |
| 后端搜索接口 | `GET /api/products?keyword=` 已支持 | **可用**：`keyword=手机` 正确返回手机类商品 |

结论：**「搜索界面」目前实际不存在**——首页搜索框是纯装饰跳转，落地的 `/products` 页又是坏的。
后端能力已经就绪，缺的是前端页面 + 一个必须修掉的分页死锁。

### 1.2 目标

1. 新增一个真正可用的**独立搜索页**：能输入、能提交、能看结果、能改词、能翻页、能排序。
2. 补上搜索页应有的**空态内容**：搜索历史 + 热门搜索。
3. 顺手修掉 `/products` 的分页死锁（不修则新搜索页的结果区同样加载不出来）。
4. **不新增数据库表、不改后端接口签名、不改路由层级约定**（默认方案）。

### 1.3 非目标（本阶段不做）

- **联想补全（输入即提示）**：需要新后端接口（很可能还要新表/倒排），超出阶段 2 范围，列为二期。
- 搜索埋点、搜索词统计报表、个性化推荐排序（涉及建表，需单独确认）。
- 拼音搜索、近义词/分词、Elasticsearch 接入（技术栈变更，需单独确认）。
- 搜索历史云端同步（一期只落 localStorage）。

## 2. 关键设计决策（请重点评审 §2.1 的四个选择）

### 2.1 形态选择

| 方案 | 说明 | 结论 |
|---|---|---|
| **A. 独立搜索页 `/search`** | 新路由；顶部「返回 + 输入框 + 搜索」；默认态=历史+热搜，提交后同页切结果态 | ✅ **推荐**。主流电商（淘宝/京东/拼多多）都是这个形态；改词不用来回跳；能放历史和热搜 |
| B. 只修 `/products` 页内搜索 | 改动最小，不新增路由 | ❌ 首页搜索框仍是装饰；没有历史/热搜；`/products` 本身定位是「分类列表页」，塞搜索语义会越来越混 |
| C. 首页搜索框直接可输入 | 首页就地搜索 | ❌ 首页吸顶区只有 42px 高，键盘弹出会顶飞吸顶布局；且首页没有放结果的地方 |

### 2.2 结果区放哪

**内嵌在搜索页内**（同一路由的「推荐态 ↔ 结果态」切换），不跳 `/products`。
理由：保留顶部输入框，用户看到「搜错了」可以立刻改词；避免多一层路由和一次多余的历史记录。
URL 用 `router.replace({ query: { keyword } })` 同步，保证可刷新、可分享，但不会把返回键堆满。

### 2.3 热门搜索的数据来源

| 方案 | 后端改动 | 评价 |
|---|---|---|
| **用 `/api/categories` 的分类名** | **零** | ✅ 推荐。接口已存在，21 个分类名天然是像样的搜索词 |
| 前端写死一组固定词 | 零 | 备选。可控但不会随商品变化 |
| 新增 `GET /api/search/hot-keywords` | 需新接口 + 很可能新表 | 二期。要先做「搜索词 PV 统计」才有意义，需你单独确认建表 |

### 2.4 是否抽公共组件

`/products` 与搜索页的「排序栏 + 商品网格 + 触底分页」是同一套东西。
**推荐抽成 `components/ProductFeed.vue`**：死锁只修一处、排序口径只有一份（符合 AGENTS.md「杜绝重复代码」）。
代价是动了 `/products` 的页面结构，需要回归。若你希望**风险最小**，也可以让搜索页自己写一套、暂时不动 `/products`（但死锁仍必须单独修）。

## 3. 页面结构设计

### 3.1 路由

```
path: '/search'
name: 'search'
meta: { title: '搜索', depth: 2 }
```

- 进入：首页搜索框 → `router.push({ name: 'search' })`；也支持 `/search?keyword=xxx` 直达。
- 返回：左上角返回箭头 → `router.back()`；无历史时兜底回首页。
- **无 tabbar**：`search` 必须加入 `layouts/TabBarLayout.vue` 的 `FULLSCREEN_ROUTES`（二级页自带返回，留着 tabbar 会让人误点跳走）。
- **过渡方向**：首页(depth 1) → 搜索(depth 2) 天然判为 forward（右滑前进），返回 back。**不需要**在 `resolvePageTransition` 里加配对规则。
- **不加进 `CACHED_VIEWS`**：搜索页每次进入都应回到干净的空态，缓存反而会残留上次关键词。

### 3.2 空态（进入后未提交）

```
┌──────────────────────────────────────────┐
│  ←   ┌──────────────────────┐  ┌──────┐  │
│      │ 🔍 搜索商品           │  │ 搜索 │  │
│      └──────────────────────┘  └──────┘  │
├──────────────────────────────────────────┤
│  搜索历史                          🗑 清空 │
│  ( 手机 ) ( 衬衫 ) ( 运动鞋 ) ( 面霜 )     │
│                                          │
│  热门搜索                                 │
│  ( 手机数码 ) ( 鞋类 ) ( 服饰 ) ( 护肤彩妆 )│
│  ( 箱包 ) ( 家居百货 ) ( 运动 ) ( 手表 )   │
└──────────────────────────────────────────┘
```

- 搜索历史：最多 **10 条**，倒序、去重（新词覆盖旧位置），单条点击即搜，右侧「清空」带二次确认（`van-dialog`）。
- 无历史时整个「搜索历史」区块不渲染（不出现空标题）。
- 热门搜索：取 `/api/categories` 前 8 个（`status=1` 已由后端过滤）。

### 3.3 结果态（已提交关键词）

```

│  ←   ┌──────────────────────┐  ┌──────┐  │
│      │ 🔍 手机               │  │ 搜索 │  │
│      └──────────────────────┘  └──────┘  │
├──────────────────────────────────────────┤
│  综合   销量   价格↓   价格↑              │
├──────────────────────────────────────────┤
│  为你找到 37 件商品                       │
│  ┌────────┐  ┌────────┐                  │
│  │ 商品卡  │  │ 商品卡  │                  │
│  └────────┘  └────────┘                  │
│  ┌────────┐  ┌────────┐                  │
│  │ 商品卡  │  │ 商品卡  │                  │
│  └────────┘  └────────┘                  │
│            没有更多了                     │
└──────────────────────────────────────────┘
```

- 排序栏口径与 `/products` 完全一致：`综合=createdAt desc`、`销量=sales desc`、`价格↓=price desc`、`价格↑=price asc`。
- 商品卡复用现有 `components/ProductCard.vue`（2 列网格，价格用 `#323233`，不用电商红）。
- 「为你找到 N 件商品」用 `PageResult.total`。
- 触底翻页用 `van-list`（`size=10`）。
- **空结果**：`van-empty` 描述「没有找到相关商品」+ 副文案「换个关键词试试」，下方保留热门搜索词便于一键换词。
- **请求失败**：走 van-list 的 `error` / `error-text` 态，文案「加载失败，点击重试」。

输入 ≥1 字时的联想下拉列表。需要新后端接口，且要处理防抖、竞态、键盘上下选择，工作量独立成切片。

## 4. 必须一并修掉的既有缺陷

### 4.1 `/products` 的 van-list 死锁（**阻塞项**）

**现象**：`/products` 商品区永远 0 张卡片，持续显示「加载中...」。

**根因**（已读 `vant@4.10.2/es/list/List.mjs` 确认，不是猜测）：

1. `onMounted` → `check()`（`immediateCheck` 默认 true）→ 命中边缘 → **先** `loading.value = true; emit('update:loading', true)`，**再** `emit('load')`。
2. 此时 `ProductListView` 的 `ready` 还是 `false` → `load()` 首行 `if (!ready.value …) return` **直接返回**，没有把 `loading` 复位。
3. `loading` 永久停在 `true` → van-list 的 `check()` 因 `loading.value === true` 永远早退 → 不再 emit `load`。
4. 页面的 `onMounted` 接着 `ready = true; await reload()`，但 `load()` 又被 `loading.value === true` 拦住。
   → **双向死锁**，接口一次都没发出去。

**修复方案**（推荐，最小且无循环风险）：

- 模板上给列表区加 `v-if="ready"`，让 van-list **在分类就绪后才挂载**（挂载时 `ready` 已为 true）；
- `load()` 里**去掉** `!ready` 判断，只保留 `if (loading.value || finished.value) return`。

为什么不能用「在早退分支里把 `loading` 复位」：那会让 `watch(() => [props.loading, …], check)` 立刻重新 `check()` → 再次 `emit('load')` → 又早退 → **无限循环**。

**顺带确认**：van-list 内部 `watch(() => [props.loading, props.finished, props.error], check)`，
所以 `loading` 由 true 回到 false 时会自动再 `check()` 一次 —— 首屏商品不足一屏时会自动续拉第二页，**不会卡住**。

### 4.2 关键词通配符未转义（正确性问题）

**实测**：`GET /api/products?keyword=%` 与 `keyword=_` 都返回了全部商品。

原因：`ProductService.filterWrapper` 用 `LambdaQueryWrapper.like(Product::getName, keyword)`，
MyBatis-Plus 只做 `%value%` 拼接，**不转义用户输入里的 `%` 和 `_`**。
用户搜「100%」会命中全库，属于明显的搜索行为错误。

**修复**：拼进 `like` 前对 `\` `%` `_` 做转义（并显式指定 `ESCAPE '\'`，或统一改用 `apply` + 参数绑定）。
**这属于后端业务逻辑改动，按 AGENTS.md 需要你先确认再做。**

### 4.3 首页搜索框

`readonly` + `@click="goList"` → 改为跳 `/search`（保留 `readonly`，样式不动）。

| 约定 | 本方案的处理 |
|---|---|
| 二级页隐藏 tabbar | `search` 加入 `FULLSCREEN_ROUTES`；**同步** `address-tabbar-hidden-verify.mjs` C 段的断言表 |

## 7. 边界与异常处理

| 场景 | 处理 |
|---|---|
| 空 / 纯空格关键词 | `trim()` 后为空 → 不请求，停留空态 |
| 超长关键词 | 输入框 `maxlength=30`，后端无长度限制故前端先收口 |
| `%` `_` `\` `'` 等特殊字符 | 后端转义（§4.2，待确认）；前端不做半吊子兜底 |
| 快速连续改词 / 连点搜索 | 递增 `requestId`，只接受最后一次响应，丢弃过期结果 |
| 请求失败 | van-list `error` 态 + 「加载失败，点击重试」 |
| 结果为空 | `van-empty` + 热门词快捷换词 |
| 未登录 | 搜索是公开接口，未登录也能用；不挂 `requiresAuth` |
| 返回 | `router.back()`；直接打开 `/search` 无历史时 `router.replace('/')` |
| 键盘收起后布局 | 不依赖 `100vh`，用 `calc(100vh - 50px)` 同款写法，避免移动端键盘顶飞 |

### 12.1 切片 1：修 `/products` 死锁（已完成）

实施时发现 §4.1 只写出了一个成因，**实际是双重死锁**，两个都要修才通：

| # | 成因 | 修法 |
|---|---|---|
| 1 | `load()` 首行的 `if (!ready.value) return`：van-list 挂载时先置 `loading=true` 再 emit `load`，早退后 `loading` 永久停在 true | 模板给列表区加 `v-if="ready"`，让 van-list 等分类就绪后再挂载；`load()` 不再判 `ready` |
| 2 | `if (loading.value …) return`：van-list 触底时**先** `loading.value = true; emit('update:loading', true)`，**再** `emit('load')` —— 进入 `load()` 时 `loading` 已是 true，等于把自己刚触发的那次请求挡在门外 | 改用独立的 `requesting` 布尔量做并发锁，`loading` 只用于向 van-list 表达「正在加载」 |

顺带补了 `generation` 请求代号：切分类 / 换排序时自增，响应回来若已过期就丢弃，避免慢请求覆盖新结果。

**验证**：`.workbuddy-ai/tmp/cdp/products-list-verify.mjs`（只读，用 `performance.getEntriesByType('resource')` 取真实请求列表）——
修前首屏 0 张卡片、只有「加载中...」；修后首屏 10 张、触底发出 `page=2`、切「鞋类」首卡变为「篮球实战鞋 黑白红」。**全部断言通过**，`vite build` 通过。

### 12.13 建议5：搜索同义词表（已完成）

问题：用户搜的词与商品里的词对不上——典型「苹果手机」搜不到 iPhone 系列。实测

**数据层（V14）** `search_synonym` 用**同义词「组」模型**：
`(id, group_id, word, created_at)`，同一 `group_id` 下的词互为同义词（天然对称、天然 1:N），
`uk_word` 保证一个词只归属一个组。种子 4 组共 10 行：
`苹果手机↔iPhone`、`笔记本电脑↔笔记本↔电脑`、`无线耳机↔蓝牙耳机↔耳机`、`唇膏↔口红`。

**召回**：新增 `SearchSynonym` 实体 + `SearchSynonymMapper`（子查询取同组词）+ `SynonymService.expand`；
