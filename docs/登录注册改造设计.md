# 登录注册改造设计（手机号统一为登录账号）

> 版本：v1（**已实施**，2026-11-01）
> 范围：`/api/auth/login`、`/api/auth/register`、`/api/auth/register/sms` 及前后台登录/注册页
> 约束：遵循 `AGENTS.md` —— **不改表结构、不增删字段**；登录凭据属于核心业务逻辑，已人工确认后方进入设计。

---

## 一、改造目标

| # | 现状 | 目标 |
|---|---|---|
| 1 | 账密登录用「用户名 + 密码」 | 账密登录用「**手机号 + 密码**」 |
| 2 | 登录页有独立的用户名输入框，两种方式切换时整块表单换掉 | 手机号字段**常驻**，切换方式只改变「密码 / 验证码」这一项 |
| 3 | 账密注册的手机号可选、无验证码 | 手机号、用户名、密码、**短信验证码**四项必填 |
| 4 | 注册收集昵称 | 不再收集，`nickname` 落库恒等于 `username` |
| 5 | 后台管理端用「用户名 + 密码」登录 | 同步改为「手机号 + 密码」 |

**一句话**：一个账号只有一个登录凭据 —— 手机号；用户名退回「注册时起的展示名 + 唯一标识」。

---

## 二、需求定义

### 2.1 登录

- 账号统一为**手机号**，账密登录与验证码登录共用同一个手机号输入框。
- 切换登录方式时：手机号**保留不清空**，只有第二项在「密码 / 验证码」之间切换。
- 验证码登录的业务规则不变（scene=2，手机号必须已注册，未注册返回「该手机号尚未注册」）。
- 登录失败仍走原有频控：QPS → 锁定态 → 图形码 → 凭据比对；失败计数与锁定 key 由「IP + 用户名」改为「IP + 手机号」。

### 2.2 注册

必填四项，**字段顺序：用户名 → 手机号 → 密码 → 验证码**。

| 字段 | 必填 | 规则 |
|---|---|---|
| 用户名 | 是 | 4~20 位，仅字母/数字/下划线，全局唯一 |
| 手机号 | 是 | `^1[3-9]\d{9}$`，全局唯一 |
| 密码 | 是 | 8~32 位，必须同时含字母和数字，且不得含空白 |
| 验证码 | 是 | 6 位数字，短信场景 = 1（注册），一次性 |

- 昵称输入框删除，`nickname` 落库 = `username`；`sys_user.nickname` 字段**保留不动**（`ProfileView`、后台用户管理仍在展示它）。
- 注册成功后仍自动登录（返回 `TokenResponse`），前端跳回 `route.query.redirect || '/'`。
- 注册态**不做登录方式切换**，`method` 在进入注册时强制重置为 `password`，避免从验证码登录切过来时残留状态。

## 三、已确认决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 后台管理端登录 | 同步改为手机号（默认 `13800000000`） |
| 2 | 注册接口 | `/register` 与 `/register/sms` **都保留，都校验验证码** |
| 3 | 历史 phone 为空的老账号 | 不处理，自然无法登录 |
| 4 | 注册页字段顺序 | 用户名 → 手机号 → 密码 → 验证码 |
| 5 | 昵称 | 取消输入，落库取用户名 |
| 6 | 登录失败文案 | 统一「手机号或密码错误」，不暴露账号是否存在 |

## 四、接口契约

### 4.1 变化总览

| 接口 | 变化 | 破坏性 |
|---|---|---|
| `POST /api/auth/login` | `username` → **`phone`**，`password` 不变 | **是** |
| `POST /api/auth/register` | `phone` 改必填；**新增 `code` 必填**；删除 `nickname` | **是** |
| `POST /api/auth/register/sms` | `username`、`password` 改必填；删除 `nickname` | **是** |
| `POST /api/auth/login/sms` | 无变化 | 否 |
| `POST /api/auth/sms/send` | 无变化（scene 1/2/3 语义不变） | 否 |

### 4.2 请求示例

```jsonc
// POST /api/auth/login —— 账密登录
{ "phone": "13900000000", "password": "123456" }

// POST /api/auth/register —— 账密注册（四项必填）
{ "username": "alice", "phone": "13700000000", "password": "abc12345", "code": "483920" }

// POST /api/auth/register/sms —— 验证码注册（改造后与上面等价）
{ "username": "alice", "phone": "13700000000", "password": "abc12345", "code": "483920" }
```

### 4.3 错误语义

| 场景 | HTTP | 文案 |
|---|---|---|
| 手机号格式不对 | 400 | 手机号格式不正确 |
| 手机号/密码不匹配 | 401 | 手机号或密码错误 |
| 用户名已存在 | 409 | 用户名已存在 |
| 手机号已被注册 | 409 | 手机号已被注册 |
| 验证码错误 | 400 | 验证码错误 |
| 验证码错满 5 次 | 400 | 验证码错误次数过多，请重新获取 |
| 密码命中弱口令 | 400 | 密码过于简单，请更换一个 |
| 密码包含用户名 | 400 | 密码不能包含用户名 |

## 五、后端设计

### 5.1 登录链路（`AuthService#loginByPassword`）

顺序保持不变，只替换「账号」的来源：

```
QPS(ip) → 锁定态(ip, phone) → 需要验证? → 图形码校验
        → findByPhone(phone) → BCrypt 比对（不存在时用 dummyHash 陪跑）
        → 失败计数 / 成功清零 → issueTokens
```

- `String account = req.getPhone()`：局部变量由 `username` 改为 `account`，与「账号」语义对齐。
- `findByUsername` → `findByPhone`。
- **`dummyHash` 陪跑必须保留**：账号不存在时也要跑一次 BCrypt，否则响应时间差 50~100ms，靠计时就能枚举手机号是否注册过。
- 失败文案统一为「手机号或密码错误」。

**为什么登录不再接受用户名**：两套凭据并存会让失败计数、阶梯锁定、图形码挑战各维护一份 key；改手机号或改用户名后，旧 key 还会残留，锁定态与账号的真实状态脱节。一个账号只留一个登录入口，这些问题从根上消失。

### 5.2 登录守卫（`LoginGuard` / `RedisLoginGuard`）

- 方法参数 `username` → `account`，纯语义修正，**Redis key 前缀不变**（`auth:fail:acct:` / `auth:lock:acct:` / `auth:gate:acct:`），旧 key 自然过期，不需要清理脚本。
- 阶梯锁定规则（1 轮 15 分钟 / 2 轮 60 分钟 / 3 轮起 1440 分钟）与 IP 维度封禁逻辑**完全不动**。

### 5.3 注册链路

两个接口收敛到同一套顺序：

```
密码策略 → 消费验证码(scene=1) → 查重(手机号/用户名) → 建号(nickname=username) → issueTokens
```

```java
@Transactional(noRollbackFor = SmsCodeExhaustedException.class)
public TokenResponse registerByPassword(RegisterRequest req) {
    passwordPolicy.validatePassword(req.getPassword(), req.getUsername());
    verifyAndConsumeCode(req.getPhone(), SMS_SCENE_REGISTER, req.getCode());
    assertNotRegistered(req.getPhone(), req.getUsername());
    return issueTokens(createUser(req.getUsername(), req.getPhone(), req.getPassword()));
}
```

**三个刻意的顺序选择**

1. **密码策略先于消费验证码**：不合规的密码不该白白吃掉一次验证码（沿用现有 `registerBySms` 的做法）。
2. **消费验证码先于查重**：反过来的话，未验证手机号的人就能用「手机号已被注册」这条提示探测注册状态。代价是「手机号已注册」也会走到消费这一步 —— 但因为查重抛出的 `BizException` 会回滚整个事务，`markUsed` 一起回滚，验证码实际仍然可用，用户修正后可重试。
3. **`noRollbackFor = SmsCodeExhaustedException`**：验证码错满上限时要把码作废，这个动作不能被回滚掉，否则「作废」等于没做。

**`createUser` 抽取**：两条注册接口的建号逻辑完全一致（BCrypt、`gender=0`、`role=0`、`status=0`、`nickname=username`），抽成一个私有方法，避免两处各写一遍后逐渐分叉。

### 5.4 DTO 校验

| DTO | 字段 | 注解 |
|---|---|---|
| `LoginRequest` | `phone` | `@NotBlank` + `@Pattern("^1[3-9]\\d{9}$")` |
| `LoginRequest` | `password` | `@NotBlank` + `@Size(1,32)` + `@Pattern("^\\S+$")`（**不校验强度**） |
| `RegisterRequest` | `username` | `@NotBlank` + `@Size(4,20)` + `@Pattern("^[a-zA-Z0-9_]+$")` |
| `RegisterRequest` | `phone` | `@NotBlank` + `@Pattern("^1[3-9]\\d{9}$")`（由可选改必填） |
| `RegisterRequest` | `password` | `@NotBlank` + `@Size(8,32)` + `@Pattern("^(?=.*[A-Za-z])(?=.*\\d)\\S+$")` |
| `RegisterRequest` | `code` | `@NotBlank` + `@Pattern("^\\d{6}$")`（**新增**） |
| `SmsRegisterRequest` | `username` | `@NotBlank` + `@Size(4,20)` + `@Pattern("^[a-zA-Z0-9_]+$")`（由可选改必填） |
| `SmsRegisterRequest` | `password` | `@NotBlank` + `@Size(8,32)` + `@Pattern(...)`（由可选改必填） |
| 两个注册 DTO | `nickname` | **删除字段**（旧客户端多传会被 Jackson 忽略，Spring Boot 默认不因未知字段报错） |

> 登录侧密码只卡长度上限，**不加复杂度校验**：`demo` 的密码是 6 位纯数字，登录侧一旦卡强度，演示账号与全部健康检查脚本都会失效。强度只属于「设置新密码」的场景（注册）。

|---|---|
| `auth/dto/LoginRequest.java` | `username` → `phone`，换校验与注释 |
| `auth/dto/RegisterRequest.java` | `phone` 必填、新增 `code`、删除 `nickname` |
| `auth/dto/SmsRegisterRequest.java` | `username`/`password` 必填、删除 `nickname` |

## 六、前端设计

### 6.1 字段可见性矩阵

`utils/login-form.ts` 的 `showsCredentialFields` / `showsPhoneFields` 语义已不再够用（它们按「账密组 / 手机组」分组，而新需求是按「单个字段」判定），改为逐字段判定：

| 字段 | 登录·账密 | 登录·验证码 | 注册 |
|---|---|---|---|
| 用户名 | ✗ | ✗ | ✓ |
| 手机号 | ✓ | ✓ | ✓ |
| 密码 | ✓ | ✗ | ✓ |
| 验证码 | ✗ | ✓ | ✓ |

对应纯函数：

```ts
showsUsername(ctx)  // 仅注册
showsPhone(ctx)     // 恒 true（登录两种方式 + 注册）
showsPassword(ctx)  // 账密登录 或 注册
showsCode(ctx)      // 验证码登录 或 注册
```

**核心约定不变**：只校验当前可见的字段，不可见字段一律返回空串。历史回归（短信登录被隐藏的账密字段拦住、点按钮无反应）就是这条约定被破坏造成的，改造时不能退化。

### 6.2 登录页布局（`views/LoginView.vue`）

```
返回箭头 / 品牌
标题（欢迎回来）
手机号        ← 常驻第一行
密码 或 验证码 ← 按方式切换，第二行
[用验证码登录 / 用账号密码登录]  [忘记密码？]
错误提示（凭据错误 / 锁定倒计时 / 需要验证）
[登录]
还没有账号？立即注册
```

- 删除用户名输入框。
- 手机号输入框 `autocomplete="tel"`、`inputmode="numeric"`。
- 切换方式只切换第二行，手机号值保留；`toggleMethod()` 仍调用 `resetErrors()`，但**不清空手机号**。

### 6.3 注册页布局

```
返回箭头 / 品牌
标题（创建账号）
用户名        ← 4~20 位字母数字下划线
手机号
密码          ← 8~32 位，含字母和数字
验证码  [获取验证码]   ← 30s 倒计时
错误提示
[注册]
已有账号？去登录
```

- 删除昵称输入框。
- 「获取验证码」使用 `SMS_SCENE.REGISTER = 1`；登录验证码方式用 `SMS_SCENE.LOGIN = 2`。
- 进入注册态时 `method` 强制置为 `password`（注册不展示方式切换）。

### 6.4 前端校验规则

| 字段 | 登录 | 注册 |
|---|---|---|
| 用户名 | 不校验（不可见） | 必填 + 4~20 位 + 字符集 |
| 手机号 | 必填 + `^1[3-9]\d{9}$` | 同左 |
| 密码 | 必填 + ≤32 位 + 不含空格（**不校验强度**） | 必填 + 8~32 位 + 字母与数字 |
| 验证码 | 验证码方式必填 + 6 位数字 | 必填 + 6 位数字 |

## 九、风险与兼容

| 风险 | 影响 | 处置 |
|---|---|---|
| `/api/auth/login` 入参是破坏性变更 | 未同步的调用方直接 400 | 已列入清单：mall、admin、E2E、两个压测脚本 |
| phone 为空的历史账号 | 无法登录 | 已确认不处理；本地库仅 `admin`/`demo` 两个种子账号且都有手机号 |
| 注册从此依赖短信验证码 | Mock 关闭时注册不可用 | 本项目 Mock 是最终形态；`mock-enabled=false` 时本就 fail-loud |
| 逻辑删除用户仍占用用户名/手机号 | 同名无法重新注册 | 既有行为，本次不变 |
| 并发同名注册 | 唯一索引抛 `DuplicateKeyException` → 500 | 既有缺口，建议后续补 `DataIntegrityViolationException` handler 转 409 |

## 十、决策记录

| # | 问题 | 结论 |
