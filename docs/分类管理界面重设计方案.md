> ① `分类管理重设计①：修「清空阈值不生效」+ 4 个窄接口`
> ② `分类管理重设计②：列表页重做（拖拽排序 + 行内编辑）`
> 原型：`docs/design/category-manage-redesign.html`（浏览器打开，顶部切换 A/B/C，`#a` `#b` `#c` 直达）
> 落地实现：`frontend/apps/admin/src/views/CategoryManageView.vue`

## 已定的五个决策

| # | 问题 | 结论 |
|---|---|---|
| 1 | 选哪个方案 | **方案 A**（表格增强 + 行内编辑） |
| 2 | 排序方式 | **拖拽**（原生 HTML5，不引 sortablejs） |
| 3 | `icon` 字段 | **去掉表单输入框**，列保留；V20 清掉那条 `D:\...` 脏数据 |
| 4 | 二级分类 | **确定不做**，但**保留下拉** —— 它是「库存预警线继承」的唯一数据来源，去掉继承链就成死代码 |
| 5 | 删除按钮 | **有商品就置灰 + tooltip 说明** |

> **★ 落地时发现一个我自己引入的 bug**：把预警线清空（留空 = 继承）时接口返回
> success、库里纹丝不动。原因是 MyBatis-Plus 默认 `update-strategy: NOT_NULL`
> 会把值为 null 的字段从 UPDATE 的 SET 里剔掉 —— 代码里「无条件赋值」看着是对的，
> 实际没写进去。修法：实体加 `@TableField(updateStrategy = ALWAYS)`，
> 窄接口用 `LambdaUpdateWrapper.set()` 显式写列。

> **★ 第 4 条的判断在查代码后改了**：最初建议「确定不做二级分类就把父分类下拉去掉」，
> 但查完发现 `parent_id` 只有两处消费者 —— 阈值继承链（`StockWarnService`）
> 和删除前的子分类检查。去掉下拉，阈值继承就永远走不到（parentId 全是 0），
> 那段逻辑变死代码。所以改成**保留下拉 + 在表单里写明它只影响继承**。

## 一、先看事实（都实测过，不是推测）

| 事实 | 数据 | 影响 |
|---|---|---|
| 分类全部是顶级 | 20 个分类，`parent_id` 全为 0，`level` 全为 1 | 「父分类」列全是"顶级"、「层级」列全是 1 —— **两列零信息量** |
| `icon` 字段基本没人填 | 20 个里 19 个为空 | 后台有个「图标URL」文本框要人手填路径 |
| **商城端不渲染图标** | 首页分类栏只用 `cat.name`（`HomeView.vue` 的 `categoryTabs`） | `icon` 是彻底的死字段 |
| 每个分类下都有商品 | 手机数码/鞋类/服饰各 20 个，其余各 6 个 | **现在没有一个分类能被删除** |
| 分类顺序直接影响前台 | 商城首页分类栏按 `sort` 升序排 | 调顺序是高频操作 |

## 二、现状诊断

| # | 问题 | 说明 |
|---|---|---|
| 1 | **两列纯占位** | 「父分类」全是"顶级"、「层级」全是 1，占 220px 却零信息 |
| 2 | **ID 列是开发视角** | 运营不需要知道 `id=13`，80px 白占 |
| 3 | **图标 URL 要手填** | 输入 `/img/xxx.png` 这种路径，运营填不了；而且商城端根本不显示 |
| 4 | **排序要手填数字** | 想把「食品生鲜」从第 23 挪到第 5，得先想清楚中间值再改两个数字 |
| 5 | **看不到影响面** | 每个分类多少商品、多少告急，列表上没有；删除时点了才知道「存在商品」 |
| 6 | **删除按钮是"假亮"的** | 20 个分类全都有商品，全都删不了，但按钮看起来可点，点完弹报错 |
| 7 | **状态是只读 tag** | 启用/禁用是高频开关，却要开弹窗、选 radio、点保存 |
| 8 | **阈值要开弹窗改** | 上一轮刚加的「库存预警线」，改一次要开一次弹窗，而且弹窗必须带全字段（`name`/`parentId` 必填） |
| 9 | **没有搜索** | 20 个还能翻，涨到 50 个就找不到了 |
| 10 | **表单字段顺序错** | 「图标URL」排在「排序」前面，把最没用的放最前 |

**一句话总结**：这个页面的真实任务是**「调顺序 + 切状态 + 配阈值 + 看影响面」**，而现在的实现把力气花在了「维护一棵不存在的树」和「填一个没人看的图标路径」上。

## 三、三个方案

### 方案 A · 表格增强 + 行内编辑（`#a`，推荐）

保留表格，把力气花在真正的高频操作上：

- **砍列**：去掉 ID / 层级 / 父分类三列；ID 和「顶级分类」下沉成名称下方的小字
- **商品列**：`20 个商品 · 1 告急`（告急数 > 0 才标红）
- **排序**：`▲` `▼` 两个小按钮（外加拖拽手柄），**不填数字**
- **库存预警线**：行内输入框，空 = 显示占位符「继承 10」，失焦即保存
- **状态**：`el-switch` 直接切
- **删除**：分类下有商品就置灰，`title` 说明原因（"该分类下有 20 个商品"），不用点了才报错
- **搜索框**：按名称过滤
- **树形能力保留**：数据按 `parentId` 嵌套 + `el-table` 的 `tree-props`，将来有二级分类自动展开，不用重做

**成本**：前端 1 文件重写；后端 **+4 个窄接口**（见第五节）。

### 方案 B · 左树 + 右详情（`#b`）

- 左侧 268px 分类树（带商品数徽标、可拖拽排序）
- 右侧：选中分类的基础配置 + **它下面的商品列表**（前 4~10 个，带库存和告急标）
- 删除放在右侧「危险操作」区，并把不能删的原因写在旁边

**优点**：改一个分类时能直接看到它的商品，「影响面」最直观。
**缺点**：现在 20 个全是顶级，左树就是一列 20 行，和方案 A 的列表没区别，却白占 268px；将来有二级才发挥价值。

### 方案 C · 分类卡片（`#c`）

- 每个分类一张卡：名称 / ID / 状态 / 商品数 / 告急数 / 阈值 / 操作
- 视觉最轻，扫一眼能看完全局

**优点**：改阈值、切状态都在卡上，不用开弹窗。
**缺点**：**表达不了顺序**（商城首页顺序是这个页面最要紧的东西），20 个分类一屏只能放 5~6 张。

## 四、对比与推荐

| 维度 | A · 表格增强 | B · 左树右详情 | C · 卡片 |
|---|---|---|---|
| 调顺序 | **▲▼ + 拖拽** | 左侧树拖拽 | **做不了** |
| 改阈值 | **行内改** | 右侧表单改 | 行内改 |
| 切状态 | **switch 直接切** | 右侧 switch | switch 直接切 |
| 看影响面 | 只给数字 | **能看商品清单** | 只给数字 |
| 一屏密度 | **12 条** | 左树一屏 + 右侧 | 5~6 张 |
| 将来有二级分类 | tree-props 展开 | **天然支持** | 表达不了 |
| 后端改动 | +4 窄接口 | +5 接口 | +2 窄接口 |

**推荐 A。** 理由：现在没有二级分类，B 的主从结构和 C 的卡片都在为不存在的需求付成本；而 A 恰好解决诊断里 10 条中的 7 条，且把「顺序」这个最要紧的操作做对了。

B 的「看商品清单」确实有价值，但它可以后面单独做——商品管理页已经支持 `?categoryId=` 筛选，从分类跳过去就行，不必在一个页面里塞两个列表。

## 五、落地拆解

### 5.1 要补的 4 个后端接口

现在的接口只够「开弹窗改整个分类」，行内操作都不支持（`PUT /categories/{id}` 要求 `name`、`parentId` 必填，只传一个字段直接 400）。

```
GET  /api/admin/categories/overview
     → [{ id, name, parentId, sort, status, stockWarnThreshold,
          effectiveThreshold, productCount, lowStockCount }]
       商品数与告急数在内存里算（一次取 (category_id, stock)，162 行），
       不写 GROUP BY + 阈值条件 —— 阈值要按分类继承，SQL 里再实现一遍会分叉

PUT  /api/admin/categories/{id}/stock-threshold?value=30
     value 省略 = 改回继承（NULL）
     只更新 stock_warn_threshold 一列

PUT  /api/admin/categories/{id}/status?status=0
     只更新 status 一列

PUT  /api/admin/categories/reorder
     body: [3, 1, 5, ...]   按数组顺序重写 sort = index
     拖拽/上移下移都调这一个
```

**为什么不用现有接口凑合**：行内改一个阈值却要带上 `name`/`parentId`，等于前端每次都得先读一遍整个对象再整体提交；并发下还可能把别人刚改的名字覆盖回去。

### 5.2 前端（已落地）

| 切片 | 内容 |
|---|---|
| 1 | 列表重做：砍掉 ID / 父分类 / 层级 / 排序 四列，加商品用量列、阈值行内、状态 switch、删除置灰、搜索 |
| 2 | 新增/编辑弹窗瘦身：名称 / 父分类 / 预警线，去掉图标URL 与排序 |
| 3 | 拖拽排序：**用原生 HTML5 拖拽，没有引 sortablejs** |

**为什么不用 sortablejs**：`frontend/pnpm-lock.yaml` 每次跑 pnpm 命令都会被塞一段
重复的 lock 块（`git diff --numstat` 永远是「增 N / 删 0」），加依赖必然要动它。
原生 DnD 在这个场景（单列纵向排序）足够，40 行搞定，零依赖。

### 5.3 迁移

**不需要表结构变更。** 只有一个数据清理：V20 把「不像 URL」的分类图标清空
（唯一填过的那条是 `D://develop//...//iphone_17__...jpg` 本地磁盘路径）。
