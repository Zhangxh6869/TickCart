# 后台「搜索分析」界面重设计方案

> 状态：**待选型**。本文件只记录设计与落地成本，代码尚未改动。
> 原型：`docs/design/search-analytics-redesign.html`（浏览器打开，顶部可切换 A/B/C，也支持 `#a` `#b` `#c` 直达）

## 一、现状诊断

当前实现 `frontend/apps/admin/src/views/SearchAnalyticsView.vue`（131 行）+ `GET /api/admin/search-stats`。

| # | 问题 | 说明 |
|---|------|------|
| 1 | 指标无主次 | 三个等宽数字卡平铺，「无结果率」这个最该看的指标要人工 `noResultSearches / totalSearches` 心算 |
| 2 | 只有快照，没有趋势 | `search_log` 有 `created_at` + `idx_created_at`，完全能按天聚合，但接口没做 → 看不出「在变好还是变坏」 |
| 3 | 看到问题，无法处理 | 无结果词本质是运营待办，现在只能看。后端已有 `search_synonym` 表可复用（加同义词后下次就能命中） |
| 4 | 版面浪费 | 两张表 12/12 平分：热搜词 6 列挤，无结果表 4 列空 |
| 5 | 命中率无视觉编码 | 纯文字百分比，20 行扫不出问题项 |
| 6 | 空状态无引导 | `empty-text="暂无搜索记录"`，没解释为什么、该做什么 |

## 二、三个方案

### 方案 A · 诊断台（待办优先）
**一句话**：回答「今天该补什么货」。

- 顶部健康条：无结果率大字 + 一句话结论（哪个品类在漏）+ 有结果/无结果占比条
  - **吸收 B 的迷你趋势**：占比条右侧接一条 96×26 的 sparkline，画「每日无结果率」，
    后跟文案 `近 7 天 20.0% → 19.0%`。同一行左边是当期快照（7 天合计 20.5%），
    右边是走势，避免读者只看到一个孤立数字。
    - 口径必须写清首尾值，不能写 `↓1.0pt` —— 左侧 20.5% 是 7 天合计，
      右侧 20.0→19.0 是首尾单日，写相对变化量会让人误以为 20.5% 降到 19.5%
- 左栏「搜不到的词」：做成**可操作清单**，每行带 `+ 同义词` / `建商品` 按钮，支持「≥3 次 / ≥10 次」过滤掉噪音
- 右栏「热搜词」：条形长度=搜索量，命中率 <90% 的条自动转橙色
- 底部可折叠「原始搜索日志」

**后端改动：清单部分 0；趋势需 +1 接口**（即下面 B 的 `trend`，两个方案可共用同一个接口）
**适合**：小团队日常盯盘，打开就知道下一步干什么

### 方案 B · 趋势看板（数据优先）
**一句话**：回答「搜索在变好还是变坏」。

- 4 个 KPI 卡：搜索总量 / 无结果率 / 独立关键词 / 人均搜索，各带环比 + 迷你 sparkline
- 主图：**堆叠面积图**（有结果 + 无结果 = 总量），红色带即「白搜了」，一眼看出无结果量随总量同步涨
- 下方双榜：热搜词 TOP10、无结果词 TOP10 横向条形

**后端改动：+1 接口** `GET /api/admin/search-stats/trend?days=7`
```sql
SELECT DATE(created_at) AS day,
       COUNT(*)          AS total,
       SUM(result_count = 0) AS miss
FROM search_log
WHERE created_at >= #{since}
GROUP BY DATE(created_at) ORDER BY day
```
**适合**：周会/汇报截图，向上说明搜索质量走势

### 方案 C · 机会矩阵（分析优先）
**一句话**：回答「哪些词值得投」。

- 搜索漏斗：发起搜索 → 搜到结果 → 无结果流失 →（点击/加购/下单，待埋点）
- 核心：**搜索量 × 无结果率** 四象限散点，气泡大小=搜索次数
  - 黑洞词（量大 + 搜不到）= 供给缺口，最该动手
  - 潜力词（量大 + 命中差）= 分词/别名问题
  - 明星词（量大 + 命中高）= 运营位选品
  - 长尾词 = 噪音
- 右侧「自动洞察」卡：按象限生成结论文案 + 建议动作按钮
- 底部关键词明细表，无结果率单元格做热力着色

**后端改动：+1~2 接口**（明细表需要全量关键词，不能只靠两个 TOP20 榜拼）
```
GET /api/admin/search-keywords?days=7&limit=200   -- 关键词明细（可先复用 hotTopN 放大 limit）
GET /api/admin/search-stats/trend?days=7          -- 漏斗与趋势复用 B 的接口
```
漏斗后两段（点击/加购/下单）**需要新埋点**，短期留空占位。

**适合**：想拿搜索数据反推选品/供给，面试叙事也最强

## 三、对比

| | A 诊断台 | B 趋势看板 | C 机会矩阵 |
|---|---|---|---|
| 回答的问题 | 该补什么货 | 在变好还是变坏 | 哪些词值得投 |
| 后端改动 | 0（加趋势则 +1，与 B 共用） | +1 接口 | +1~2 接口 |
| 前端工作量 | 中（纯重构） | 中（SVG 图） | 大（矩阵+洞察） |
| 数据前提 | 现有即可 | 需按天聚合 | 需明细 + 部分埋点 |
| 日常价值 | 高 | 中 | 中 |
| 汇报价值 | 低 | 高 | 高 |

## 四、推荐

**A 为主 + 吸收 B 的迷你趋势**（A 版布局，健康条里内嵌 sparkline + 保留待办清单）。理由：
1. 搜索分析的真实使用者是运营，核心诉求是「发现供给缺口并处理」，A 直接闭环
2. 迷你趋势只占一行，却能补上「判断变好变坏」，成本是 B 的那个 `trend` 接口（一条 SQL）
3. C 的矩阵视觉冲击强但信息密度低，适合作为后续「关键词详情页」而不是主界面

注意：`trend` 接口一旦做了，A 和 B 共用同一份数据，**先做 A 不必浪费**。

若目标是**面试演示**，则选 C（洞察感最强），但需先补 `/search-keywords` 接口。

## 五、落地时需注意

- 复用现有 `AdminLayout`（侧栏 `#001529` + `#1890ff` 选中态），只重写 `SearchAnalyticsView.vue`
- 图表用内联 SVG 手写即可，**不引入 ECharts**（admin 现在没有图表库，为一个页面加 1MB 依赖不划算）
- sparkline 在原型里已抽成公共函数（`sparkline(id, data, color, w, h)`），A 的健康条与 B 的 KPI 卡共用，落地时抽成 `components/SparkLine.vue`
- 「+ 同义词」写入现有 `search_synonym` 表，注意 `SearchSuggestionService` 有缓存，需同步失效
- 时间范围沿用 `days<=0 表示全部` 的既有约定，前端不要另造语义
