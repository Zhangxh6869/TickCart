## 结论

**方案 A 已落地**，后端最终是 **1 个新接口 + 1 个详情 VO + 4 个列表字段 + 3 个查询参数 + 2 个写接口**，全部是加法，没动既有语义。

一句话：这个页面的真实任务是**「每天把待发货清掉」+「客服查单」**，而旧实现把 370px 宽度给了「支付流水号 / 支付渠道 / 件数」这种核对用不上的字段，却没告诉管理员**哪一单等得最久**（最早一单已经等了 18 天 22 小时）。

## 二、现状诊断

| # | 问题 | 说明 |
|---|---|---|
| 1 | **状态只有下拉，看不到分布** | 48 待发货 vs 101 已取消，得点开下拉才知道；「今天有几单要发」无从判断 |
| 2 | **默认排序写死 `id` 倒序，且没有排序控件** | 48 单待发货里最早等了 18 天，列表按新单在前排，**最该处理的沉在最底下** |

| 5 | **两列 300px 给支付核对** | 「支付流水号」200px +「支付渠道」100px，运营日常用不上；真正要核对时是去查支付流水，不是在列表里扫 |
| 6 | **表格最小宽度 ≈1400px** | 1440 屏下减去侧栏 210 + 内边距 48，可用 ≈1182px → **必然横向滚动**，操作列靠 `fixed` 才看得见 |
| 7 | **商品列 + 件数列共 250px 只放了一个商品名** | 明细里明明有 `productImage`，列表不展示；`等 N 种` 分支永远走不到 |
| 8 | **买家列只有收货人 + 手机** | `userId` 下发了但没展示（后台该知道「谁下的单」，收货人可能是家人）；地址要开弹窗 |
| 9 | **详情弹窗是 el-descriptions 平铺** | 下单/支付/发货/完成四个时间混在两列描述里，看不出「卡在哪一步」；商品明细无图；备注（21 单有）只是一行灰字，容易漏看 |
| 10 | **发货是一键、无物流单号、无批量** | 点完就变待收货，不可撤销；48 单要开 48 次确认框。DB 里没有运单号字段，所以这是「能力缺失」而非「UI 没做」 |

**一句话总结**：页面把一半宽度给了「支付流水号」这种核对用不上的字段，却没告诉管理员**哪一单等得最久**；而它真正的日常是「清 48 单待发货 + 查某一单」。

## 三、三个方案

### 方案 A · 状态工作台（`#a`，推荐）

保留表格（管理员的肌肉记忆），把力气花在「待办」和「查单」上：

**① 页头三张 KPI 卡**
- 待发货 **48** · 最早一单已等 **18 天 22 小时**
- 待收货 4 · 已发出等确认
- 累计成交 ¥116,133.80 · 62 单已付款 · 客单 ¥1,873

> ★ **刻意不写「今日 N 单」**：数据停在 10-21，今天打开会全是 0。概览卡只挂「不会因为数据陈旧而变 0」的指标。

**② 状态 chips 替代下拉**：`全部 172 / 待付款 2 / 待发货 48 / 待收货 4 / 已完成 10 / 已取消 101 / 已超时 7`，计数直接来自新接口。

**③ 工具栏**：搜索（订单号 / 收货人 / 手机 / **商品名**）、时间范围、排序（下单时间 ↓ / **付款时间 ↑「等最久优先」**）、每页 20。

> ★ 交互细节：切到「待发货」chip 时，排序**自动切**成「付款时间 ↑」，这样一进来第一条就是等最久的那单。

**④ 表格 8 列 → 6 列**

| 列 | 内容 | 变化 |
|---|---|---|
| 勾选 | 批量 | 新增 |
| 订单 | 缩略图 + 订单号 + 下单时间 + `秒杀` 标 | 合并 |
| 商品 | 商品名 + 规格 × 件数 | 合并（砍掉独立的「件数」列） |
| 买家 / 收货 | 收货人 · 手机 / 地址摘要（hover 全文） | 补地址 |
| 实付 | `¥189.00` | — |
| 状态 | tag + **等待时长**（待发货红字「已等 16 天 23 小时」） | 新增时长 |
| 操作 | 详情 / 发货 | — |

砍掉：支付流水号、支付渠道（下沉到抽屉）、件数（并入商品列）。

**⑤ 批量条**：勾选后出现「已选 3 单 · 合计 ¥248.90 ｜ 批量发货」——合计金额让管理员在点发货前能对一眼量级。

**⑥ 详情抽屉 760px（替代 700px 弹窗）**
- **状态时间线**：下单 → 支付 → 发货 → 完成，四节点；当前卡点用红圈标出并写「已等 16 天 23 小时」；未到达的节点灰掉
- 买家备注：黄条置顶（有备注才出现）
- 收货信息：收货人 / 手机 / 地址，每行带「复制」（客服刚需）
- 商品明细：缩略图 + 规格 + 单价 × 数量 + 小计
- 支付信息：渠道 / 状态 / 时间 / 流水号，**状态语义明确区分**「支付成功」与「未支付成功（已关闭）」——后者隐藏流水号
- 底部固定「关闭 / 发货」

**成本**：前端 1 文件重写；后端 **+1 概览接口、列表 VO +3 字段、查询 +排序/时间范围**（详见 5.1）。

### 方案 B · 左列表 + 右详情（`#b`）

客服查单台：左侧 380px 紧凑列表（缩略图 + 单号后 8 位 + 买家 + 金额 + 相对时间），`↑` `↓` 键切换；右侧详情常驻，底部「发货并看下一条」。

**优点**：**后端 0 改动**（现有 3 个接口全够）；查一单发一单不用开关弹窗；键盘流很快。
**缺点**：一屏只看 8 条；108 单已取消/超时混在左列表里非常吵；批量发货、时间筛选没地方放；右侧面板会越加越挤。

### 方案 C · 发货看板（`#c`）

三列看板：待发货 / 待收货 / 已完成，卡片上直接点发货，卡面标等待时长；顶部「今天要发 48 单，最早一单等了 18 天 22 小时」。

**优点**：积压一眼看清，适合仓库/平板按单打包；「等最久」在卡上最显眼。
**缺点**：**108 单已取消/超时没有位置**（要么加第四列变四列滚动，要么这些单彻底查不到）；搜索、时间筛选、批量、分页全都装不下。

## 四、对比与推荐

| 维度 | A · 状态工作台 | B · 左列表右详情 | C · 发货看板 |
|---|---|---|---|
| 清 48 单积压 | **chips 筛选 + 批量发货** | 一条条点，48 次确认 | 卡上直接发，但一列只放 5 张 |
| 客服查单 | **搜索 + 抽屉，够用** | **键盘上下切，最强** | 只能按状态找 |
| 看状态分布 | **6 个计数直接铺开** | 挤在 380px 的 tab 里 | 只看得到 3 个在途状态 |
| 「等最久」优先 | **排序 + 红字时长** | 可排但没地方放控件 | **卡面最显眼** |
| 一屏信息量 | **20 条** | 8 条 + 详情面板 | 15 张卡（纵向很长） |
| 已取消 / 超时单 | **一个 chip 筛出来** | 混在列表里很吵 | **没有位置** |
| 后端改动 | +1 接口 / +3 字段 / +查询参数 | **0 改动** | +1 接口 |
| 长期可扩展 | **导出、关闭订单、退款都有位置** | 右侧面板越加越挤 | 状态一多就摊不开 |

**推荐 A。** 理由：
1. 当前最痛的是「48 单积压不知道从哪单开始」，A 用「付款时间 ↑ + 等待时长红字 + chips 计数」正面解决，B/C 都是绕开；
2. 101 单已取消必须能一键筛出来（对账、客服回访都要），只有 A 给得了位置；
3. B 的键盘流确实好用，但它是「查单」这一个场景的最优解，而 A 顺带也能查单；真要提升查单效率，后面单独给 A 的抽屉加 `↑↓` 切换即可（成本 ≈ 20 行）。

## 五、落地拆解（已实施）

### 5.1 后端改动（全部是加法）

**① `GET /api/admin/orders/overview`** → `OrderOverviewVO`

```json
{
  "total": 172,
  "pendingPayment": 2, "pendingShipment": 48, "pendingReceipt": 4,
  "completed": 10, "cancelled": 101, "timeoutClosed": 7,
  "oldestPendingShipmentTime": "2026-10-06T19:23:13",
  "paidOrderCount": 62, "paidAmount": 116133.80
}
```

实现：**一条 SQL**（照 `countByStatus()` 的 `selectMaps + QueryWrapper` 写法）：

```sql
SELECT status, COUNT(*) cnt, SUM(pay_amount) amt, MIN(pay_time) min_pay
FROM t_order GROUP BY status
```

→ 6 行，Java 里累加：`paidAmount` = status ∈ {1,2,3} 的 `amt` 之和，`oldestPendingShipmentTime` = status=1 那行的 `min_pay`。
★ 不要写 6 次 `count(*)`；`deleted=0` 由 `@TableLogic` 自动拼，别手写。
★ 聚合列的类型要防：`SUM` 是 `BigDecimal`，`MIN(pay_time)` 在部分驱动下会退化成 `Timestamp` → 补了 `decimalValue` / `dateTimeValue` 两个取值助手。

**② `AdminOrderListItemVO` 补 4 个字段**：`payTime`、`shipTime`、`cancelTime`、`seckill`。
★★ **不能复用 VO 里已有的 `channel`**：那个字段是「支付渠道」（从 `payment_record` 取，0模拟/1微信/2支付宝），而 `t_order.channel` 是「订单来源」（0普通/1秒杀）—— **同名不同义**，复用必踩坑。`seckill` 单独一个字段。
★ **落地时额外补了 `receiverAddr`**（原方案没列）：列表要给「地址摘要」，不补这一列只能显示 `-`。

**③ `AdminOrderQuery` 补 4 个参数**：`sortBy`（`createdAt` / `payTime`）、`order`、`beginDate` / `endDate`（`LocalDate` + `@DateTimeFormat(ISO.DATE)`）。
★ 排序**白名单映射**（`applyAdminSort`），未知字段回落 `createdAt`，末尾补 `id` 兜底防翻页重复。
★ 日期范围是**闭区间**：`>= beginDate 00:00` 且 `< endDate+1 00:00`。

**④ `PUT /api/admin/orders/batch/ship`** body 直接是订单号数组，返回 `BatchShipResultVO`：

```json
{ "success": ["NO…"], "failed": [{ "orderNo": "NO…", "reason": "订单当前为「已取消」，无法发货" }] }
```

★★ **语义与商品批量接口刻意相反**：商品批量是「整批拒绝」，发货必须**允许部分成功** —— 货已经打包了，不能因为第 47 单状态被别人改了就把前 46 单退回去。
★ 先用一次 `IN` 查回目标订单，才能把失败原因区分为「订单不存在」/「状态不允许」/「并发下状态已变」；逐单仍用「带状态条件的 UPDATE」收口。上限 100，重复订单号去重。

**⑤ `PUT /api/admin/orders/{orderNo}/close`**
仅 `待付款 → 已取消`，复用 `restoreStock(order)`。
★ `cancel(userId, orderNo)` 走 `getOwned()`（带归属校验），后台拆出不校验归属的 `doCancel(order)`，用户取消与后台关闭共用同一份库存回补逻辑（含秒杀按渠道分流）。

**⑥ `AdminOrderDetailVO extends OrderDetailVO`**：补 `payStatus` / `payStatusLabel` / `payChannel` / `payNo` / `userId`。
★ 没往共用的 `OrderDetailVO` 上加字段 —— 前台订单详情是用户看自己的单，不该多返回一组支付内部字段。`buildDetail()` 改成泛型 `buildDetail(order, T vo)`，两处共用 13 个 set 而不复制。

## 六、口径与坑

1. ★★**「已取消」订单的支付信息必须改口径**（已修）。旧 `loadLatestPayments()` 只取 id 最大的流水、不看 `status`，30 单已取消会显示失败/待支付流水，读起来像已付款。现在：**优先取支付成功那条，没有才取最新一条**；判断有没有收到钱只看 `payStatus`，不看 `payNo` 是否存在。
2. ★**「等最久」用 `payTime` 而不是 `createdAt`**。待发货订单的 `pay_time` 都有值（实测 48/48）。
3. ★**等待时长文案分档**：< 1 天灰字、1~3 天橙字、≥ 3 天红字。实测 48 单待发货**全部**超过 3 天，打开「待发货」是一片红 —— 这不是渲染 bug，是积压真实状态。
4. ★**概览卡别绑「今日」**：数据停 4 天，任何今日/近 7 天都是 0。
5. ★**搜索商品名不要用 `inSql` 拼字符串**：`apply("order_no IN (SELECT order_no FROM order_item WHERE product_name LIKE {0})", "%" + kw + "%")`，`{0}` 走参数绑定。项目里没有 Mapper XML，别顺手引入第一份。
6. ★**缩略图要占位符**：21 条明细 `product_image` 为空，空 `src` 会显示成裂图；图片加载失败时只隐藏图片、保留灰块。
7. ★**分页加 `sizes` 要同时重置页码**，否则第 5 页切成 50 条/页会落在空页。
8. ★**批量发货不要动 `sold_count`**：销量在 `markPaid` 时已累加，发货只是状态流转。
9. ★★**不要给表格加 `reserve-selection`**（落地时改掉了）：勾选会跨筛选/翻页保留，导致「批量发货」可能发出**当前看不见的订单**。发货不可撤销，选择必须随筛选清空。
10. ★★**关闭订单的库存回补对「已被软删的 SKU」静默失效**（既有问题，非本次引入）：`InventoryService.restore` 走 MP 的 `update`，会自动追加 `deleted=0`，而 SKU 在商品编辑时是**软删重建**的（`ProductService.update` 会 `skuMapper.delete` 后重插）。演示库 489 个 SKU 里 106 个已软删，**2 个待付款订单恰好都指向软删的 sku 34**，所以关这两单不会回补库存（订单状态照常变已取消）。实测用「立即购买」新建的待付款单关闭后库存正常 78 → 80。
