## 1. 订单列表 N+1

### 现状

`OrderService.page()` 每查一页，就对每条订单单独查一次明细：

```java
for (Order order : page.getRecords()) {
    records.add(toListItemVO(order));        // 内部 loadItems(order.getOrderNo())
}
```

- 前台列表 10 条 = **1 次分页 + 10 次明细 = 11 条 SQL**
- 后台列表 10 条 = 1 次分页 + 1 次支付流水 + 10 次明细 = **12 条**

### 改法

一次 `IN` 查询取回本页所有明细，按订单号分组：

```java
List<String> orderNos = page.getRecords().stream().map(Order::getOrderNo).toList();
Map<String, List<OrderItemVO>> itemsByOrder = loadItemsGrouped(orderNos);
```

`toListItemVO(order)` / `toAdminListItemVO(order, payment)` 增加 `List<OrderItemVO> items` 参数，
不再自己去查。明细顺序仍由 `orderByAsc(id)` 保证。

### 验收

| 场景 | 改前 | 改后（实测） |
|---|---|---|
| 前台订单列表 10 条 | 12 条（1 count + 1 page + 10 明细） | **3 条**（count + page + 1 次明细） |
| 后台订单列表 10 条 | 13 条（再多 1 次支付流水） | **4 条** |
| 订单详情（单条） | 1 次明细 | 不变（本来就是 1 次） |

> 设计时漏算了 MyBatis-Plus 分页的 COUNT 查询，实测比预估多 1 条。

## 2. 购物车 N+1

### 现状

`CartService.buildItemVo(item)` 对每个购物车项各查一次商品、一次 SKU：

```java
Product product = productMapper.selectById(item.getProductId());   // 每项 1 次
ProductSku sku  = productSkuMapper.selectById(item.getSkuId());    // 有规格时再 1 次
```

10 个购物车项 = **1 次列表 + 20 次单查 = 21 条 SQL**。

### 改法

`list()` 先收集 `productIds` / `skuIds`，用 `selectBatchIds` 批量取回，再交给 `buildItemVo(item, productMap, skuMap)`：

- 商品被物理删除时 map 里没有 → 保持现有「商品已下架」失效分支
- SKU 缺失 → 保持「商品规格已下架」分支
- 两个 map 为空时不发查询（避免 `IN ()` 语法错误）

### 验收

| 场景 | 改前 | 改后（实测 4 项） |
|---|---|---|
| 购物车 N 项（都有规格） | 1 + 2N 条 SQL | **3 条**（列表 + 商品批量 + SKU 批量），与 N 无关 |
| 购物车 N 项（无规格） | 1 + N 条 | **2 条**（无 SKU 查询） |
| 失效商品提示 | 文案不变 | 不变（单测覆盖） |

## 3. 搜索日志异步写

### 现状

`SearchLogService.record()` 在**搜索请求线程里同步 insert**：

```java
searchLogMapper.insert(entity);   // 每次搜索 1 次写
```

两个问题：① 搜索接口的响应时间被写库拖住；② 热点词被搜爆时，`search_log` 成为写热点，
且每条一次 DB 往返。

### 改法：内存缓冲 + 定时批量落库

```
record()  →  ConcurrentLinkedQueue.offer(entity)   // 内存入队，立即返回
                    │
@Scheduled(fixedDelay = 1s) 或队列满 200 条
                    ↓
        drainTo(batch)  →  一条 INSERT ... VALUES (...),(...)
```

要点：

- **队列有界**（默认 10000）：满了直接丢弃并累加丢弃计数 —— 搜索日志是统计素材，不能因为
  写不进去就把内存撑爆，更不能阻塞搜索。
- **停机刷盘**：`@PreDestroy` 里 flush 一次，避免优雅停机丢数据。
- **批量插入**用自定义 `@Insert` + `<foreach>`：MyBatis-Plus 的 `BaseMapper` 没有批量插入，
  为这个引 `insertBatchSomeColumn` 扩展（要自定义 SqlInjector）不划算。
- **失败重试**：一次批量写失败 → 记 WARN，不重投（丢一秒日志可接受），避免故障时无限重试。

### 验收

- 100 次搜索 → `search_log` 增加 100 行，但 **insert 语句只有 1~2 条**
- 搜索接口 P95 不再包含 DB 写耗时（对比改前）
- 后台「搜索分析」看板数字在 1 秒内追平

### 代价（需确认）

进程崩溃 / `kill -9` 时，最多丢失 **1 秒**的搜索日志。这是拿「统计完整性」换「主链路性能」，
对搜索日志是合理的 —— 但如果这个项目要拿 `search_log` 做对账，就不能这么做。

## 4. 随机分页：建议降级为「配置化 + 边界标注」

### 现状

`ProductService.randomPage()` 每次首页请求：

1. 查最多 2000 个 id（只查 id 列，走覆盖索引）
2. 在 JVM 里用 seed 做确定性洗牌
3. `selectBatchIds` 取当前页

### 先量化，再决定要不要改

当前库 **647 个商品**，实测这一整套的开销是：

- 拉 id：647 行 × 8 字节 ≈ **5KB**，走 `idx_status` 覆盖索引
- 洗牌：`Collections.shuffle` 对 647 个元素，**< 1ms**
- 第二次查询：`selectBatchIds` 取 20 条，与普通分页相同

**结论：在当前数据量下，这不是瓶颈。** 为一个 <1ms、5KB 的操作加一层 id 池缓存（还要处理
商品增删改时的失效），属于为优化而优化，违反「杜绝冗余代码」。

### 所以本切片只做两件事

1. 把 `RANDOM_POOL_LIMIT`（当前硬编码 2000）提成配置 `tickcart.product.random-pool-limit`
2. 在代码注释与设计文档里写清**触发改造的量化条件**：

| 条件 | 改造方案 |
|---|---|
| 商品数 > 5000 | 加 `random_weight` 列 + 索引，改「按权重排序 + 游标翻页」 |
| 或该接口 P95 > 50ms | 同上 |
| 或池子命中上限（2000）成为瓶颈 | 先加 id 池缓存（复用 `CacheService`，TTL 5min） |

> 这条我会在实现时明确标注「当前是演示量级方案」，避免后来人误以为已经优化过。

**如果你认为应该现在就加 id 池缓存，请直接说** —— 我按上面第 3 档方案实现。

## 5. MQ publisher confirm

### 现状

`RabbitTemplate` 没开 confirm / return。`OrderMessageProducer` 只 catch **同步**异常
（连接失败、序列化失败）；消息发出后 Broker 是否真的落盘、路由键是否匹配到队列，**完全不知道**。

后果：投递成功但路由失败（队列不存在）→ 订单永不自动关单，而且没有任何告警。

### 改法

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # 异步确认（带 correlationData）
    publisher-returns: true              # 路由失败时回传
    template:
      mandatory: true                    # 必须配，否则 return 不会触发
```

`common/mq/RabbitConfirmConfig` 里给 `RabbitTemplate` 挂两个回调：

| 回调 | 触发时机 | 处理 |
|---|---|---|
| `ConfirmCallback` | Broker 收到消息（ack=true）/ 拒收（ack=false） | ack=false 记 ERROR + 计数 |
| `ReturnsCallback` | 消息到了交换机但**没有匹配队列** | 记 ERROR + 计数（带 replyText） |

计数用 `AtomicLong`，通过日志输出（如每 100 次打一条汇总），不引监控系统（阶段 4 再做）。

### 不做的部分

**本地消息表**（业务库 + 消息表同事务、定时补偿）才是真正不丢的方案，但它要加表、加扫描任务、
加状态机 —— 属于「可靠消息」的完整工程，超出 3A 范围。本轮只做到「投递失败可见」，
并在 README 的面试叙事里写清「这里还差一步本地消息表」。

### 验收

- 停掉 RabbitMQ 后下单：日志出现 confirm 失败（或同步异常），下单仍成功（不阻塞主链路）
- 恢复后新订单正常投递、正常超时关单
- 故意发一条路由键不存在的消息 → `ReturnsCallback` 打 ERROR

## 6. 池子基线

### 现状

| 配置 | 当前值 | 问题 |
|---|---|---|
| `server.tomcat.threads.max` | 未配置（默认 200） | 200 个请求线程抢 20 个 DB 连接，`connection-timeout: 30s` 下会大面积等连接 |
| `spring.datasource.hikari.maximum-pool-size` | 20 | 单机够用，但与 200 线程不匹配 |
| `spring.rabbitmq.listener.simple.prefetch` | 10（全局） | 超时关单消费者与支付回调消费者共用一个值，但两者耗时不同 |

### 改法

```yaml
server:
  tomcat:
    threads:
      max: 100            # 与 Hikari 20 保持 5:1，减少「抢不到连接」的等待
      min-spare: 20
spring:
  datasource:
    hikari:
      maximum-pool-size: 20      # 单机 + MySQL max_connections 151，留足余量
      minimum-idle: 5
      connection-timeout: 3000   # 从 30s 收到 3s：等不到连接要快速失败，别让请求挂 30 秒
  rabbitmq:
    listener:
      simple:
        prefetch: 10
```

并在 yml 里逐项写注释说明**为什么是这个数**（AGENTS.md 要求配置化管理 + 关键逻辑有注释）。

**消费者级 prefetch**：`@RabbitListener` 上可以单独指定 `concurrency` / `prefetch`，
支付回调消费者（要调 `markPaid` 改订单状态）比超时关单更重，可单独调小到 5。
这项作为可选优化，若实现时发现配置分散反而难维护，就统一保持 10。

### 验收

- 50 并发下单压测（关限流）全程无 `HikariPool ... Connection is not available` 超时
- 日志无连接池等待告警
- 基线数值写进 yml 注释，后来人知道为什么

## 6.5 实测结果（2026-10-18 22:00，后端 8080）

```
订单列表 10 条（demo）           → 3 条 SQL（count + page + 1 次批量明细）
购物车 4 项                     → 3 条 SQL（列表 + 商品批量 + SKU 批量）
30 个并发搜索                   → 2 条 INSERT，30 行落库（批量合并生效）
30 个串行搜索（约 12 秒）        → 13 条 INSERT —— 每秒刷一次盘，属预期
docker stop tickcart-rabbitmq 后下单
  → 下单仍成功（200，status=0），日志 ERROR「投递订单超时消息失败（不影响下单）」
```

> 搜索日志的批量效果取决于请求密度：并发 30 次 → 2 条 INSERT；串行 30 次跨越十几秒 →
> 每秒刷一次，得到 13 条。**这是设计意图**（宁可多刷几次也不让日志滞留内存），
> 不是「批量没生效」。

验证数据已清理：订单/明细/流水/幂等记录删除、SKU 39 库存回补至 95、
demo 购物车清空、探针关键词（zzzprobe/zzzprobe2）的 search_log 删除、热搜缓存已失效重建。

## 8. 决策记录（2026-10-18 已确认并实施）

| 项 | 决策 | 理由 |
|---|---|---|
| 搜索日志缓冲 | 内存有界队列 + 1s 批量落库，接受崩溃丢 ≤1s | 日志是统计素材，不能拖慢搜索主链路 |
| 随机分页 | **降级**为配置化 + 边界标注，暂不加 id 池缓存 | 647 商品下开销 <1ms / 5KB，加缓存属为优化而优化 |
| MQ | 只做到「失败可见」（confirm + returns + ERROR 计数） | 本地消息表是完整可靠消息工程，超出 3A |
| 池子基线 | Tomcat 100 / Hikari 20 / connection-timeout 3s | 线程与连接 5:1，等不到连接要快速失败 |
| 批量插入 | 自定义 `@Insert` + `foreach` | 不引 MP 的 SqlInjector 扩展 |
