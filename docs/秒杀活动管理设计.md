## 1. 范围

**本切片做**：活动表、活动状态推导、后台 CRUD、前台活动列表。
**本切片不做**：Redis 预热、Lua 扣减、抢购接口、异步建单、专场页与轮询（B2~B4）。

此时还没有 Redis，抢购按钮不存在 —— 这是一个可演示的完整切片。

## 2. 表设计

```sql
-- -----------------------------------------------------------------------------
-- 秒杀活动表
--
-- 设计要点：
--   1. 不存 status —— 状态由 (start_time, end_time, enabled) + 当前时间推导，
--      避免「到点没自动开始/结束」这类必须靠定时任务补救的经典问题
--   2. 库存独立于 product_sku.stock —— 秒杀与普通售卖各算一套账，互不影响
--   3. sold_count 由建单消费者原子累加，是「Redis 剩余库存」的对账依据
-- -----------------------------------------------------------------------------
CREATE TABLE `seckill_activity` (
    `id`              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '活动ID',
    `title`           VARCHAR(64)     NOT NULL                COMMENT '活动标题',
    `product_id`      BIGINT UNSIGNED NOT NULL                COMMENT '商品ID',
    `sku_id`          BIGINT UNSIGNED NOT NULL DEFAULT 0      COMMENT 'SKU ID（无规格为0）',
    `seckill_price`   DECIMAL(10, 2)  NOT NULL                COMMENT '秒杀价',
    `seckill_stock`   INT             NOT NULL                COMMENT '秒杀总库存（独立于商品库存）',
    `sold_count`      INT             NOT NULL DEFAULT 0      COMMENT '已成交数量（建单成功后原子累加）',
    `limit_per_user`  INT             NOT NULL DEFAULT 1      COMMENT '每人限购数量',
    `start_time`      DATETIME        NOT NULL                COMMENT '开始时间',
    `end_time`        DATETIME        NOT NULL                COMMENT '结束时间',
    `enabled`         TINYINT         NOT NULL DEFAULT 1      COMMENT '是否上线 0下线 1上线',
    `created_at`      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at`      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    KEY `idx_time` (`start_time`, `end_time`),
    KEY `idx_product` (`product_id`),
    KEY `idx_enabled_start` (`enabled`, `start_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT '秒杀活动表';
```

**为什么有 `sold_count`**：后台列表要显示「已抢 x 件 / 进度条」，若每次都去 `t_order` 里 `COUNT(*) WHERE channel=1 AND activity_id=?`，
列表页立刻变成 N+1。存一个原子累加值更直接，且它正是「Redis 剩余库存」出问题时的对账依据。

**为什么有 `idx_enabled_start`**：前台只查「已上线 且 结束时间 > now」的活动，这个组合索引直接命中。

## 3. 状态：不落库，按时间推导

```
DISABLED   enabled = 0            （后台手动下线）
PENDING    enabled = 1 且 now <  start_time
ONGOING    enabled = 1 且 start_time <= now < end_time
ENDED      enabled = 1 且 now >= end_time
```

判定顺序固定：**先看 enabled，再看时间**。

**为什么不存 status 字段**：

- 存了就必须有定时任务在 `start_time` / `end_time` 到点改状态；任务漏跑、服务重启、
  时钟偏差都会让「活动该开始了却还是未开始」——这是秒杀项目最经典的线上事故。
- 时间推导永远准，不需要任何补偿机制。
- 后台「手动下线」是唯一需要人工干预的状态，用 `enabled` 表达就够了。

> 代价：无法记录「曾经被下线过」这类审计信息。本项目的量级不需要。

## 4. 秒杀库存与商品库存的关系（关键设计）

| | 普通售卖 | 秒杀 |
|---|---|---|
| 库存来源 | `product_sku.stock` | `seckill_activity.seckill_stock` |
| 扣减位置 | `InventoryService.deduct`（条件 UPDATE） | Redis Lua（B2） |
| 回补 | `InventoryService.restore` | Redis `INCR` + `sold_count - 1` |

**秒杀订单不扣 `product_sku.stock`，取消也不回补它。** 理由：

- 若两者都扣，同一件商品会被扣两次，秒杀一开普通库存就凭空消失。
- 秒杀库存是活动维度的配额，本来就该独立核算。
- 活动结束后剩余秒杀库存不会回流到商品库存 —— 这是业务选择（避免活动结束后台库存突变）。
  若以后要回流，加一个「活动结束对账任务」即可。

这条必须在 `saveOrder` 的调用方明确：**秒杀建单走一个不扣 SKU 库存的入口**（见 §5）。

## 5. 秒杀建单入口契约（B3 用，B1 先定死）

现有两个入口都不适用：`create` 读购物车、`createBuyNow` 让前端传商品和数量并扣 SKU 库存。

新增（B3 实现，B1 只写进设计）：

```java
/**
 * 秒杀建单：由 MQ 消费者调用，不读购物车、不扣 SKU 库存。
 *
 * @param activityId 活动 ID（订单需能反查所属活动）
 * @param price      活动价快照（不是商品价，也不由前端决定）
 */
public OrderVO createSeckillOrder(Long userId, Long activityId, Long productId, Long skuId,
                                  int quantity, BigDecimal price, Long addressId);
```

行为约定：

| 项 | 值 |
|---|---|
| `channel` | `1`（秒杀） |
| 订单号前缀 | `SK`（普通为 `NO`，表结构早已预留） |
| 库存扣减 | **不扣** `product_sku.stock`；秒杀库存在 Lua 里已扣 |
| 超时关单 | 照常投递（复用 `OrderMessageProducer`） |
| 取消/超时回补 | 回补 **Redis 秒杀库存** + `sold_count - 1`，不动 SKU 库存 |
| 幂等 | 复用 `idempotent_record`，`scene = seckill.buy` |

⚠️ 订单表目前**没有 `activity_id` 字段**。B3 需要它来反查「这笔订单属于哪场活动」，
用于取消时回补正确活动的库存。**是否加这一列，需要你确认**（加表结构变更）。

替代方案：把 `activityId` 编进订单号或备注 —— 不推荐，反查要靠解析字符串，且无法建索引。

## 6. 接口清单

### 后台（`/api/admin/seckill/**`，ADMIN 角色）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/activities` | 分页列表，可按 enabled / 状态筛选 |
| GET | `/activities/{id}` | 详情 |
| POST | `/activities` | 新建（校验商品存在、秒杀价 > 0、库存 > 0、限购 ≥ 1、start < end） |
| PUT | `/activities/{id}` | 编辑（**进行中的活动禁止改库存与价格**，只能改标题/时间外的字段） |
| PUT | `/activities/{id}/enabled` | 上线 / 下线 |
| DELETE | `/activities/{id}` | 删除（**有成交记录时拒绝**，保留对账依据） |

**「进行中禁止改价改库存」**是必须的：改价会让已下单用户的价格与展示不符，
改库存会让 Redis 与 DB 的账对不上（B2 之后 Redis 才是权威）。

### 前台（`/api/seckill/**`，匿名可访问）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/activities` | 已上线且未结束的活动（进行中 + 即将开始），按开始时间升序 |
| GET | `/activities/{id}` | 活动详情（B1 先返回活动 + 商品快照，B2 加实时剩余库存） |

> 前台接口按 A3 的规则**单独配一条限流**，不复用 `product-read` 的 60/秒（抢购时会另算）。

## 7. 预热时机（B2 实现，B1 只留调用点）

三处触发，缺一不可：

1. **后台「上线」时** —— 立即预热，避免用户等到定时任务
2. **应用启动时** —— 扫「已上线且未结束」的活动补预热（Redis 重启/数据丢失的兜底）
3. **定时扫描（每 30s）** —— 预热「30 秒内即将开始」的活动，防止上线时预热失败后无人重试

预热动作（B2 定义）：写 `seckill:stock:{activityId}`、活动缓存、TTL = `end_time + 1h`。

## 10. 决策记录（2026-10-18 已确认并实施）

| 项 | 决策 | 理由 |
|---|---|---|
| `seckill_activity` 表 | 按 §2 DDL 建立（含 `sold_count` 与 `idx_enabled_start`） | `sold_count` 既避免列表 N+1，也是 Redis 对账依据 |
| `status` 存储 | **不落库，按时间推导** | 定时任务漏跑会让「该开始的活动停在未开始」 |
| `t_order.activity_id` | **加列**（默认 0，非秒杀订单不受影响） | B3 取消订单要回补正确活动的库存 |
| `product.is_seckill` | 保留字段但不再作为秒杀依据 | 由活动表取代；删列属表结构变更，暂不动 |
| 秒杀库存 | 独立核算，**不扣 `product_sku.stock`** | 两套账各扣一次会让普通库存凭空消失 |
| 进行中禁改价改库存 | **是** | 已下单用户的价格与展示不一致；Redis 与 DB 对不上 |
| 有成交禁删 | **是** | 删了就没法对账 |

### 追加的一条校验（实现时补上）

**秒杀价必须低于原价**：不校验很容易建出「秒杀价比原价还贵」的活动 ——
用户看到「秒杀」两个字反而多付钱，是最伤的体验事故。已按规格价回退原价后比较。
