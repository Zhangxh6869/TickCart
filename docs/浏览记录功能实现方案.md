# TickCart · 浏览记录功能实现方案

> 状态：**待评审**（本文只做设计，不含代码改动）
> 需求来源：「我的」页「我的收藏」下方新增「浏览记录」入口
> 关联文档：《TickCart项目阶段划分.md》、《TickCart详细设计-架构与模块.md》、《docs/数据库设计说明.md》
> 关联代码：`FavoriteController/Service/Entity`（后端模板）、`FavoriteListView.vue`（前端模板）

---

## 1. 背景与目标

### 1.1 现状

- 「我的」页 `.member__cells` 目前 **3 项**：我的收藏 / 收货地址 / 个人信息。
- 收藏已是一套完整闭环：`user_favorite` 表（唯一键 `uk_user_product`、**无 deleted 列**、物理删除）+ `FavoriteService` + `FavoriteListView.vue`（两列 `ProductCard` 网格 + 卡片右上角取消按钮 + `van-list` 分页）。
- **浏览行为目前完全没有被记录**，详情页 `ProductDetailView.load()` 只拉详情与收藏状态。

### 1.2 目标

1. 「我的」页在「我的收藏」**下面**新增一行「浏览记录」，点进去是浏览过的商品列表。
2. 浏览过的商品**自动记录**（进入商品详情页即记），同一商品只占一条、按最近浏览时间倒序。
3. 记录页支持：分页加载、删除单条、清空全部、空态提示。
4. 数据按用户隔离，只有本人能看/删自己的记录。

### 1.3 非目标（本阶段不做）

- 未登录状态的浏览记录（游客本地暂存 + 登录后合并上传）—— 见 §9 待确认项 A。
- 浏览时间分组（今天 / 昨天 / 更早）、「浏览过 N 次」计数展示。
- 浏览行为的分析报表（后台看板）、个性化推荐。
- 定时清理任务（理由见 §4.3，本方案不需要）。

## 2. 关键设计决策

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| D1 | 存储位置 | **后端建表**，不用 localStorage | 浏览记录要跨设备、要能被「我的」页计数；localStorage 在清缓存后丢失，且与收藏能力不对等 |
| D2 | 表结构 | 唯一键 `uk_user_product` **去重**，重复浏览只更新时间 | 浏览记录的产品语义是「最近浏览过的商品」，不是流水日志；去重后单用户记录数**有界**（见 D4） |
| D3 | 删除语义 | **物理删除**（与 `user_favorite` 一致） | 删掉后再次浏览该商品要能重新出现在列表里，逻辑删除会让唯一键撞键（`purgeDeleted` 那套坑） |
| D4 | 记录条数上限 | **不做上限、不做清理任务** | 唯一键去重 ⇒ 单用户最多 = 在售商品总数（当前 162）。表规模 = 用户数 × 人均浏览商品数，可控 |
| D5 | 埋点失败处理 | 前端**静默上报**（silent），失败不弹 toast、不阻塞页面 | `utils/request.ts` 的响应拦截器会对任何失败 `showToast`，埋点失败弹「网络异常」是纯噪音 |
| D6 | 未登录埋点 | **不发请求**（未登录直接 return） | 否则 401 会触发拦截器 `clearTokens()` + 「登录已过期」toast，属于误伤 |
| D7 | 接口鉴权 | 走默认 `anyRequest().authenticated()`，**不加进 permitAll** | 浏览记录是私有数据，必须登录；`SecurityConfig` 无需改动（★与「新增 `/api/**` 必须 permitAll」那条规则不冲突，那条针对的是匿名可访问的接口） |
| D8 | 「我的」页条数 | **显示**（`N 件`），与收藏 / 地址保持一致 | 实现成本与收藏完全一致：`GET /api/view-history?page=1&size=1` 取 `total` |
| D9 | 页面视觉 | 与 `FavoriteListView.vue` **同构** | 两页交互几乎一样（列表 + 单条移除 + 空态），复用 `ProductCard` 两列网格即可，避免第二套视觉语言 |

## 3. 数据库设计

### 3.1 新增迁移 `V16__user_view_history.sql`

```sql
-- 用户浏览记录：同一用户同一商品只保留一条，重复浏览刷新 view_time。
-- 无 deleted 列：删除记录走物理删除（删掉后再浏览会重新出现）。
CREATE TABLE `user_view_history` (
    `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    `user_id`    BIGINT UNSIGNED NOT NULL                COMMENT '用户ID',
    `product_id` BIGINT UNSIGNED NOT NULL                COMMENT '商品ID',
    `view_time`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '最近一次浏览时间',
    `created_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '首次浏览时间',
    `updated_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_product` (`user_id`, `product_id`),
    KEY `idx_user_time` (`user_id`, `view_time`),
    KEY `idx_product_id` (`product_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT '用户浏览记录表';
```

字段说明：

- `view_time` 是**排序字段**（最近浏览倒序），与 `updated_at` 分开：`updated_at` 会被任何 UPDATE 刷新，语义上不该拿来当业务时间。
- `idx_user_time` 覆盖「某用户按时间倒序分页」这个唯一的热查询。
- `idx_product_id` 与 `user_favorite` 对齐，留给未来的「商品被多少人看过」统计。

> ★ 建表语句需你确认后再执行（AGENTS.md §5：禁止私自增删改字段、修改表结构）。

### 3.2 迁移落地注意

- 新增迁移文件后必须跑 `scripts/verify-fresh-clone.py`（空库 + 8081）验证 Flyway 全量重放。
- 本文件是**新增**迁移，不涉及「改未提交的迁移要 `DELETE FROM flyway_schema_history`」那套重放流程。
- 不需要种子数据：浏览记录是用户行为产生，空表即正确初始态。

### 4.3 核心逻辑与要点

**① upsert 幂等**

```sql
INSERT INTO user_view_history (user_id, product_id, view_time, created_at, updated_at)
VALUES (#{userId}, #{productId}, NOW(), NOW(), NOW())
ON DUPLICATE KEY UPDATE view_time = NOW()
```

- 用 `@Insert` 写自定义 SQL（MyBatis-Plus 无 ON DUPLICATE KEY 封装）。
- 若不想写自定义 SQL，可退回 `FavoriteService` 的写法：先 `exists()` 判断 → `insert` → `catch (DuplicateKeyException)` 兜底。**但那条路在「已存在」分支要再发一条 UPDATE**，是两次往返；自定义 upsert 一条 SQL 解决，推荐前者。
- 幂等性：同一用户同一商品反复上报，结果都是「一条记录 + view_time 更新」，不会产生重复行。

**② 记录前校验商品存在**

`POST` 时先 `productMapper.selectById(productId)`，不存在抛 `BizException.notFound("商品不存在")`（照抄 `FavoriteService.add`）。避免脏 productId 进表。

**③ 列表分页口径（照抄 `FavoriteService.page`）**

1. `selectPage` 查 `user_view_history`（`eq(userId)` + `orderByDesc(viewTime, id)`）；
2. 取出本页 `productId` 列表 → `selectBatchIds` 批量查商品 → 按原顺序 `map` 回去；
3. 商品已删除的自动缺项（`filter(Objects::nonNull)`）；
4. `PageResult.total` 仍按**记录数**统计（不是实际返回的商品数），避免「边翻页边消失」导致页码错乱。

**④ 清空**

`DELETE FROM user_view_history WHERE user_id = ?`，一条 SQL 走 `LambdaQueryWrapper`，天然幂等。

**⑤ 并发**

唯一键 + upsert 天然并发安全；无需分布式锁、无需「带条件 UPDATE 看影响行数」那套（那是订单状态机的要求）。

**⑥ 事务**

`record()` / `remove()` / `clear()` 标 `@Transactional`；`page()` 只读不标。

### 4.4 单元测试 `ViewHistoryServiceTest`

必须覆盖：

1. 首次上报 → 插入一条；
2. **重复上报同一商品 → 仍然只有一条，`view_time` 被刷新**（用 `selectCount` 断言）；
3. 上报不存在的商品 → 抛 `BizException`；
4. 列表按 `view_time` 倒序（构造两条不同时间，断言顺序）；
5. 商品被删除后列表自动过滤；
6. 删除单条幂等（没记录也成功）；
7. 清空只删当前用户（另一个用户的记录不受影响）。

> ★★ 断言 MyBatis-Plus wrapper 参数前**必须先调一次 `getSqlSegment()`**（参数是惰性写进 `paramNameValuePairs` 的），并需要 `@BeforeAll` 里 `TableInfoHelper.initTableInfo(new MapperBuilderAssistant(new MybatisConfiguration(), ""), UserViewHistory.class)`。照抄 `FavoriteServiceTest` 的骨架。
> ★ 参数表里除目标值还会带 `status` 的 1，断言用 `contains` 不用 `equals`。
> ★ 跑 `mvn test` 前先停后端（JVM 占 `target/classes` 文件锁 → failed to discover tests）。

### 5.2 `api/view-history.ts`

```ts
/** 浏览记录列表（需登录，按最近浏览时间倒序）。 */
export function fetchViewHistory(params: { page?: number; size?: number }) {
  return request.get('/view-history', { params })
}
/** 上报一次浏览（幂等）。silent：失败不弹提示、不阻塞页面。 */
export function reportViewHistory(productId: number) {
  return request.post(`/view-history/${productId}`, null, { silent: true })
}
/** 删除单条（幂等）。 */
export function removeViewHistory(productId: number) {
  return request.delete(`/view-history/${productId}`)
}
/** 清空全部。 */
export function clearViewHistory() {
  return request.delete('/view-history')
}
```

### 5.3 `utils/request.ts` 的 silent 支持（跨切面，需单独说明）

现状：响应拦截器对**所有**失败统一 `showToast`。埋点必须能豁免，否则每次网络抖动都会在商品详情页弹「网络异常」。

改法（最小侵入）：

```ts
// 模块增强，让 config 支持 silent
declare module 'axios' {
  export interface AxiosRequestConfig { silent?: boolean }
}

// 成功分支：body.code !== 0
if (!response.config.silent) showToast(body.message || '请求失败')

// 失败分支：
if (!error.config?.silent) {
  // 原有的 401 / 403 / 其他 分支
}
```

注意：**401 分支里的 `clearTokens()` 要保留**（登录态确实失效时必须清），只豁免 toast 文案。不过埋点已由 D6 保证「未登录不发请求」，401 在这里属于极端情况（token 恰好在浏览详情页时过期），此时静默清 token、页面不弹提示是合理的。

### 5.5 路由

```ts
{
  path: '/view-history',
  name: 'view-history',
  component: () => import('@/views/ViewHistoryView.vue'),
```

1. `loadOverview()` 的 `Promise.allSettled` 加第 4 个请求 `fetchViewHistory({ page: 1, size: 1 })`，取 `total`；未登录时同样置 `null`。

### 5.8 `ProductDetailView.vue` 埋点

在 `load()` 末尾追加（**不 await、不 try/catch 到阻塞页面**）：

```ts
// 记录浏览：未登录不上报（避免 401 误报），失败静默（silent）
if (userStore.isLoggedIn) {
  reportViewHistory(Number(route.params.id)).catch(() => {})
}
```

要点：

- **放在 `load()` 里而不是 `onMounted`**：`load()` 已经拿到商品详情，商品不存在时不会白记一条。
- **不 await**：埋点是旁路，不能拖慢首屏。
- 详情页是**唯一**的商品落地页（首页卡片、搜索、收藏页、浏览记录页、订单详情都跳它），所以在这一处埋点即可全覆盖，不需要在每个入口各写一遍。
- 同一商品在「收藏 → 详情 → 返回 → 再点」这种来回场景会重复上报，由后端 upsert 天然收敛为一条，前端**不做防抖抑制**（简单优先）。

## 7. 测试与验收

### 7.1 后端

- 单测：§4.4 的 7 条。
- 接口手测（curl，带 accessToken）：
  1. `POST /api/view-history/{id}` 两次 → `GET` 只返回 1 条且在最前；
  2. `DELETE /api/view-history/{id}` → 列表少一条；再删一次仍 200；
  3. `DELETE /api/view-history` → 列表空；
  4. 不带 token → 401。

### 7.2 新增 CDP 回归 `view-history-verify.mjs`（建议覆盖）

1. 「我的」页菜单 4 项、顺序正确、`浏览记录` 在第 2 位；
2. 未登录访问 `/view-history` → 被重定向到 `/login` 且带 `redirect`；
3. 登录后进详情页 → 产生 `POST /api/view-history/{id}` 请求（按 URL 过滤 `performance.getEntriesByType('resource')`，★该 API 跨页累积，必须过滤）；
4. 同商品进两次 → 列表仍 1 条；
5. 列表按最近浏览倒序（先看 A 再看 B → B 在前）；
6. 单条删除 → 立即消失、不重新拉列表；
7. 清空 → 空态文案出现、`van-list` 不再继续加载；
8. tabbar 在该页隐藏（与 `member-subpages-tabbar-verify` 同口径）；
9. 页面几何：`.view-history` 至少一屏高、背景不透明（tab 互切不留残影）。

★ 脚本不要用真实用户数据做写操作，沿用「自建 ZZ 测试账号 + 跑完清理」的既有约定。
★ 读 Vant toast 要等 `display === 'none'` 再触发下一条（否则读到上一条，假失败）。

### 7.3 手工验收路径

1. 未登录：我的 → 浏览记录 → 跳登录页 → 登录后 redirect 回浏览记录（空态）；
2. 首页点商品 A → 返回 → 点商品 B → 我的（显示 `2 件`）→ 浏览记录（B 在前、A 在后）；
3. 再点一次 A → 记录页 A 跑到最前，总数仍是 `2 件`；
4. 删掉 A → `1 件`；清空 → 空态；
5. 退出登录 → 菜单项还在（与收藏一致），点进去跳登录。
