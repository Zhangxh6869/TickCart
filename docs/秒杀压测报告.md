## 3. 关键结论

**① 1000 倍超发下不超卖。** 500 并发抢 100 件库存，成功恰好 100 个，
Redis 剩余 0，`sold_count` 100，多一个都没有。Lua 三段校验（限购 → 库存 → 扣减）在
单线程执行下天然串行，这是不超卖的根本原因。

**② 削峰是真实的。** 停掉建单消费者后，同一场景 QPS 从 627 升到 949、P95 从 503ms 降到
383ms，100 条消息原样堆在队列里 —— 说明**建单不在抢购的关键路径上**。
反过来也说明：正常链路下消费者与抢购在**争抢 DB 连接**。

**③ 秒杀接口吞吐是普通下单的 12 倍。** 普通立即购买 100 并发 QPS 只有 82、P95 1146ms；
秒杀接口 500 并发 QPS 990、P95 467ms（且并发数是对方的 5 倍）。
原因很简单：普通下单要在事务里做「扣库存 + 建单 + 写明细」，DB 写入速度就是上限；
秒杀接口只做 Redis 指令 + MQ 投递。

**④ 抢购链路的延迟瓶颈是地址校验，不是 Redis。** P95 400~500ms 里，
Redis Lua 与 MQ 各只占约 1ms，剩下几乎全是**地址归属校验的那一次 DB 查询**
（每用户每 3 秒最多一次，500 个用户 = 500 次查询，被 Hikari 20 个连接串行化）。
这条要么加连接池，要么牺牲「秒的即时校验」改回异步兜底。

---

## 4. 瓶颈分析

按耗时排序（S1 的 500ms 里）：

| 环节 | 预计耗时 | 说明 |
|---|---|---|
| 地址校验 DB 查询 | ~350ms | 500 次单行查询 / 20 个连接串行 |
| 请求排队 | ~100ms | Tomcat 100 线程扛 500 并发，每线程轮 5 次 |
| Redis Lua | ~1ms | 单指令，走内存 |
| MQ 投递 | ~1ms | 本地 Broker |

**可做的优化（按性价比）**：

1. 连接池 20 → 40（单机 MySQL 完全撑得住），预期 P95 降一半以上
2. 地址校验结果进 Redis 短缓存（5 秒），把「每请求一次」变成「每用户 5 秒一次」
3. 若要再上一层，就只能去掉抢购时的同步地址校验，靠消费者兜底 + 回补

## 5. 复现方式

```bash
# 1. 关限流与登录频控启动后端
RATE_LIMIT_ENABLED=false LOGIN_GUARD_ENABLED=false \
MYSQL_PORT=3307 SERVER_PORT=8080 mvn spring-boot:run

# 2. 准备账号（token 会缓存到 .workbuddy-ai/tmp/bench-tokens.json）
node scripts/seed-bench-users.mjs 500

# 3. 跑场景
STOCK=100 CLEANUP=1 node scripts/bench-seckill.mjs        # S1
STOCK=500 CLEANUP=1 node scripts/bench-seckill.mjs        # S2
SCENARIO=single SINGLE_STOCK=10 CLEANUP=1 node scripts/bench-seckill.mjs
SCENARIO=normal USERS=100 CLEANUP=1 node scripts/bench-seckill.mjs   # S5

# 4. 削峰对比（S4）：换个开关重启后端
SECKILL_CONSUMER_ENABLED=false ...
DRAIN_TIMEOUT_MS=2000 EXPECT_DRAIN=0 STOCK=100 CLEANUP=1 node scripts/bench-seckill.mjs

# 5. 清理
node scripts/seed-bench-users.mjs --clean
docker exec tickcart-rabbitmq rabbitmqctl purge_queue trade.seckill.order
```

## 6. 局限

1. 单机同环境压测，客户端与服务器抢同一份 CPU，数字偏保守
2. 无真实网络延迟、无网关、无 TLS
3. 数据量小（647 个商品、几千条订单），索引效果比生产更乐观
4. 未覆盖「Redis 宕机」「MQ 宕机」的降级路径压测（那是阶段 4 的混沌实验）
