## 一、问题一：E2E 每跑一次，永久消耗 1 件库存

### 1.1 现象

E2E 下单主链路会真实下单并支付，库存单调递减，且**没有任何合法途径补回**。

2026-10-27 实测快照（目标商品 id=302）：

| 项 | 值 |
|---|---|
| `product.stock`（派生汇总） | 185（原 190） |
| `product_sku` #490 | 105（原 110） |
| `product_sku` #491 | 80 |
| `e2e_runner` 名下订单 | 5 张（全部已支付） |

跑 5 次 → 库存 -5、订单 +5。**库存耗尽后，失败原因会变成「结算按钮不可点」，与真正的代码回归混在一起。**

### 1.2 成因链（附代码依据）

1. **下单即扣库存**，不是支付时扣 —— `OrderService:172`（购物车结算）、`:237`（立即购买）。
   这是刻意设计：防超卖必须早扣，等支付再扣会在并发下卖超。
2. **E2E 必须走到支付成功**，否则测不到收银台、渠道页、订单列表可见。
3. **支付后订单进入「待发货」，状态机不允许取消** —— `OrderStatus:63`：

   ```java
   TRANSITIONS.put(PENDING_PAYMENT,  EnumSet.of(PENDING_SHIPMENT, CANCELLED, TIMEOUT_CLOSED));
   TRANSITIONS.put(PENDING_SHIPMENT, EnumSet.of(PENDING_RECEIPT));   // ← 没有 CANCELLED
   ```

4. **取消请求被直接拒绝，回补逻辑根本没执行** —— `OrderService:740` 第一行就是状态机校验：

   ```java
   private void doCancel(Order order) {
       OrderStatus.of(order.getStatus()).assertTransitionTo(OrderStatus.CANCELLED, "取消");
       restoreStock(order);   // ← 走不到这里
   ```

   2026-10-27 实测：

   ```
   PUT /api/orders/NO202610271956158395718/cancel
   → HTTP 409  {"code":40900,"message":"订单当前为「待发货」，无法取消"}
   库存 105 → 105（未变）；订单状态仍为 1（待发货）；cancel_time 为 NULL
   ```

**结论**：这不是「取消了但库存没回补」，而是「取消这个动作被拒绝」。回补代码本身是好的 ——
同一套 `restoreStock` 在「待付款订单取消」时工作正常（2026-10-27 秒杀订单取消实测：Redis 9→10、`sold_count` 1→0、SKU 库存 +1）。

### 1.3 为什么不能「让已支付订单也能取消」

「付款了不能随便取消」本身是对的。放开它需要连带解决：

- 退款流程（当前**完全没有**）
- 库存回补时点（发货前？发货后？退货入库前？）
- 已发货订单取消，货在哪里、是否质检

**为了测试方便去放宽业务规则，是把成本从测试转嫁到业务上。** 正确做法是绕开，不是修改。

### 1.4 七个方案

| # | 方案 | 做法 | 优点 | 缺点 | 改动 | 风险 |
|---|---|---|---|---|---|---|
| 1 | **E2E 独立数据库** | `application-e2e.yml` 指向 `tickcart_e2e` + 8081；每次 suite 前 DROP/CREATE；Playwright 起两套 webServer；vite proxy 环境变量化 | 真根治；业务代码零改动；本地与 CI 一致 | 本地要起第二套后端（+15~20s、双份 JVM 内存）；排查链路变长 | 5 处 | 低 |
| 2 | **跑前数据重置脚本** | 直连 MySQL 删 `e2e_runner` 订单/购物车 + `UPDATE product_sku/product SET stock = stock + n` | 不用第二套后端；跑完库回原样 | **绕过业务不变量**；两本账容易改歪（项目踩过）；需 DB 凭据 | 1 脚本 | **中** |
| 3 | **复用已有补货接口** | E2E teardown 调 `PUT /api/admin/skus/{skuId}/stock`，把库存写回基线 | 走业务层，账目正确；**接口已存在，零业务改动**；成本极低 | 只解决库存，不解决订单累积；绝对值语义有并发覆盖风险 | 约 10 行 | 极低 |
| 4 | **改测试流程为「下单→取消」** | 不支付，直接取消回补 | 零基础设施，走正常业务回补 | **丢失支付链路覆盖**（收银台/渠道页/订单列表） | 改 spec | 覆盖倒退 |
| 5 | **专用商品 + 超大库存** | 种子库存调到几千 | 成本最低（1 行 SQL）；几乎永不耗尽 | 治标；演示数据失真；新建商品会丢搜索覆盖 | 1 行 | 低 |
| 6 | **每次跑完重建开发库** | `flyway clean + migrate` | 最彻底，所有脏数据一次清掉 | **会清掉 demo 手工数据**；`clean-disabled: true` 要改 | 小 | **高** |
| 7 | **维持现状（守卫）** | 已有：低于 5 件告警 | 零成本；问题可感知、可重置 | 不解决，只是不再"悄悄"发生 | 无 | 无 |

### 1.5 关于方案 3 的重要更正

早期判断「后台只有补货待办（看），没有补货动作（做）」是**错的**。实际已完整实现：

| 层 | 位置 |
|---|---|
| 后端接口 | `AdminProductController:111` → `PUT /api/admin/skus/{skuId}/stock?stock=N` |
| 服务实现 | `ProductService.updateSkuStock:703`（校验非负 → 落库 → `refreshProductStock` 从库重算汇总 → 失效详情缓存） |
| 前端 API | `admin/src/api/product.ts:180` |
| 前端 UI | `ProductManageView.vue:317` 补货清单抽屉，每行一个库存输入框，改完即落库，补够了自动从清单消失 |

所以方案 3 的真实成本是「E2E teardown 接上这个已有接口」，**不是新功能**。

### 1.6 建议

- **当下**：T1（方案 3）。10 行代码、零业务改动，立刻止住库存递减。
- **终局**：T2（方案 1）。这是唯一同时解决「库存累积」和「订单累积」的方案。
- **不推荐**：方案 2（SQL 绕过业务层改两本账，改歪了比不改更糟）、方案 6（会误伤 demo 数据）。

## 二、问题二：已支付之后，完全没有售后出口（产品缺口）

### 2.1 现状矩阵

| 订单状态 | 用户能做什么 | 库存 | 后台能做什么 |
|---|---|---|---|
| 待付款 | 取消订单 | 回补 | 关闭订单（`adminClose`） |
| **待发货（已付款）** | **无** | 锁死 | **无** |
| **待收货** | 只能等自动确认 | 锁死 | 无 |
| **已完成** | 无售后入口 | 锁死 | 无 |

数据库侧：`db/migration/` 只到 `V9`，**grep 不到任何 `refund` / 退款 / 退货 / 售后相关表**。
前台只有「取消订单」一个按钮，`canCancel` 只对待付款生效。

**一句话**：用户付了钱反悔，只能干等收货。这是真实产品缺陷，与 E2E 无关。

### 2.2 「退款」不是一个功能，是一组能力

| 能力 | 场景 | 库存处理 | 复杂度 |
|---|---|---|---|
| **未发货取消 + 退款** | 付款后、发货前反悔 | 立即回补，最干净 | **低** |
| **仅退款** | 已发货但用户不要货 / 拒收 | 货未回来，不能回补 | 中（要物流状态） |
| **退货退款** | 收到货不满意 | 退回并入库，可能质检 | **高**（物流 + 入库 + 质检） |
| 换货 | 尺码不对等 | 一退一发 | 高 |

### 2.3 优先级：先做第一件

**「待发货时取消 + 退款」**，理由：

1. 覆盖最高频场景（买错、地址错、不想买了，多数发生在发货前）
2. 库存处理最干净 —— `restoreStock` 现成的，不需要"退货仓""质检合格"概念
3. 不依赖物流对接，做完即形成闭环，后续都是增量
4. 成本可控：一次 schema 变更 + 状态机加两条边 + 两个接口

「退货退款」本质是**仓储与售后流程**，不是支付功能，应单独排期。

### 2.4 第一步的设计轮廓（未定稿）

```
状态机：待发货 → 退款中 → 已退款
        待发货 → 待收货（发货，现有路径不变）

表：refund_record
    order_no / amount / reason / status / refund_no / created_at / finished_at
    ★ 改 schema，按项目铁律必须先审批

接口：
    POST /api/orders/{orderNo}/refund           用户申请（限待发货）
    POST /api/admin/refunds/{refundNo}/confirm  后台确认

库存：确认退款时回补（复用 restoreStock）
幂等：refund_no 唯一 + 条件 UPDATE（WHERE status = 待发货）
```

**一个要提前定的取舍**：是否需要「退款中」中间态。

- 本项目支付是**模拟渠道**（`MockChannelController`），没有真实资金流，理论上可以一步到「已退款」
- 但真实渠道必须有中间态（等回调）。建议**保留中间态**，将来接真实渠道不用改状态机

### 2.5 必须审批的点

按 `AGENTS.md`：AI 禁止私自变更数据库字段 / 表结构 / 核心业务逻辑。

| 变更 | 需要审批 |

## 三、两个问题的关系

两者**同源不同层**：

```
业务规则（正确，不该改）
  已支付订单不可取消
        │
        ├──→ 产品缺口：用户付了钱没有出口  ← 该补（退款）
        │
        └──→ 测试困境：E2E 每跑一次永久扣 1 件库存  ← 该绕（teardown / 独立库）
```

**即使将来做了退款，也不应让 E2E 靠退款来保持环境干净**：退款一旦有 bug，E2E 会红，
但失败原因与下单链路无关，排查成本反而上升。E2E 的环境治理与退款是两件事。

> 附带好处：退款做完后，E2E teardown 可从「调补货接口」升级为「取消订单」，
> 更贴近真实业务路径，并顺带覆盖退款链路 —— 但这是副产品，不是做的理由。
