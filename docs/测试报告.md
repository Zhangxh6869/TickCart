## E2E 数据隔离（2026-10-27）

### 问题

E2E 直接打开发库：下单扣真实库存、购物车残留、订单堆在 demo 名下。
后果不是「测试挂掉」，而是**测试让人不敢跑** —— 每跑一次就往 demo 塞一张订单，
手动体验时满屏测试数据，且库存只减不增，迟早买空。

### 做法：专用账号 + 全局前后置

| 文件 | 职责 |
|---|---|
| `e2e/support/e2e-account.ts` | 注册（幂等，已存在则跳过）→ 登录 → 补收货地址 → 清购物车 → 库存守卫 |
| `e2e/global-setup.ts` | suite 开跑前调用一次，打印「已清空 N 项；库存 M 件」 |
| `e2e/global-teardown.ts` | suite 结束后清购物车，失败只告警不外抛 |
| `e2e/order-flow.spec.ts` | 改用 `e2e_runner`；`beforeEach` 再清一次购物车 |

**为什么不用 demo**：demo 是给人手动体验的。专用账号把不可避免的残留（已支付订单删不掉）
圈在一个人身上。

**为什么 `beforeEach` 还要清一次**（globalSetup 已经清过）：CI 上 `retries: 1`。
第一次尝试若在「加购之后、下单之前」失败，重试时购物车里还留着那件商品，
再点「加入购物车」数量会变 2 —— 起点就不一致了。一次 API 调用换来重试行为与首次一致。

### 验证

```
[e2e] 账号就绪：已清空购物车 0 项；目标商品库存 188 件
  3 passed (12.0s)
```

| 检查点 | 结果 |
|---|---|
| `sys_user` | 新增 `e2e_runner`（id 3145），demo 不动 |
| 订单归属 | demo 143 张（历史，未增加）；`e2e_runner` 1 张 |
| 购物车有效项（`deleted=0`） | **0** |

### ★ 一个自己造成的假警报

跑完查库看到 `cart_item` 里有一行，以为收尾没清干净。实际那行 `deleted=1` ——
**订单提交后购物车项是软删的**，`GET /api/cart` 已经看不到它。

教训：查库断言「有没有残留」必须带 `deleted = 0`，否则会把软删的历史行当成脏数据，
进而去「修」一个并不存在的问题。

### 仍未解决：库存只减不增

**这不是测试写坏了，是业务规则和测试目标撞上了。** 链条是：

1. 库存在**下单时**就扣（`OrderService:172` / `:237`），不是支付时 —— 这是对的，
   防超卖必须早扣，等到支付再扣就会在并发下卖超。
2. E2E 必须走到「支付成功」，否则测不到收银台、渠道页、订单列表这条链路。
3. 支付后订单进入「待发货」，而状态机里 `PENDING_SHIPMENT` 只能流转到 `PENDING_RECEIPT`
   （`OrderStatus:63`）—— **没有到「已取消」的边**。付款了就不许随便取消，业务上也该如此。
4. 于是那张订单永远占着 1 件库存，回补不了。

190 件库存 = 190 次 E2E。耗尽后失败原因是「结算按钮不可点」，会被误读成回归。

**守卫读的是 SKU 而不是商品汇总**：加购扣的是 `product_sku.stock`，商品上的 `stock`
只是派生汇总。实测两者差得很远 —— 商品 187 / SKU #490=107 / SKU #491=80。
按汇总判断会把可跑次数高估近一倍，所以取**所有规格的最小值**（测试点哪个规格不确定，按最紧的算）。

★ 守卫读的是商品详情接口，**命中 60 秒缓存**，读数可能滞后一两次运行（实测报 107 时库里已是 105）。
作为「库存告急」的提示够用，不能当成精确对账。

**为什么 CI 不受影响**：CI 的 e2e job 每次起全新 MySQL，跑完销毁，库存天然从种子开始。
只有本地长期复用同一个开发库才会累积。

**为什么不做「下单后取消」来回收库存**：那样就丢失了「支付 → 订单可见」的覆盖，
而那正是这条用例存在的理由。要做只能在「覆盖」和「无副作用」之间选一个，
真正两全的办法是独立测试库 —— 属于基础设施投入，本轮没做。

## 前端单元测试（2026-10-27）

### 结果：58 个用例 / 5 个文件，全绿（约 1 秒）

```
✓ tests/checkout-route.spec.ts (10 tests)
✓ tests/shared-utils.spec.ts (17 tests)
✓ tests/share.spec.ts (10 tests)
✓ tests/pay-countdown.spec.ts (11 tests)
✓ tests/cart-store.spec.ts (10 tests)
Tests  58 passed (58)   Duration 976ms
```

### 为什么选这五处，而不是「给组件补测试」

这五个都是**「多处共用、写岔了不报错」的约定**：

| 文件 | 不测会怎样 |
|---|---|
| `utils/checkout-route.ts` | 「立即购买」与「购物车结算」靠一个 query 字段区分，写岔了就静默走错分支 |
| `composables/usePayCountdown.ts` | 后端给的是 `yyyy-MM-dd HH:mm:ss`，Safari 直接 `new Date()` 会 Invalid Date；过期返负数会显示 `-1:-1` |
| `packages/shared-utils` | 两个 app 共用，`formatCount` 的 9999/10000 边界错一处就两边一起错 |
| `stores/cart.ts` | `checkedItems` 少一个 `item.valid` 判断，下架商品就会被带进结算 |
| `utils/share.ts` | 分享链接口径散在三处入口，`toAbsoluteUrl` 少补一个斜杠，第三方分享页就抓不到图 |

组件渲染不在这里测 —— 那是 E2E 的活，而且 E2E 已经抓到过真 bug（地址异步加载那次）。
**E2E 管「看得见的东西对不对」，单测管「看不见的东西算得对不对」。**

### 配置上的三个决定

1. **`environment: 'node'`，不装 jsdom**。全部是纯逻辑，需要 `window`/`navigator` 的地方用
   `vi.stubGlobal` 打桩即可。为两个纯函数引一整套 DOM 模拟不划算。
2. **测试文件放 `apps/mall/tests/`，不放 `src/`**。`build` 第一步是 `vue-tsc --noEmit`，
   而 tsconfig 的 `include` 是 `src/**` —— 放 `src/` 会让测试参与构建期类型检查，
   一改测试就可能让构建失败。放 `tests/` 则完全隔离（实测 `vue-tsc` 仍无错）。
3. **不开 `globals: true`**，显式 `import { describe, it, expect } from 'vitest'`，
   避免往 tsconfig 塞 `types: ["vitest/globals"]`，把测试和构建链绑在一起。

`@` 别名由 `vitest.config.ts` 通过 `mergeConfig(viteConfig, ...)` 复用 ——
**`tsconfig.json` 的 `paths` 只影响类型检查，vitest 运行时读的是 vite 的 `resolve.alias`**，
两处各写一份迟早会分叉。

### 变异验证：证明这些断言是活的

把 `cart.ts` 里 `checkedItems` 的 `item.valid &&` 去掉（模拟「下架商品被带进结算」）：

```
Tests  1 failed | 57 passed (58)
```

改回来立刻恢复 58 全绿。这条变异对应的是真实业务风险（结算页带上下架商品 → 下单失败），
不是为凑覆盖率写的空断言。

### 已知边界

- **`apps/admin` 没有单测**。它的纯逻辑（`pct` / `barWidth` / `hitTagType`）都写死在
  `SearchAnalyticsView.vue` 里，要测得先抽成 utils —— 那属于重构，不该混在「补测试」里做。
- **组件渲染仍未覆盖**，靠 E2E 兜。将来若要测，再加 `@vue/test-utils` + jsdom，
  并且只挑「有分支逻辑的组件」（如 `ProductCard` 的售罄态），不追求覆盖率数字。

## 故障注入（2026-10-27）

### 方法

先读代码预判「依赖挂掉时的行为」，再实测验证。这样即使环境起不来也有可复用的结论，
实测只是确认预判对不对。

### 预判表

| 依赖 | 挂掉后的行为 | 代码依据 | 设计理由 |
|---|---|---|---|
| **Redis**（商品缓存） | 降级查 DB，接口正常但变慢 | `CacheService:103` → `catch { log.warn("读取缓存失败，直接回源") }` | 缓存是可选的，不该因它挂掉就不可用 |
| **Redis**（秒杀库存） | 秒杀下单失败（500），但**不会超卖** | `SeckillStockService.tryDeduct:212` **没有 try-catch** | 库存必须原子扣减；降级到 DB 会直接超卖，宁可不可用 |
| **RabbitMQ** | **下单成功**，但超时关单消息发不出去 | `OrderMessageProducer:41` → `catch { log.error("不影响下单") }` | 可用性优先：宁可订单卡住，也不让下单失败 |
| **MySQL** | 全部失败 | 无降级空间 | 唯一数据源 |

同一个 Redis，在两处用了**完全相反**的策略——缓存降级、库存不降级。这不是不一致，
而是按「降级的代价」分开判断：缓存失效只是慢一点，库存降级会卖超。

### ★ 一个值得记录的缺口

RabbitMQ 挂掉时下单仍然成功，但超时关单消息丢失 → **订单永远停在「待付款」，库存永远被占用**。

目前**没有兜底机制**（比如定时任务扫描「创建超过 N 分钟仍未支付」的订单）。

这是「可用性优先」的代价，属于已知取舍而非 bug。要补的话，加一个低频补偿任务即可，
成本和风险都不高。

### 实测结果（2026-10-27）

环境：Docker 三件中间件 + 本地后端（8080），逐个 `docker stop` 后调接口，测完立即 `start`。

| 场景 | 接口 | 结果 | 与预判 |
|---|---|---|---|
| 停 Redis | 商品详情 | **200 / 6.06 s**（正常 0.019 s） | ✅ 降级成功，但**慢了 320 倍** |
| 停 Redis | 鉴权接口 | **200**（fail-open） | ✅ |
| 停 RabbitMQ | 下单 | **200 / 0.17 s**，订单建成待付款 | ✅ |
| 停 MySQL | 订单数（查 DB） | **500 / 3.03 s** | ✅ |
| 停 MySQL | 商品详情（走缓存） | **200 / 0.011 s** | ⚠️ 预判「全挂」，实际**被缓存挡住了** |

### ★ 实测修正了预判的两处

**1. Redis 降级「成功」了，但性能崩了**

代码分析看到 `catch` 就以为降级没问题。实测发现每次请求要 **6 秒**——
`spring.data.redis.timeout: 3s`，读缓存一次超时 + 写缓存一次超时，叠加成 6 秒。

**这不叫降级成功，这叫降级后不可用。** 并发稍高就会把 Tomcat 线程池占满，
一个 Redis 故障会演变成整个服务不可用——比直接 500 更糟，因为它慢，会拖住所有请求。

要修有两条路：把 Redis 超时调小（如 500ms），或者加熔断器（连续失败 N 次后
一段时间内直接跳过 Redis，不再尝试连接）。

**2. MySQL 挂掉不是「全挂」**

预判写的是「无降级空间，全部失败」。实测发现**商品详情仍返回 200**——
因为缓存命中，压根没碰 DB。

这说明缓存不只是性能优化，也是**一层故障隔离**：MySQL 挂掉时，热门商品还能看。

### 未实测的部分（秒杀接口，已补测，见下方「三项缺口已修」第 3 条）

**秒杀接口**：当前没有进行中的活动（3 场都已结束），无法构造真实扣减场景。
按代码分析，`tryDeduct` 没有 catch，Redis 挂掉会直接抛异常 → 500，不会超卖。

### 这次故障注入的结论

代码分析能告诉你「设计意图」，实测才能告诉你「实际行为」。两处偏差都很典型：

- **catch 住了 ≠ 降级可用**（超时叠加让降级变成慢性毒药）
- **有缓存 ≠ 缓存有效**（这次反而是缓存救了 MySQL 故障）

如果不做实测，报告里会写「Redis 挂了自动降级查 DB」——听起来很稳，
实际上 6 秒的响应时间在生产上等同于故障。

### 三项缺口已修 / 已测（2026-10-27 晚）

**1. Redis 降级 6 秒 → 1.05 秒**

先纠正本节早先的归因：**不是「读+写各超时一次」**。`CacheService.get` 一旦 catch 就
`return loader.get()`（第 106 行），根本不走 `writeQuietly`。真实构成是**两次独立超时**：

1. 限流器 —— `RateLimitConfig` 拦 `/api/**`，`product-read` 规则命中 `/api/products/**`，
   `RedisRateLimiter:98` catch 后放行 = 3 秒
2. 缓存 —— `CacheService:103` catch 后回源 = 3 秒

修法：`spring.data.redis.timeout` 3s → **500ms**，并显式加 `connect-timeout: 500ms`
（不写时 Lettuce 默认 10 秒，网络分区场景会比 3 秒更糟）。

实测（`docker stop tickcart-redis`，商品详情连打 3 次）：

| 场景 | 耗时 |
|---|---|
| 正常 | 0.010 ~ 0.060 s |
| Redis 挂掉（修前） | 6.06 s |
| Redis 挂掉（修后） | **1.04 ~ 1.07 s** |

**4. 补上熔断器：1.05 秒 → 20 毫秒**

500ms 只是把 6 秒压到 1 秒，**每个请求仍要为一个已经挂掉的连接白等 1 秒**。
Tomcat 只有 100 个线程，`100 ÷ 1.05 ≈ 95 RPS` —— 容量比正常低约 100 倍。
熔断器不让 Redis 变快，它让服务**停止去试**。

新增 `common/redis/RedisHealthGuard`（关闭 / 打开 / 半开三态），接入四处：

| 位置 | 熔断期间的行为 |
|---|---|
| `RedisRateLimiter.tryAcquire` | 直接放行，不碰 Redis |
| `CacheService.get` | 直接回源 |
| `RedisTokenBlacklist.isRevoked` / `isIssuedBefore` | 直接 fail-open |
| `SeckillStockService.tryDeduct` | **快速抛异常，但不跳过校验**（跳过等于超卖） |

实测（`docker stop tickcart-redis`，连续请求 8 次）：

| 第几次 | 耗时 | 说明 |
|---|---|---|
| 1 | 1.089 s | 2 次失败 |
| 2 | 1.042 s | 4 次失败 |
| 3 | 0.557 s | 第 5 次失败触发熔断，后续环节被跳过 |
| 4 ~ 8 | **0.020 ~ 0.038 s** | 熔断中，完全不碰 Redis |

`docker start` 后等过 30 秒窗口，半开探针成功 → 日志 `Redis 已恢复，熔断关闭`，
缓存重新写入（`cache:product:detail:302` 出现），耗时回到 0.010 ~ 0.019 s。

**两个设计细节**（都是为了「不要卡死」）：

- **半开只放一个探针，且探针有租约**。用 CAS 抢租约而不是布尔标记 ——
  万一探针请求在回报结果前就终止，布尔标记会永久卡住、再也恢复不了；
  租约到期会自动放行下一个探针，能自愈。
- **只在状态切换时打日志**。故障期间每个请求都打一行会把日志刷爆，
  而「什么时候熔断、什么时候恢复」这两条才有用。

★ **一个只有启动才暴露的问题**：`RedisHealthGuard` 有一个公开构造器（Spring 注入）
和一个包级构造器（单测注入时钟），**两个构造器时 Spring 不会自动挑选**，
直接报 `No default constructor found`，应用起不来。修法是给公开构造器加 `@Autowired`。
单测全绿也发现不了 —— 这类问题只有 `ContextSmokeIT` 或真实启动能抓。

**2. MQ 兜底补偿**

新增 `trade/task/OrderTimeoutCompensateTask`：每 60 秒扫
`status = 待付款 AND created_at < now - 支付时限 - 60s`，LIMIT 100，逐个调
`orderService.closeTimeout`。

安全性不来自新代码，而来自 `closeTimeout` 本身（`@Transactional` + 条件 UPDATE
`WHERE status = 待付款`）—— 与 MQ 消费者并发时只有一个能改成功，不会重复回补库存。
**故意不加分布式锁**：本任务要兜的正是「Redis 挂了」的场景，反过来依赖 Redis 会弄脆兜底。

实测（把 TTL 调成 10 秒、宽限 2 秒、间隔 5 秒跑一轮）：

| 检查点 | 结果 |
|---|---|
| 订单状态 | 0（待付款）→ **5（已超时关闭）** |
| `product_sku.stock` | 110 → **111** |
| `product.stock`（派生汇总） | 190 → **191** |
| 单测 | 新增 8 个；全量 **435 个**全绿 |

顺带一个值得记的副作用：用短 TTL 跑的时候，库里 3 张**早就该关**的历史待付款订单
（10-06 与 10-27 14:19 创建）被一并关掉了。这恰好说明补偿任务在默认配置下上线后，
第一批扫描就会清掉这些「消息早就丢了」的僵尸单 —— 它们是故障注入那次留下的痕迹。

**3. 秒杀链路故障注入（补测，不改代码）**

之前这一项只停留在「代码分析」：`tryDeduct` 没有 catch，所以 Redis 挂了会 500。
这次造了一场真实的进行中活动来验证。

准备：`POST /api/admin/seckill/activities`（商品 302 / SKU 490，秒杀价 9.90，库存 10）
→ `PUT .../enabled=1` 触发预热，Redis 出现 `seckill:stock:36 = 10`。

| 场景 | 结果 |
|---|---|
| Redis 挂掉 → 抢购 | **500**（`服务器内部错误`），耗时 1.53 s |
| 故障期间 `product_sku.stock` | 110 → **110**（未动） |
| 故障期间 `sold_count` / 订单数 | 0 / 0 → **0 / 0**（未动） |
| Redis 恢复 → 库存键 | 回到 **10** |
| 恢复后再抢 | **200**，`remainingStock=9`，订单 `SK202610271914365777497` 建成 |
| 取消该订单 | Redis 回到 **10**，`sold_count` 回到 **0** |

**结论**：代码分析的判断成立 —— 秒杀链路是 **fail-close**：不知道库存就不卖，
直接 500，而不是像商品缓存那样降级回源（降级会超卖）。这与缓存那条 fail-open
形成刻意的对照，判断依据是「降级的代价」：缓存失效只是慢，库存降级是卖错。

★ 一个容易误读的点：抢购成功后 `product_sku.stock` 仍然是 110 —— 秒杀库存是
**独立的账**（Redis 计数 + `seckill_activity.seckill_stock`），不占普通 SKU 库存。

★ 另一处观察：取消订单后 `seckill:bought:{activityId}:{userId}` 被 `decrement` 到 `0`
而不是删除。这不是 bug（Lua 里 `GET ... or '0'` 对 0 的处理正确），但会留一个
无 TTL 的零值键 —— 活动删除后需手动清理。

测试数据已全部清理：活动 36 删除、订单与明细删除、`product_sku.stock` / `product.stock`
还原为 110 / 190、前台活动列表回到 `[]`。

### CI 首跑失败：一个典型的「本地绿、CI 红」

首次跑（`08f5ccc`）E2E 挂了，其余 3 个绿。日志下载需要 admin 权限拿不到，于是从数据入手查：

```
user_address 只出现在 V3__init_trade.sql 里 —— 而那是建表语句，不是种子 INSERT
```

**种子数据根本没有收货地址。** CI 用全新库，demo 用户没有地址，结算页 `.card__name`
永远等不到就超时了；本地库因为之前手动建过地址，所以一直能过。

走 `/api` 而不是直连 8080，因为 vite dev server 有反代，本地和 CI 共用同一套地址。

这类问题的教训是：**E2E 的「前置数据」必须自己准备，不能依赖开发库里碰巧存在的数据**。

### CI 结构：三个并行 job

| job | 内容 | 本地耗时 |
|---|---|---|
| `backend-unit` | `mvn -B test` | ~15 s（427 个） |
| `backend-integration` | `mvn -B test -Dtest='*IT'` | ~52 s（16 个，Testcontainers 起真实中间件） |
| `frontend` | `pnpm install --frozen-lockfile` + `vue-tsc` ×2 + `vite build` ×2 | ~20 s |

三者互不依赖，并行跑总时长约等于最慢的那个（~1 分钟）。

### 三个踩到的坑

**1. 命名陷阱：`TestcontainersSmokeIT` 仍被单测 job 带走**

surefire 的默认 include 是 `**/Test*.java`，这是**前缀匹配**。`TestcontainersSmokeIT` 以 `Test` 开头，
改后缀成 `IT` 根本没用——实测单测 job 仍然跑了它，还多花 12 秒。

最终改名 `ContainerSmokeIT` 才真正归到集成测试。**想靠 `IT` 后缀区分是不够的，类名不能以 `Test` 开头。**

**2. lock 与 package.json 不一致，`--frozen-lockfile` 会失败**

前面修前端类型错误时给两个 app 加了 `@types/node`，但 lock 一直被还原
（当时的判断是「代码没改、lock 却变了 = 噪音」，那个判断在当时是对的）。
这次代码真的加了依赖，lock 必须同步。

用 `pnpm install --lockfile-only` 生成——**它只写 lock、不碰 node_modules**，
正好绕开本机沙箱创建符号链接失败的问题。

关于 diff 里的 42 条 `@pnpm/exe`：pnpm 12 的 `packageManagerDependencies` 会把 pnpm 自身写进 lock。
这不是随机污染，是新版本的正常行为，不必再还原。

**3. 本地 `vite build` 被 safe-delete 拦**

vite 默认先清空 `dist`，而 `dist/assets` 有 50+ 文件时沙箱要求批量删除确认，
连 `fs.unlinkSync` 都被 hook 住。解法是 `--emptyOutDir false`。
CI 里 dist 本来就不存在，加这个参数无影响，所以两边统一成一样的命令。

### P6 结论

四道闸门全部就绪：本地一条命令验证（`scripts/verify.sh`），推送到 GitHub 后自动跑。
CI 已实测 4 个 job 全绿，总耗时 96 秒。

### 一个绕开的设计：为什么不测 TTL 延迟

超时关单用「TTL + 死信队列」实现延迟，队列 TTL 是 **15 分钟**，真实等待不可行。

想改短 TTL 也不行：`OrderMqConfig` 用 `QueueBuilder.durable(...).ttl(...)` 声明队列，
TTL 是**队列参数**。若测试上下文用 1 秒、生产上下文用 15 分钟，同一个 RabbitMQ 实例上
第二次声明会因参数不一致抛 `PRECONDITION_FAILED - inequivalent arg 'x-message-ttl'`。

**所以测试直接把消息投到 `trade.dlx` 交换机（routing key `order.timeout.dead`）**，
等价于「TTL 到期后转入死信」这一步的结果，然后验证消费链路。

这个取舍是合理的：TTL 是 RabbitMQ 的内置能力，配置对了就行；真正容易出错的是
**消费逻辑、幂等、死信路由、ack 行为**，这些全在被测范围内。

### 变异验证：证明 A2 不是假绿

A2 最大的风险是「第二条消息还没消费完就断言」——那时库存恰好是 100，测试会假绿。
除了用「死信队列被消费空」做同步点，还做了变异验证：

**变异点**：删掉 `OrderService.closeTimeout` 的状态条件

```java
int affected = orderMapper.update(null, new LambdaUpdateWrapper<Order>()
        .eq(Order::getOrderNo, orderNo)
-.eq(Order::getStatus, OrderStatus.PENDING_PAYMENT.getCode())   // ← 删除这行
        .set(Order::getStatus, OrderStatus.TIMEOUT_CLOSED.getCode())
        .set(Order::getCancelTime, LocalDateTime.now()));
```

**结果**：

```
Tests run: 1, Failures: 1
expected: 100
 but was: 102
```

重复消息把库存回补了两次（100 → 102），A2 准确抓住。**已还原并重跑，5 个用例仍全绿。**

> 顺带验证了一个细节：MySQL 的 `UPDATE` 默认返回**匹配行数**而非**实际改变行数**
> （`useAffectedRows=false`）。所以即使 `status` 已经是 5、再改成 5，`affected` 仍然是 1，
> 幂等保护完全依赖那个 `WHERE status = 0` 条件——删掉它，幂等立刻失效。

### G3 结论

1. **超时关单链路完整可用**：消息进死信 → 消费 → 状态流转 → 库存回补。
2. **重复消费幂等成立**，且经过变异验证，具备真实防护力。
3. 「静默丢单」这个最难靠人工发现的风险，现在有了自动化防线。

### 底座设计要点

| 决策 | 原因 |
|---|---|
| **singleton container**（手动 `start()`，不用 `@Container`） | `@Container` 会让每个 IT 类各起一次容器，实测第二个类从 1.3s 涨回 37.8s |
| **自造数，不用 Flyway 种子** | 种子库存固定，多个并发用例共享会互相干扰；自造才能精确控制「库存 10」 |
| **`@Transactional` 回滚清理 → 改为 `TRUNCATE`** | 并发用例不能被事务包裹（回滚会让并发失效），MQ 的异步结果也看不见 |
| **不变量集中到 `InventoryInvariantChecker`** | 新增用例不用重写断言，也不会漏维度 |

已实现的不变量：**I1** 商品汇总库存 == SKU 库存合计、**I2** 库存非负、
**I3** 成交数量 ≤ 初始备货（超卖的定义）。

### P1 结论

1. **幂等与防超卖在真实数据库下都成立**，不是「靠单测的 mock 假装成立」。
2. **测试本身经过了变异验证**，具备真实防护力。
3. 集成测试底座可复用，后续补异步链路（G3）、权限（G4）的边际成本只有几秒。

### P0 结论与发现

**1. 后端基线是绿色的，428 个用例全过。** 后续任何失败都可以判定为新引入的回归，基线可信。

**2. 但「全绿」的含义有限。** 这 428 个用例全部是 Mockito 单测，被 mock 掉的恰好是幂等、超卖、MQ 可靠性这三套核心机制依赖的真实中间件行为（详见 `docs/测试方案.md` §1.2）。基线绿只说明「正常路径的代码逻辑没坏」，不说明「系统不会超卖」。

**3. 前端构建链路此前是断的（P0 最重要的发现），已修复。**

`apps/*/package.json` 的 `build` 脚本是：

```json
"build": "vue-tsc --noEmit && vite build"
```

`vue-tsc` 非零退出会直接中断 `build`。所以修复前**前端根本无法构建，也就无法部署**——这不是「测试不通过」，是上线阻塞项。此前一直被归类为「既有类型错误，勿改」，性质判断错了。

两处根因与修法：

| 根因 | 修法 |
|---|---|
| 缺 `@types/node`，`vite.config.ts` 里 `import ... from 'node:url'` 没有类型声明 | 两个 app 各加 `@types/node: ^22.0.0`（**必须跟运行时 Node 22 对齐，不能装最新的 26**） |
| 拦截器返回 `body.data`，而 axios 类型签名要求返回 `AxiosResponse` | 类型层桥接一次并加注释，不改运行时（api 层已按解包后的类型声明返回值） |

**为什么开发时一直没发现**：`vite dev` 和 `vite build` 都用 esbuild 转译，**不做类型检查**，类型错误在开发期完全静默。只有 `vue-tsc` 会报，而它只在 `build` 时执行。

**修复过程中的环境事故（值得记录）**：执行 `pnpm add -D @types/node` 时触发了 pnpm 的 peer 依赖重解析，需要重建 `vite` / `@vitejs/plugin-vue` / `@types/node` 三个链接。但该沙箱环境**禁止创建符号链接**（`ln -s` 返回成功但无文件；PowerShell junction 报 `sandbox-center cmd decisionRecord missing`），导致旧链接被删、新链接建不回来，`@types` 和 `@vitejs` 变成空目录，前端一度完全起不来。最终由用户在自己的终端执行 `pnpm install --force` 恢复。

**结论**：依赖安装类操作不要放在受限环境里执行。

**4. 测试基础设施已就绪。** `TestcontainersSmokeTest` 保留在代码库中，换机器或升级 Docker 后先跑它验证环境（12 秒），避免集成测试阶段误判。
