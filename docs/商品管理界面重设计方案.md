## 二、三个方案

三个方案**共用同一套后端接口**，差异全在前端信息组织方式。

### 方案 A · 精修表格 + 抽屉表单（`#a`）

**一句话**：保留表格心智，把「商品」列做成复合单元，把弹窗换成三段式抽屉。

- **商品列**：56px 圆角图 + 名称 + 副标题 + `分类 tag / ID / SKU 数` 三件套；下架行图片降透明度
- **价格列**：主价大字 + 副行「区间 / 秒杀价 / 单一价格」
- **库存列**：数字 + 告急红标；告急行左侧加 3px 红条，扫表时整行可定位
- **状态列**：`el-switch` 直接切换，乐观更新不重查列表（解决 #4）
- **操作列**：`编辑` + `更多 ▾`（复制 / 加入秒杀 / 预览 / 删除），把高危操作收进二级菜单
- **筛选区**：搜索 + 状态 segmented + 排序下拉 + 分类 chips（带数量）
- **批量操作**：勾选后在表头上方浮出操作条（批量上下架 / 改分类 / 删除）
- **表单**：720px 弹窗 → 760px 右侧抽屉，分三个 tab（基础信息 / 图片 / 规格 SKU），每段一屏放得下
- **成本**：前端 1 文件重写 + 1 个抽屉组件；后端 **+2 个 VO 字段**（`skuCount`、`priceMin/priceMax`），不想要可以砍掉这两个副行 → 0 改动
- **适合**：要「筛一批、逐条核对改」的日常运营

### 方案 B · 商品墙（`#b`）

**一句话**：以图为主，先看图再看字。

- 4~5 列自适应卡片：4:3 大图 + 左上状态角标（在售 / 已下架 / 秒杀中）+ 右上勾选 + 左下「仅剩 N」红标
- hover 从底部升起 `编辑 / 下架 / 删除` 操作条，平时不占版面
- 卡片底部：名称 2 行 + 副标题 + 价格 + `库存 / 销量` 双指标
- 工具条：大搜索 + 状态 segmented + 排序 + **网格/列表视图切换**
- 分页改「加载更多」或每页 48，减少翻页次数
- **成本**：前端 1 文件；后端 **0 改动**（`mainImage / price / stock / sales / status / isSeckill` 列表 VO 全有）
- **适合**：挑品、检查图片质量（主图糊不糊、白底是否统一）
- **短板**：单屏信息量只有表格的 1/2，翻页更多；价格/库存横向对比不直观

### 方案 C · 主从工作台（`#c`）

**一句话**：零弹窗，选中即就地编辑。

- 左栏 352px 紧凑列表：40px 缩略图 + 名称 + 价格 + 库存 + 状态点，`↑` `↓` 键切换
- 右栏常驻编辑面板：头部（大图 + 名称 + 分类 + 状态开关）→ 价格与库存 → SKU 表 → 图片 → 文案，区块可折叠
- **就地改**：价格、销量、每个 SKU 的价格/库存都是行内输入框，改动字段带橙色左边点
- 底部固定保存条：`N 处未保存改动` + 放弃 + 保存；切商品前提示
- **成本**：前端 1 文件；后端 **0 改动**（`PUT /api/admin/skus/{skuId}/stock` 已存在，SKU 库存可即时落库）
- **适合**：连续调价 / 补货，一次改 5 个商品不跳页
- **短板**：横向吃空间（≥1280 才舒服）；dirty 状态管理最复杂，容易丢改动；不适合批量操作

## 六、两个刻意的取舍

1. **库存不做进度条**。原型初稿画过「库存 / 300」的比例条，删掉了：没有明确的仓容基准，条形长度会被读成「充足度」，而实际含义只是「占某个虚构上限的比例」，比纯数字更容易误导。改用「数字 + 告急标签 + 行左红条」，只表达「要不要补货」这一个二元信息。
2. **删除不留在主操作列**。删除是低频高危，和「编辑」并列摆放会提高误点率；收进 `更多 ▾` 且需要二次确认。

## 七、需要拍板的点

1. **选哪个方案**（或 A + C 的组合）
2. **库存安全线**：见第八、九节专题。建议取「分类级落库 + 全局配置兜底 + 后端下发 `stockLow`」
3. **批量操作**：加 3 个批量接口，还是前端循环发 N 个请求？（≤20 条时循环可接受）
4. **列表默认每页**：维持 10，还是 12 / 20？
5. **「库存告急」要不要服务端筛选**（`stock < N` 作为查询条件），还是只在前端对当前页标红？

## 八、专题：库存安全线怎么定

### 8.1 这条线控制什么

按对后端的依赖递增，一共三个用途：

| 用途 | 能否前端算 |
|---|---|
| ① 列表里标红「告急」 | 能 |
| ② 「库存告急」筛选 / 全量统计（第 3 页的告急商品也要能筛出来） | **不能**，要进 SQL `WHERE stock < ?` |
| ③ 自动补货提醒（定时扫描 + 站内信） | **不能**，要服务端定时任务 |

只做 ① 的话前端常量就够；一旦要做 ② 或 ③，阈值必须挪到服务端——否则前后端两套口径，会出现「页面标红 3 个、筛选出 5 个」。

### 8.2 三个选项

**选项一 · 前端常量**：`const STOCK_WARN = 10` 写死在 `ProductManageView.vue`。成本 0，但只能做 ①。

**选项二 · 商品级字段**（表结构变更）：
```sql
ALTER TABLE `product`
  ADD COLUMN `stock_warn_threshold` INT NOT NULL DEFAULT 10
  COMMENT '库存预警线：stock 低于该值在后台标记告急' AFTER `stock`;
```
改动面：迁移 1 个 + `Product.java` / `ProductSaveRequest` / `ProductListItem` / `ProductDetail` / `ProductService` 映射 + 前端 `ProductPayload` + 抽屉里多一个输入框，共 7 处。
真正的成本不在写代码，在**运营**：存量 156 条商品会全部落到 `DEFAULT 10`，等于「字段开了但没配」，得逐个去调才有意义——这是这类字段最常见的结局。

**选项三 · 全局配置项**（0 表结构变更）：
```yaml
tickcart:
  stock:
    warn-threshold: ${STOCK_WARN_THRESHOLD:10}
```
配一个 `StockProperties`，照现有 `StaticProperties`（`tickcart.static.*`）的写法即可，项目里已有这个约定。

### 8.3 为什么一刀切会漏报

同一个「10 件」，对不同商品含义完全不同（数字取自 `V6__seed_products_more.sql`）：

| 商品 | 库存 | 累计销量 | 10 件意味着 |
|---|---|---|---|
| 真无线蓝牙耳机 | 228 | 5,612 | 卖得最快的那批，228 件可能不到一周清空，**但 228 > 10，不告急 → 漏报** |
| 竞速跑步鞋 | 8 | 975 | 抓到 ✓ |
| 一体机电脑 | 144 | 205 | 半年卖不完，永远不告急 |

所以常量只能当「绝对下限兜底」，不能当「补货建议」。真要算得准，安全线应该是 `近 N 天日均销量 × 备货天数`——数据上可行（`t_order` + `order_item` 有下单时间和数量），但要写聚合查询，属于阶段 4 之后的事。

### 8.4 还有个更隐蔽的问题：粒度

`product.stock` 是**汇总字段**（= `sum(product_sku.stock)`）。总库存 120 但某个尺码是 0 的情况真实存在——原型方案 C 里尺码 43 的库存就是 0。

- 按商品级判断 → 「某个尺码断货」被平均值掩盖，用户下单时才发现
- 真正的补货单位是 SKU

所以**商品级字段其实是次优解**：一旦要精细化，字段应该加在 `product_sku` 上，而不是 `product` 上。

### 8.5 建议

取**选项三 + 判定放后端**，不做表结构变更：

1. 阈值来自配置项 `tickcart.stock.warn-threshold`（默认 10），走 `StockProperties`
2. `ProductListItem` / `ProductDetail` 增加一个布尔字段 `stockLow`，由 `ProductService` 判定后下发
3. 前端**不持有阈值**，只渲染 `stockLow`（文案从「低于安全线 10」改成「库存偏低」，不写具体数）
4. SKU 级：抽屉的 SKU tab 里对 `stock === 0` 的 SKU 单独标红——0 是绝对语义，不需要阈值

这样：表结构 0 变更、前端 0 阈值、口径唯一在服务端。将来若要按商品差异化，只需给 `product` 加 `stock_warn_threshold`，Service 里 `COALESCE(p.stock_warn_threshold, 配置值)`，**前端一行都不用改**——升级路径是平滑的。

代价：改阈值要重启后端（`@ConfigurationProperties` 非热更新）。对当前阶段可以接受；真要热更新，后面接一张 `sys_config` 表即可。

> **最终落地时调整了这条**：既然要按分类差异化（见第九节），就顺势给 `product_category` 加了 `stock_warn_threshold`，所以不是「0 表变更」而是「+1 列」。其余结论不变 —— 全局配置仍作兜底，`stockLow` 仍由后端算好下发，前端不持有阈值。

## 九、专题：按「不同类型的商品」配不同阈值

### 9.1 四层粒度，选一层做主、其余留口子

| 粒度 | 配置点数（当前） | 能否运营自助 | 评价 |
|---|---|---|---|
| SKU 级 | 300+ | 否 | 太碎，没人配得动。SKU 只看 `stock = 0`（绝对断货），不进阈值链 |
| 商品级 | 156 | 勉强 | 精准但配不完；存量会全落 `DEFAULT`，等于「开了没配」 |
| **分类级** | **20** | **能** | **性价比最高，已按这层落地** |
| 全局 | 1 | 需重启 | 只当兜底，不能当唯一 |

取值按**最近非空**覆盖，与主流电商后台的库存预警配置一致：

```
商品级（可空，本期未做）→ 分类级（可空）→ 全局配置（默认 10）
```

### 9.2 为什么分类级是最划算的那一层

阈值本质是「**周转速度**」的代理变量，而周转速度主要由品类决定：

| 分类 | 建议阈值 | 理由 |
|---|---|---|
| 食品生鲜 | 30 | 周转快、有保质期，宁可多备 |
| 鞋类 | 8（或按 SKU 算 3） | 尺码分散，总量 20 也可能某个码是 0 |
| 手机数码 | 10 | 客单价高、周转慢，压货成本高 |
| 大家电 | 3 | 单价高、周转极慢，几乎不备货 |

配置点从 156 降到 20（V12 扩到 20 个一级分类），运营会去配；而且「分类管理」页已经存在（`CategoryManageView.vue`），加一列输入框是最自然的落点。

V19 只给三个分类配了种子值（生鲜 30 / 鞋类 8 / 家电 3），其余留 NULL —— 全配等于把「继承」这条链路藏起来，演示时看不出分层效果。

### 9.3 两条落地路径

**路径 A · 落库（推荐）**
```sql
ALTER TABLE `product_category`
  ADD COLUMN `stock_warn_threshold` INT DEFAULT NULL
  COMMENT '库存预警线；NULL 表示继承全局配置' AFTER `status`;
```
NULL 而不是 `DEFAULT 10` 是关键：**NULL = 没配过 = 继承**，`10` = 配过 = 就用 10。用 `DEFAULT 10` 会把「继承」和「恰好等于 10」混成一种状态，以后改全局默认值时，存量分类不会跟着变。

改动面：迁移 1 个 + `Category.java` / `CategorySaveRequest` / `CategoryService.update` 映射 + 分类管理页一列 + `ProductService` 判定 + `ProductListItem.stockLow`，共 **6 处**。

**路径 B · 配置文件映射（0 表变更）**
```yaml
tickcart:
  stock:
    warn-threshold: 10
    category-thresholds:
      1: 10   # 手机数码
      4: 30   # 食品生鲜
      5: 8    # 鞋类
```
`Map<Long, Integer>`，不碰表结构。缺点：运营新增分类要改配置文件 + 重启，**不能自助**。适合「先验证差异化是否真的有用」的过渡期。

### 9.4 三个必须提前处理的坑

1. **分类是树形的**。`product_category` 有 `parent_id` + `level`，现在数据全是 level 1，但字段在。判定要向上找祖先：二级分类没配就找一级，一级没配才落到全局。写成一次递归或「沿 parent_id 上溯」的循环，不要假设只有一层。
2. **分类被整表缓存**。`CategoryService.list(true)` 走 `CacheKeys.categoryListEnabled()`（`category:list:enabled`）。阈值判定**不要**复用它——后台改完分类后，前台缓存可能还没失效，会导致商品列表的红标慢一拍。单独维护一份 `categoryId → threshold` 的轻量映射（分类表极小，全量加载 + 分类变更时刷新）。
3. **改分类会改变告急状态**。商品从「手机数码」移到「食品生鲜」，阈值从 10 变 30，原本不告急的立刻变告急。语义是对的，但要在商品编辑页给一句提示，否则运营会以为是 bug。

### 9.5 更准的做法（阶段 4 之后）

分类级只是**手工近似**。真正准确的是动态安全线：

```
阈值 = max(配置阈值, 近 N 天日均销量 × 备货天数)
```

数据上可行——`t_order` 有 `created_at`，`order_item` 有 `quantity`，按商品聚合即可。这样做的好处是爆款自动抬高安全线（前面那个「库存 228 但一周卖空」的耳机就会自己冒出来），长尾自动降低。配置阈值退化为**绝对下限兜底**，两者并存不冲突。

需要一张按天汇总的销量表或一个定时聚合任务，属于阶段 4 的「数据看板」一起做更划算。

### 9.6 建议的落地顺序

1. **本次**：全局配置项 + 分类级字段（路径 A）+ `stockLow` 由后端下发。前端只渲染，不持阈值。
2. **暂不做**：商品级字段。等真出现「重点商品单独盯」的需求再加——`COALESCE` 里多一层而已，前端零改动。
3. **阶段 4**：动态安全线（日均销量 × 备货天数），与数据看板同批做。

## 十、专题：批量操作怎么落

### 10.1 三种操作性质完全不同，不该一刀切

| 操作 | 幂等 | 有级联 | 可逆 | 现状实现 |
|---|---|---|---|---|
| 批量上/下架 | 是（改同一个 status 值） | 无 | 是（再点一次改回来） | `changeStatus`：1 SELECT + 1 UPDATE + 1 Redis DEL，**无事务** |
| 批量改分类 | 是 | 无（只改 `category_id`） | 是 | 现在只能走 `update` 全量覆盖，**这是坑**（见 10.4） |
| 批量删除 | 否（第二次 404） | 有：`product_sku` + `product_image` | **否**（逻辑删，但用户视角不可逆） | `delete`：`@Transactional`，1 SELECT + 3 DELETE + 1 Redis DEL |

### 10.2 循环发 N 次请求的真实代价（按本项目代码量化）

20 条商品，两种方式对比：

| | 前端循环 20 次 | 批量接口 1 次 |
|---|---|---|
| HTTP 请求 | 20 | 1 |
| SQL 语句 | 60~100 条（每条 1 SELECT + 1~4 写） | 2~4 条（`WHERE id IN (...)`） |
| Redis 失效 | 20 次 DEL | 1 次 pipeline |
| 事务 | **20 个独立事务** | 1 个事务 |
| 失败语义 | 第 13 条失败 → 前 12 条已提交，后 8 条没做 | 全成功或全回滚 |

两个具体的项目级风险：

1. **连接池会被打满**。`application.yml` 里 `hikari.maximum-pool-size: 20`、`connection-timeout: 3000`。如果前端用 `Promise.all` 并发发 20 个请求，正好占满全部连接，任何其他请求（包括商城前台）都要排队，3 秒拿不到连接直接 500。串行发能避开，但 20 × 60ms ≈ 1.2s，且中间失败无法回滚。
2. **半成功状态最难处理**。运营点了「批量下架」，页面提示「部分失败」，但他不知道是哪几条成功了——只能重新刷新逐条核对。而「以为都下架了、实际有 3 个还在卖」是真实会出事的。

顺带澄清一个**不成立**的反对理由：现在 `/api/admin/**` 没有任何限流规则（`application.yml` 的 `rate-limit.rules` 只配了前台 `/api/products`、`/api/search`、`/api/seckill`、`/api/orders`、`/api/payments` 五条），所以循环发 20 个请求**不会**撞 429。但这也意味着一旦以后给 admin 加限流，这套循环实现就会突然坏掉。

### 10.3 接口形态：一个还是三个

**三个独立端点**（更 RESTful）：
```
PUT    /api/admin/products/batch/status?status=0     body: [1,2,3]
PUT    /api/admin/products/batch/category            body: {ids:[...], categoryId: 3}
POST   /api/admin/products/batch/delete              body: [1,2,3]   ← DELETE 带 body 有客户端兼容问题，用 POST
```

**一个端点 + action**（更省）：
```
POST /api/admin/products/batch
{ "action": "STATUS_OFF", "ids": [1,2,3], "status": 0, "categoryId": null }
→ { "successCount": 3, "failed": [] }
```

倾向前者。理由：`action` 字符串本质是 RPC，参数校验（`STATUS_OFF` 要不要 `status`？`CATEGORY` 要不要 `categoryId`？）全靠 Service 里 if-else 兜，而三个端点各自有独立的 DTO 和 `@Valid`，边界清晰。多写两个 `@PutMapping` 的成本远低于日后维护条件分支。

### 10.4 改分类有个坑：不能走 `update`

`ProductService.update` 是**全量覆盖**语义：会重建 SKU（先逻辑删再插）、用 `sumSkuStock` 重算库存、把没传的字段覆盖成 null。如果为了改分类去循环调 `update`，等于把每个商品的 SKU 删了重建一遍——`product_sku.id` 会变，秒杀活动表里存的 `sku_id` 会全部失联。

所以「批量改分类」必须是一个只改 `category_id` 的窄接口：
```sql
UPDATE product SET category_id = ? WHERE id IN (...)
```
这也顺带回答了 10.1 表格里「现状只能走 update」那个坑。

### 10.5 建议

| 操作 | 方案 | 理由 |
|---|---|---|
| 批量上/下架 | **批量接口**（可先不做，用串行循环过渡） | 成本低，且是最高频的批量动作 |
| 批量改分类 | **批量接口，必须** | 走 `update` 会重建 SKU、打断 `sku_id` 引用 |
| 批量删除 | **批量接口，必须** | 有级联、不可逆，必须单事务 |

如果这一版只做一个，做**批量删除**——它是唯一「循环实现会出真事故」的操作。上下架可以先串行循环，但前端必须：

- **串行**（`for await`），不要 `Promise.all`
- 逐条更新进度（「正在处理 7/20」）
- 单条失败不中断，收集失败清单，最后一次性展示
- **完成后只刷新一次列表**，不要每条都 `load()`

> **最终落地**：三个接口都做了（不是只做删除）。理由是「改分类」也必须独立 —— 走 `update` 会重建 SKU 打断 `sku_id` 引用；而「上下架」既然已经有批量端点，就没有理由让前端再维护一套串行循环 + 进度 + 失败清单的代码。

## 十一、专题：「库存告急」筛选放前端还是服务端

### 11.1 先把层次理清：这两件事的成本不是「0 vs 很大」

| 层次 | 内容 | 成本 |
|---|---|---|
| ① 标红 | `ProductListItem` 加 `stockLow` 布尔，前端渲染 | 已包含在第八/九节的方案里 |
| ② 排序 | `sortBy=stock&order=asc`，把最危险的翻到前面 | **1 行**（`applySort` 白名单加 `case "stock"`） |
| ③ 筛选 | `?stockLow=true`，全库范围筛选 + 正确分页与计数 | wrapper 拼接 + 分类阈值分组，中等 |

所以「前端标红」本身**也不是 0 后端改动**——它需要 `stockLow` 由后端下发。真正的增量只在于 ②③。

### 11.2 只在前端标红，有一个硬缺陷：分页

- 第 3 页的告急商品**永远看不到**。156 个商品、每页 12 条，运营得翻 13 页找那 3 个红标。
- chip 上的数字只能是「本页 3 个」，翻到第 2 页可能变成「本页 1 个」，用户会当成 bug。
- 一旦要做「补货待办」（按告急程度排个序，今天该补哪些），前端标红完全给不出来。

### 11.3 服务端筛选的真实成本：阈值差异化把它变复杂了

如果阈值是全局常量，筛选就是一行：

```java
wrapper.lt(cond, Product::getStock, warnThreshold);
```

但第九节定了**按分类差异化**之后，`stock < N` 就写不成了，语义变成「`stock` 小于该商品所属分类的有效阈值」。三种写法：

**写法 1 · JOIN 分类表**
```sql
SELECT p.* FROM product p
LEFT JOIN product_category c ON c.id = p.category_id
WHERE p.deleted = 0 AND p.stock < COALESCE(c.stock_warn_threshold, #{global})
```
问题：本项目**没有 Mapper XML**（`mapper-locations` 配了但 `resources/mapper/` 是空目录，全是 MP wrapper），JOIN 只能用 `apply()` 塞裸 SQL 片段，和现有风格不一致；而且树形分类继承要在 SQL 里做多级 self-join，很难读。

**写法 2 · Service 里按阈值分组，拼 OR 分支**（推荐，如果真要做）
```java
// 先算出 Map<categoryId, 有效阈值>（继承链已在 Java 里解析好）
wrapper.and(w -> w
    .or(x -> x.in(Product::getCategoryId, idsAt10).lt(Product::getStock, 10))
    .or(x -> x.in(Product::getCategoryId, idsAt30).lt(Product::getStock, 30))
    .or(x -> x.notIn(Product::getCategoryId, allConfigured).lt(Product::getStock, global)));
```
关键洞察：**阈值的取值种类很少**（一般 3~5 种），所以 OR 分支也就 3~5 个，不会爆炸。分页和 `count` 仍然正确，因为这只是 WHERE 条件。

**写法 3 · 把有效阈值物化到 `product` 表**
分类改阈值时批量回填。查询变成一行 `stock < stock_warn_threshold`，但要多维护一份冗余数据和一致性，得不偿失。

### 11.4 更划算的第三条路：把它做成「补货待办」而不是列表筛选

真正需要「全部告急清单」的场景，是运营早上打开后台问「今天该补什么货」。这个场景的需求和商品列表**根本不一样**：

| | 商品列表 | 补货待办 |
|---|---|---|
| 分页 | 需要 | 不需要（一次看全） |
| 列 | 7 列（名称/分类/价格/库存/销量/状态/操作） | 只要 图/名/分类/库存/阈值/近 7 天销量 |
| 排序 | 用户选 | 固定按「缺口比例」降序 |
| 动作 | 编辑/上下架/删除 | 改库存 / 加入采购单 |

所以它应该是**一个独立接口**，而不是列表上的一个参数：

```
GET /api/admin/products/low-stock?limit=50
→ [{ id, name, mainImage, categoryName, stock, threshold, sales7d }]
```

比 `?stockLow=true` 更小（不碰列表分页逻辑）、更聚焦（返回的就是待办），而且天然是服务端算的。

### 11.5 建议

1. **本次**：只做 ①标红（`stockLow` 由后端下发）。156 条商品里 3 条告急，标红 + 行左红条已经够用，不必为它加筛选。
2. **救急预案**：如果告急数涨到 20 条以上，先花 1 行加 `case "stock"` 排序（把最危险的翻到前面），成本极低。注意 `ProductController`（前台）复用同一个 `ProductQuery`，等于把库存排序暴露给商城端——竞品可借此推断动销，所以要加个 `adminOnly` 开关或只给后台单独放行。
3. **阶段 4**：做独立的 `GET /api/admin/products/low-stock`，作为「补货待办」的一部分，和动态安全线（9.5）一起上。
