## 一、先看事实（都实测过）

| 事实 | 数据 | 影响 |
|---|---|---|
| 活动总量 | **3 场**（#17 / #27 / #28） | 数据量极小，但三场全是「测试」类标题，看不出运营意图 |
| 状态分布 | 已结束 **3** / 进行中 **0** / 即将开始 **0** / 已下线 **0** | 后台表格三行全灰 |
| `enabled` | **3 场全部 = 1（上线）** | 已结束还挂着上线 → 「上线中」这个筛选维度失去意义 |
| 前台可见活动 | **0 场**（实测 `GET /api/seckill/activities` 返回 `[]`） | **现在打开商城「秒杀」页签是空的**，但后台看不出来 |
| 成交 | **1 单 / ¥20.00 / 售出 1 件** | 三场活动整体售出率 **1%**（1/120 件） |
| 单场表现 | #17 卖 1/100（1%）；#27 0/10；#28 0/10 | 没有进度条，`1 / 100` 这行字看不出「几乎没卖动」 |
| 创建时机 | **3 场全部是「创建时活动已开始」**（#17 晚 19 小时、#27 晚 15 小时、#28 晚 21 小时） | 建完立刻进入「已开始」，而「已开始不能改价改库存」—— 想改价当场被 409 挡住 |
| 库存口径 | #17 秒杀库存 **100**，但对应 SKU 库存只有 **80** | 秒杀库存独立于 SKU 是设计如此，但界面上没有任何提示，看起来像超卖 |
| 在售商品 | **162 个**，且 **162 个全部有 SKU**（共 383 个 SKU） | 「规格」不是可选项，是必填项 |
| 商品下拉 | 一次拉 `size=200`，无远程搜索 | 现在 162 个刚好不漏；商品涨到 200+ 就开始静默漏数据 |
| Redis | 只有 `seckill:bought:17:3`，**没有 stock / activity key** | 活动全结束，key 到期正常；但后台看不出「有没有预热」 |
| 后台接口 | **6 个**：列表 / 详情 / 新建 / 编辑 / 上下线 / 删除 | 没有概览、没有排序、没有时间筛选、没有批量、没有复制 |

## 二、现状诊断

| # | 问题 | 说明 |
|---|---|---|
| 1 | **前台已经是空的，后台看不出来** | 3 场活动全部过期且 `enabled=1`。页面没有任何一处告诉你「商城秒杀页现在 0 个活动」 |
| 2 | **没有 KPI、没有状态分布** | 只有状态下拉，得点开才知道「进行中 0 / 已结束 3」；运营每天第一眼想知道「今天有没有场」 |
| 3 | **卖得怎么样完全看不出来** | 只有 `0 / 10`「剩 10」这种文本；没有进度条、没有成交额、没有售出率。三场活动一共卖了 1 件，界面上像卖得不错 |
| 4 | **没有相对时间** | `2026-10-19 00:00 ~ 2026-10-22 00:00` 要心算才知道「结束 4 天了」；进行中的活动也看不出「还剩 2 小时」 |
| 5 | **「已结束但仍上线」这个脏状态不可见** | 状态 tag 只显示「已结束」，`enabled` 只体现在操作按钮的文字上（显示「下线」，说明它还是上线状态）—— 反着读才知道 |
| 6 | ★**「下线」按钮对已结束活动没有实际意义** | 前台 `listActive` 已按 `end_time > now` 过滤，已结束的活动本来就不展示；下线只是把 `enabled` 改成 0，属于「整理数据」而非运营动作 |
| 7 | ★**已结束的活动永远改不了价和库存** | `SeckillActivityStatus.isStarted()` 把「已结束」也算已开始，实测改价 → `409 活动已开始，不能修改秒杀价`；删除又有 `409 已有成交记录`。**旧活动既不能改、也不能删、又没有复制** → 复用只能手填一遍 |
| 8 | ★**同规格时间重叠不校验** | 实测同一 SKU 建两场重叠活动（2027-01-01 10:00–12:00 与 11:00–13:00）**都成功**。前台会同时出现两个同商品秒杀，库存两套账，用户不知道抢哪个 |
| 9 | ★**新建即上线 + 立即预热** | 实测新建一场 2027 年的活动，保存后**立刻出现在前台**并写入了 Redis `stock/activity` key。日期填错一次就暴露一次 |
| 10 | ★**商品下拉初始显示「0」** | `form.productId` 初值 0，`el-select` 没有匹配 option 时直接渲染成「0」（见 `seckill-manage-before-dialog.png`） |
| 11 | **「规格」被写成可选项** | 表单提示「不选表示按商品级」，但前台**不让用户选规格**（`confirming.specValue \|\| '无规格'`）。不选就建出「无规格」订单，而 162 个在售商品全部有 SKU |
| 12 | **秒杀价没有原价参照** | 只在 hint 里写「必须低于商品原价」，管理员得切到商品页查原价；规格价与商品价还不同（#17：商品 ¥39.90、规格 ¥68.00） |
| 13 | **没有库存对账** | `remainingStock` 已被 Redis 覆盖，但「DB 已售」「Redis 剩余」「支付成功单数」三个口径没有并列展示，对不上时无从发现 |
| 14 | **搜索只搜标题** | 想找「牛油果那场」得知道标题叫「测试」；搜不到商品名 |
| 15 | **没有排序、没有时间筛选、每页写死 10 条** | 列表 `orderByDesc(id)` 固定；活动多了以后「本周的场」只能一页页翻 |
| 16 | **没有批量操作** | 3 场活动要下线 3 次；将来 20 场就是 20 次 |

**一句话总结**：这个页面的真实任务是**「建活动 → 盯盘 → 收尾复用」**，而旧实现只做了「建 + 删」，把运行态（卖了多少、还剩多久、是不是已经过期了）全部留白 —— 结果 3 场活动全部过期、前台空了，后台看起来一切正常。

## 三、三个方案

### 方案 A · 活动工作台（`#a`，推荐）

保留表格（管理员的肌肉记忆），把力气花在「运行态」和「建活动」上：

**① 顶部告警条**：`3 场活动已结束但仍处于「上线」状态` + 「一键下线已结束的 N 场」
> 这条是真实数据的直接产物：现在就有 3 场。它把「后台看不见的脏状态」变成一条可执行的动作。

**② 三张 KPI**
- 进行中 **0** · 当前没有正在抢的活动（有活动时显示「#17 精选牛油果 · 还剩 2 小时」红字）
- 即将开始 **0** · 没有排期，下一场：—
- 累计成交 **¥20.00** · 1 单 · 售出 1 件 · 整体售出率 **1.0%**

> ★ 同样**不写「今日 N 场」**：演示数据停在 10-22，任何「今日」指标都会是 0。

**③ 状态 chips**：`全部 3 / 进行中 0 / 即将开始 0 / 已结束 3 / 已下线 0`，计数来自新接口。

**④ 表格 8 列（原来也是 8 列，但内容全换）**

| 列 | 内容 | 变化 |
|---|---|---|
| 活动 | 缩略图 + 标题 + `#ID · 限购 N` | 限购从独立列并进来 |
| 商品 / 规格 | 商品名 + 规格 chip + SKU ID | **规格缺失标红「未配规格」** |
| 时间 | `10-19 00:00 → 10-22 00:00` + **相对时间**（进行中红字「还剩 2 小时」/ 即将开始橙字「2 小时后开抢」/ 已结束灰字「已结束 4 天」） | 新增相对时间 |
| 价格 | 秒杀价 + `-71%` 标 + 原价划线 | 新增折扣 |
| 进度 | 进度条 + `1 / 100` + `1%`（售罄变绿） | 新增进度条 |
| 成交 | `¥20.00` + `1 单` | 新增 |
| 状态 | tag + **「仍为上线」灰字** | 新增 |
| 操作 | 详情 / 下线 / ⋯（复制、删除） | 新增详情与复制 |

砍掉：独立的「限购」列（配置项不是运行态，下沉到抽屉）、「ID」列（并进活动列）。

**⑤ 新建/编辑抽屉 760px（替代 620px 弹窗）**
- **① 选商品**：带缩略图的商品列表 + 搜索（替代 162 项无图下拉），选中后显示商品价
- **② 选规格**：规格 chip 单选，**显示该规格的价格与库存**；明确提示「前台不让用户选规格，抢到的就是这里配的」
- **③ 定价与库存**：秒杀价旁边**实时算**「省 ¥48.00（2.9 折）」；库存旁提示「规格库存 80 件，秒杀单独备货可超」
- **④ 排期**：快捷模板（今晚 20:00–22:00 / 明天 10:00–12:00 / 周末全天）+ 自定义；**时间重叠时黄条提示「与 #32 撞车」**
- **右侧常驻「前台预览」**：缩略图 + 标题 + 秒杀价/原价 + 进度条 + 倒计时，改一个字实时变 —— 不用保存后再去商城确认
- 底部两个按钮：**保存为下线** / **保存并上线**（对应决策 2）

**⑥ 活动详情抽屉 660px**
- 库存对账：配置总库存 / DB 已售 / **Redis 剩余（未预热会红字标出）** / DB 推算剩余 / 支付成功订单
- 成交订单列表（直接看到 `SK202610212240309441278`，可跳订单页）
- 时间线：创建 → 开始 → 结束 → 下线收尾（未执行时灰掉）
- 底部：复制为新活动 / 下线 / 编辑

**成本**：前端 1 文件重写（约 900 行）；后端 **+1 概览接口、VO +3 字段、查询 +排序/时间范围、+1 复制接口、+1 批量下线接口、重叠校验**（详见 5.1）。

### 方案 B · 排期时间轴（`#b`）

按天铺一条横轴（10-19 ~ 10-26，一天一格），每个活动一行，色块长度 = 时长。顶部图例区分「已结束 / 进行中 / 撞车」，右上角标「今天」。

**优点**：**撞车和空档一眼看出**。真实数据下它立刻暴露两件事：10-23 之后整条轴是空的（前台确实没活动）、10-21 加一场会跟 #17 撞上。
**缺点**：已结束的 3 场只能折叠到下面；搜索、编辑、批量下线没有自然位置；跨天活动（#17 跨 3 天）色块只能按天比例画，精确到小时的场次（20:00–22:00）宽度不足 1%，几乎点不中。

### 方案 C · 活动卡片墙（`#c`）

一场活动一张卡：封面图 + 状态角标 + 倒计时 + 进度环 + 秒杀价/原价 + 三个按钮，右下角一张虚线「+ 新建活动」。

**优点**：视觉最强，3 张卡一屏看完，适合大促作战室投屏；封面图能立刻认出是哪个商品。
**缺点**：**信息密度只有表格一行的一半**，20 场就要滚三屏；没有排序/筛选/批量；「已结束 6 天」这种相对时间在卡片上占地方。**当前 3 场时好看，但它不是能长大的界面。**

## 四、对比与推荐

| 维度 | A · 活动工作台 | B · 排期时间轴 | C · 活动卡片墙 |
|---|---|---|---|
| 建活动效率 | **抽屉四步 + 前台预览 + 撞车提示** | 色块上点空白建，但没法填表单 | 卡片按钮进入同一个弹窗 |
| 盯盘（卖了多少 / 还剩多久） | **进度条 + 相对时间 + 成交额** | 只看得到时间，看不到销量 | **进度环最直观** |
| 收尾复用（复制 / 下线） | **操作列 + 批量下线** | 无处安放 | 每卡三个按钮，但 20 场要滚 |
| 撞车可见性 | 表单里黄条提示 | **整轴最直观** | 完全看不出 |
| 空档可见性 | 靠「即将开始 0」 | **一眼看到 10-23 之后全空** | 靠数卡片 |
| 已结束活动安放 | **一个 chip 筛出来** | 折叠区，位置尴尬 | 混在卡片墙里 |
| 活动 50 场时 | **分页 + 筛选，稳** | 50 行时间轴，滚不完 | 崩 |
| 后端改动 | +1 概览 / +2 写接口 / VO+3 / 查询参数 | 同 A（还需要按天聚合） | **0 改动**（现有 6 个接口够） |

**推荐 A。** 理由：
1. 当前最痛的三个问题 —— **前台空了后台不知道（①）、卖得怎么样看不出（③）、旧活动没法复用（⑦）** —— 只有 A 同时解决：告警条 + 进度/相对时间 + 复制。
2. B 的撞车可见性确实强，但它是「排期」这一个场景的最优解；而 A 只需要在**新建表单里加一条黄条**就能覆盖 90% 的撞车风险（成本 ≈ 30 行），不必为它换掉整个页面。
3. C 在 3 场活动时最好看，但它把「扫描效率」换成了「视觉冲击」，活动一多就崩 —— 后台页面首先要能长大。

## 五、落地拆解（未实施）

### 5.1 后端改动（全部是加法）

**① `GET /api/admin/seckill/overview`** → `SeckillOverviewVO`

```json
{
  "total": 3,
  "ongoing": 0, "pending": 0, "ended": 3, "disabled": 0,
  "paidAmount": 20.00, "paidOrderCount": 1, "soldQuantity": 1,
  "nextStartTime": null, "ongoingEndTime": null,
  "endedButEnabled": 3
}
```

实现：**两条 SQL**
```sql
-- 状态计数：一次查回 (enabled, start_time, end_time)，Java 里按 SeckillActivityStatus 摊平
SELECT enabled, start_time, end_time FROM seckill_activity
-- 成交：秒杀订单只算已支付
SELECT COUNT(*) cnt, SUM(pay_amount) amt
FROM t_order WHERE activity_id > 0 AND status IN (1,2,3)
-- 已售件数：直接求和活动表的 sold_count
SELECT SUM(sold_count) FROM seckill_activity
```
★ **件数不要从 `t_order` 算**：订单主表没有 `total_quantity` 字段（件数在 `order_item` 里），而且 `sold_count` 才是与前台进度条同一个口径。
★ **不要写 5 次 `count(*)`**；活动量在百级，全量查回内存分类比 5 条聚合 SQL 更简单也更准（状态是推导的，SQL 里拼时间条件容易和 `SeckillActivityStatus.of` 的口径漂移）。
★ **成交只算 `status IN (1,2,3)`**（待发货/待收货/已完成）。待付款不算成交；已取消/已超时的 `pay_amount` 不计入。

**② `SeckillActivityVO` 补 3 个字段**：`paidAmount`、`paidOrderCount`、`preloaded`（Redis 库存 key 是否存在）。

```sql
-- 列表页一次 GROUP BY 拿全页成交，避免 N+1
SELECT activity_id, COUNT(*) cnt, SUM(pay_amount) amt
FROM t_order WHERE activity_id IN (...) AND status IN (1,2,3) GROUP BY activity_id
```
★ `preloaded` 走 `SeckillStockService.currentStock(id) != null`，**不要新增 Redis 调用**（列表已调过一次 `overrideRemainingFromRedis`，把结果复用即可）。

**③ `SeckillActivityQuery` 补 4 个参数**：`sortBy`（`startTime` / `endTime` / `id`）、`order`、`beginDate` / `endDate`（`LocalDate` + `@DateTimeFormat(ISO.DATE)`），`keyword` 扩到**商品名**。

★ 排序**白名单映射**，未知字段回落 `startTime desc`，末尾补 `id` 兜底防翻页重复（同订单页 `applyAdminSort` 的写法）。
★ 搜商品名不要 `inSql` 拼字符串：`apply("product_id IN (SELECT id FROM product WHERE name LIKE {0})", "%" + kw + "%")`，`{0}` 走参数绑定。
★ 日期范围闭区间：`>= beginDate 00:00` 且 `< endDate+1 00:00`。

**④ `POST /api/admin/seckill/activities/{id}/copy`** → 新活动 id

复制规则：标题加「副本」后缀（截断到 64 字符）、`seckill_price / seckill_stock / limit_per_user / product_id / sku_id` 全复制、`sold_count = 0`、**`enabled = 0`（草稿）**、时间整体平移到**「原结束时间之后的第一天同一时段」**（`newStart = oldEnd + 1 天`，时长不变）。

> ★ 为什么不是「明天同一时段」：原活动如果是 10-19~10-22 这种跨天场，平移一天仍与原活动重叠，会被新加的重叠校验直接 409 —— 复制出来的东西自己撞自己。
★ **不能复用 `create()`**：它会 `validatePrice`（原价可能已变）、默认 `enabled=1`、并立即 `preload`。复制出来应该是草稿，等运营改完时间再上线。
★ `sold_count` 必须显式置 0 —— 直接 `BeanUtils.copyProperties` 会把已售数带过去，导致新活动一开始就是「已售 1/100」。

**⑤ `PUT /api/admin/seckill/activities/batch/enabled?enabled=0`** body 是 id 数组

语义与商品批量一致：**id 必须全部存在，不做半成功**，重复先去重，上限 100。
★ 下线要逐条 `refreshSnapshot`（同 `changeEnabled` 的 `syncCacheAfterCommit`），不能只改 DB：抢购接口是**读 Redis 快照判状态**的（`SeckillBuyService.buy` 第 58~71 行），快照不刷新，用户在下线后的 TTL 内仍能抢到。★ 注意下线**不清库存 key**，只把快照里的 `enabled` 改成 0 —— 这是刻意的，避免「下线再上线」时把已扣未建单的库存还回去。

**⑥ 重叠校验（create / update 内）**

```java
// 同一 skuId（含 0）且 enabled=1，时间区间相交
SELECT COUNT(*) FROM seckill_activity
WHERE id <> #{selfId} AND enabled = 1 AND sku_id = #{skuId}
  AND start_time < #{endTime} AND end_time > #{startTime}
```
命中 → `409 该规格在 xx~xx 已有一场活动（#32），请调整时间或先下线那场`。
★ **只校验 `enabled=1`**：已下线的草稿允许重叠，否则「先建草稿排期」这个流程走不通。
★ 区间相交用**严格不等号**：`[start, end)` 相邻（前一场 22:00 结束、后一场 22:00 开始）不算重叠。

## 六、口径与坑

1. ★★**「已售」有两个口径，别混用**：`sold_count` 是**建单即累加**（含待付款，取消时 `restore` 会减回去），「支付成功单数」才是真成交。列表进度条用 `sold_count`（与前台进度条一致），KPI 成交额用 `status IN (1,2,3)`。
2. ★**`remainingStock` 已经是 Redis 口径**（`overrideRemainingFromRedis`），不要在列表里再拿 `seckill_stock - sold_count` 算一遍 —— 高峰期两者会差几十。
3. ★**已结束的活动 `preloaded` 一定是 false**：`preload()` 对 `ttlOf == null`（已结束）直接 `return`，只刷快照不建库存 key。详情抽屉里这条要显示「活动已结束，Redis 已释放」而不是红字「未预热」，否则每天都会误报。
4. ★★**新建默认上线是现在最危险的默认值**：实测一场 2027 年的活动保存后立刻进了前台。改成默认下线后，`create` 里的 `preload` 也要跟着改条件（只有 `enabled=1` 才预热）。
5. ★**编辑已结束活动的 409 文案要改**：现在报「活动已开始，不能修改秒杀价」，但用户改的是一场 4 天前就结束的活动，这句提示会让人以为系统坏了。建议区分「进行中」与「已结束」两种情况（已结束 → 引导「复制为新活动」）。
6. ★**秒杀库存可以大于 SKU 库存**（#17：活动 100 / SKU 80），这是设计如此（秒杀单独备货）。表单里必须写明，否则每个新来的运营都会问「是不是超卖了」。
7. ★**`sku_id = 0` 的活动会建出「无规格」订单**（`buildSeckillItem` 里 `specValue = null`）。本项目 162 个在售商品全部有 SKU，所以规格应设为必填。
8. ★**复制活动不能复制 `sold_count` 与 `enabled`**（见 5.1 ④）。
9. ★**批量下线要逐条刷新 Redis 快照**：抢购接口读的是快照不是 DB，快照不刷新就会「后台已下线、用户仍能抢」。库存 key 刻意不清（见 5.1 ⑤）。
10. ★**概览别绑「今日」**：数据停在 10-22，今日指标全是 0。
11. ★**分页加 `sizes` 要同时重置页码**，否则第 5 页切成 50 条/页会落在空页。
12. ★★**已结束的活动可以靠「改时间」复活**：`update` 只在 `status.isStarted()` 时校验价格与库存，**时间不校验** —— 把 `end_time` 改到未来，一场卖过 1 件的活动就变回「进行中」，`sold_count` 还是 1。这不是 bug（运营确实可能想续场），但**必须在编辑抽屉里显式提示「改时间会让活动重新生效」**，否则改个日期就把活动放回前台了。

## 八、明确不做（本轮）

| 不做 | 原因 |
|---|---|
| 导出活动报表 | 3 场活动没有导出价值；真要做应和数据看板同批 |

| 秒杀实时大屏 | 阶段 4 之后，需要 WebSocket 推送 |
