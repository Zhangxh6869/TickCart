# A2 · 商品/分类/详情缓存设计

> 对应阶段：**3A / A2**（缺口 P0-3、P1-6 热搜部分）
> 状态：**已实施并验证（2026-10-18）**
> 前置阅读：`TickCart项目阶段划分.md`「阶段 3 前置 · 高并发能力补齐（3A）」

---

## 1. 现状与目标

**现状**：Redis 全项目只服务 4 处 auth（验证码 / 登录频控 / 短信频控 / token 吊销），
业务侧**零缓存**。一次商品详情 = 4 条 SQL：

| SQL | 表 |
|---|---|
| 1 | `product` |
| 2 | `product_sku`（按 product_id） |
| 3 | `product_image`（按 product_id） |
| 4 | `category`（按 category_id） |

分类列表每次 `selectList`；热搜词每次 `GROUP BY search_log`。

**目标**：把「读多写少」的三类数据挡在 DB 前面，并保证后台改动能**立即**反映到前台。

---

## 2. 范围：做什么、不做什么

| 数据 | 做不做 | 理由 |
|---|---|---|
| 商品详情 `detail(id)` | **做** | 4 条 SQL → 1 次 Redis；单 key、失效简单 |
| 分类列表 `list(true)` | **做** | 全量小表，一个 key 就能装下；改分类时整体失效 |
| 热搜词 `hotWords(limit)` | **做** | 每次 `GROUP BY` 全表聚合，且 5 分钟内变化无感 |
| **商品列表分页** | **不做** | key 基数 = 分类 × 排序 × 页码 × seed，几乎命中不了；失效面又覆盖全站。见 §9 |
| 相关搜索词 `relatedWords` | **不做** | key 依赖用户输入的任意关键词，基数无上界 |
| 购物车 / 订单 / 用户 | **不做** | 强一致要求，缓存收益低、风险高 |

---

## 3. 为什么不用 `@Cacheable`

Spring Cache 注解看起来省事，但三件事它做不了：

1. **批量/精确失效**：后台改分类要让整个分类列表失效、改商品要按 id 失效，注解只能按方法参数拼 key。
2. **事务提交后失效**：`@CacheEvict` 在方法返回时执行，此时事务可能还没提交 —— 并发读会把旧值写回缓存（§7.2 的经典坑）。
3. **降级**：Redis 故障时 `@Cacheable` 默认让异常冒泡 → 整个详情页 500。我们要的是「缓存挂了就回源」。

所以：**手写一个 `CacheService`**，用 `StringRedisTemplate` + Jackson JSON。
不引入 `spring-boot-starter-cache`，不引入 Caffeine（本地 L1 留到需要时再说）。

---

## 4. Key 设计与 TTL

| Key | 内容 | TTL | 抖动 |
|---|---|---|---|
| `cache:product:detail:{id}` | `ProductDetail` 的 JSON | 60s | ±10% |
| `cache:product:detail:null:{id}` | 空值标记（防穿透） | 60s | — |
| `cache:category:list:enabled` | 启用分类数组 JSON | 30min | ±10% |
| `cache:search:hot:{limit}` | 热搜词数组 JSON | 5min | ±10% |

约定：
- 统一前缀 `cache:`，与 auth 的 `auth:*` / `sms:*` 区分，便于按前缀排查与清理。
- **TTL 一律加 ±10% 随机抖动**，避免同一时刻批量过期造成雪崩。
- 所有 TTL 进 `application.yml`，不硬编码（AGENTS.md 4.3）。

## 5. 读路径

```
CacheService.getOrLoad(key, ttl, type, loader)
  ├─ GET key → 命中 → 反序列化返回
  ├─ 命中空值标记 → 直接返回 null（不打 DB）
  └─ 未命中：
       ├─ SETNX cache:lock:{key} 1 EX 3s   ← 击穿保护，只放一个线程回源
       │    ├─ 抢到锁 → loader() → SET key → 释放锁
       │    └─ 没抢到 → 等 50ms 重试 GET，最多 3 次（150ms）
       │              └─ 仍没有 → 直接 loader() 回源（降级，不阻塞用户）
       └─ loader 返回 null → SET 空值标记 60s
```

三个细节：

- **空值缓存**：`GET /api/products/999999` 这种请求不打 DB 也不穿透。用独立 key（`detail:null:{id}`）而不是存字符串 `"null"`，避免与真实数据混淆。
- **击穿保护用 SETNX 短锁**，不用 Redisson：这里只需要「同一 key 同时只一个线程回源」，不需要看门狗与可重入。Redisson 留给 B2 秒杀兜底锁。
- **降级优先于等待**：重试 150ms 还拿不到就直接回源。宁可多打一次 DB，也不能让用户等。

### 5.1 序列化：必须用「字段可见」的专用 ObjectMapper

`ProductDetail` 只有 `categoryName` 一个 setter（其余字段在 `from()` 里直接赋值、对外靠 getter 序列化）。
Jackson 默认**能序列化、不能反序列化** —— 直接用全局 ObjectMapper 会抛
`Cannot construct instance ... no Creators, like default constructor, exist`。

做法：`CacheService` 内部持有一个**专用** ObjectMapper：

```java
ObjectMapper cacheMapper = springObjectMapper.copy()
        .setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.NONE)
        .setVisibility(PropertyAccessor.FIELD, JsonAutoDetect.Visibility.ANY);
```

- 只影响缓存读写，不改变 HTTP 响应的 JSON 结构（HTTP 层仍走 getter）。
- `ALL → NONE` + `FIELD → ANY` 让字段名成为唯一来源，避免 getter/field 两套规则打架。
- 反序列化出的对象没有 setter 也没关系 —— Jackson 直接写字段。

> 备选：给 VO 补 setter。但那是为了迁就缓存而改业务对象，不如让缓存的序列化器自己适配。

## 6. 失效策略（Cache-Aside）

### 6.1 写操作 → 删缓存矩阵

| 写操作 | 删除的 key | 位置 |
|---|---|---|
| 后台新增商品 | 无（新 id 无缓存） | — |
| 后台编辑商品 `update` | `cache:product:detail:{id}` | `ProductService.update` |
| 上下架 `changeStatus` | `cache:product:detail:{id}` | `ProductService.changeStatus` |
| 删除商品 `delete` | `cache:product:detail:{id}` | `ProductService.delete` |
| 改 SKU 库存 `updateSkuStock` | `cache:product:detail:{id}` | `ProductService.updateSkuStock` |
| 分类增 / 改 / 删 | `cache:category:list:enabled` | `CategoryService` |
| **下单扣库存 / 取消回补 / 退款回补** | **不删** —— 库存已不在缓存里（见 §8 决策变更） | — |
| 搜索日志写入 | 不删（热搜 5min 自然过期） | — |

### 6.2 必须「事务提交后」才删

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override public void afterCommit() { cacheService.evict(key); }
    });
```

**为什么**：如果在事务内删，另一个读请求可能在提交前读到**旧** DB 值并写回缓存 ——
之后缓存里就一直是旧值，直到 TTL 到期。这个窗口只有几毫秒，但一旦命中就是长期脏读。
「延迟双删」是另一种解法，但它靠睡眠猜时间，不如 `afterCommit` 确定。

### 6.3 删除失败不能影响业务

`evict` 内部 catch 所有异常并打 WARN：Redis 挂了，后台照样能改商品，只是缓存靠 TTL 自愈。

## 7. 后台读取要绕开缓存

`AdminProductController.detail` 复用 `productService.detail(id)`，会命中 60s 缓存 ——
后台点「编辑」时可能拿到旧数据，保存后覆盖掉别人刚改的字段。

处理：新增 `ProductService.detailFresh(id)` 直查 DB，后台详情接口改用它。
前台详情仍走缓存版本。

## 8. 核心取舍：详情里的库存要不要缓存？

详情 VO 含 `stock`，而**下单会扣库存**。如果扣完不失效缓存，详情页会显示旧库存。

| 方案 | 缓存收益 | 库存准确性 | 写操作影响 |
|---|---|---|---|
| A. 整体缓存 60s，扣减不失效 | 4 条 SQL → 0 | 最多陈旧 60s | 无 |
| **B. 静态部分缓存，库存实时查**（2026-10-30 起采用） | 4 条 → 1 | 永远准 | 无 |
| C. 整体缓存，扣库存时删 | 4 条 → 0 | 准 | **高频下单时缓存几乎全失效** |

### 8.1 变更记录：2026-10-18 选 A，2026-10-30 改 B

当初选 A 的理由是「详情页的库存只是参考值，权威校验在下单的条件 UPDATE」。这个判断**漏了一层**：
详情页不是纯展示 —— `ProductDetailView` 拿 `stock` 决定规格卡是否禁用、默认选中哪个规格、
底部「加入购物车 / 立即购买」是否可点。于是 60s 的陈旧会变成两种**可见故障**：

- 卖完之后 60s 内仍显示「库存 5」，按钮可点，点了才失败；
- **退款回补后 60s 内仍显示「已售罄」，按钮是灰的 —— 刚退回来的货卖不出去**。

A 仍然不会导致超卖（权威校验在下单的条件 UPDATE），所以这是「体验」而非「正确性」问题。
但退款上线后第二种故障特别刺眼：用户刚收到退款，回头发现商品售罄。

### 8.2 实现（`ProductService`）

- 要进缓存的那一份由 `withoutStock()` 产出：`stock` 与 `skus[].stock` 一律置 0 占位；
- 每次 `detail()` 读到后由 `applyFreshStock()` 现读覆盖：有规格读 `product_sku.stock`
  （一条只取 id / stock 的查询），无规格读 `product.stock`；商品汇总按 SKU 合计重算；
- **置 0 而不是保留原值**：万一覆盖逻辑失效，页面显示「售罄」而不是「有货」——
  失败方向要安全，不能让人点了下单才发现没货；
- 老缓存自然兼容：反序列化出来的库存不管是多少，都会被现读值覆盖，不需要升 key 版本。

### 8.3 代价与边界

- 每次详情多 1 条 SQL（只取库存一列，走主键/索引），缓存命中不再等于 0 条；
- **销量仍走缓存**：它同样会变（退款回退销量），但不影响「能不能买」，所以 TTL 仍保持 60s；
  若将来把销量也移出缓存，TTL 可以延长到 10~30 分钟；
- 秒杀不走这条路径（Redis 与 `sku.stock` 两套账）。

> 顺带消掉一类缺陷：库存不再需要「每条写路径都记得失效缓存」。
> `InventoryService` 的扣减/回补从来就没失效过详情缓存 —— 在 A 方案下这是个 bug，
> 在 B 方案下无关紧要。**结构正确比记得调用可靠。**

### 8.4 实测（2026-10-30）

```
GET /api/products/302                  → stock=189, skus=[(490,109),(491,80)]
Redis cache:product:detail:302         → stock=0,   skus=[(490,0),(491,0)]   ← 缓存不带库存
立即买 1 件（buy-now）后立刻再读        → stock=188, skus=[(490,108)]        ← 不再等 60s
取消该订单后立刻再读                    → stock=189, skus=[(490,109)]        ← 回补同样即时
```

改之前：下单后 60s 内读到的仍是 189/109。

## 9. 为什么商品列表不做缓存

- **命中率**：首页走 `?seed=<随机>` 分页（`ProductFeed` 随机流），key 里有 seed，
  每刷新一次就是新 key；再加分类、页码、排序，组合近乎无限。
- **失效面**：任何商品改价/上下架/销量变化都要让列表失效 —— 而销量在**每笔支付成功时**变化，
  等于持续失效。
- **收益比**：详情页是「一个商品被反复看」，列表页是「每次看不同的组合」，缓存价值完全不同。

如果 A4 压测显示列表是瓶颈，再引入「分类维度版本号 + 5s 短 TTL」的方案：
`cache:product:list:{categoryId}:v{version}:{page}`，改商品时 bump 版本号。**本轮不做**。

### 11.1 单元测试

| 用例 | 断言 |
|---|---|
| 首次读 | 调用 loader 一次，写入 Redis |
| 二次读 | **不调用 loader**，直接返回缓存值 |
| 空值缓存 | loader 返回 null → 写空值标记；二次读不再调 loader |

| 总开关关闭 | 每次都调 loader |

```
        后 9 次零 SQL
```

```
后台改价 302 → 立即 GET /api/products/302 → 必须是新价格（不能等 60s）
```

### 11.5 实测结果（2026-10-18 21:25，后端 8080 + MySQL/Redis 容器）

```
清空 cache:* 后连打 10 次 GET /api/products/302
  → 全程只有 4 条 SQL（首次的 product/product_sku/product_image/category），后 9 次零 SQL

2 次 GET /api/products/999999（不存在的 id）
  → 两次都 404，SQL 只有 1 条（第二次命中空值标记，不打 DB）

2 次 GET /api/categories + 2 次 GET /api/search/hot?limit=8
  → 合计 3 条 SQL（分类 1 + 热搜聚合 1 + 无效详情 1）

Redis 中生成的 key：
  cache:product:detail:302
  cache:product:detail:999999:null
  cache:category:list:enabled
  cache:search:hot:8

一致性：后台把 302 价格改成 39.91 → 立即 GET /api/products/302 读到 39.91（afterCommit 失效生效）
```

验证后已把商品 302 恢复原状（价格 39.90、SKU 490/491 有效、库存 118/80）——

## 12. 边界与已知限制

1. ~~详情库存最多陈旧 60s~~ —— **已解决（2026-10-30，§8 改为方案 B）**：库存每次现读。
   仍在缓存里的是**销量**，退款回退后最多陈旧 60s（不影响「能不能买」）。
2. **缓存与 DB 的短暂不一致窗口**：`afterCommit` 删除到删除生效之间（毫秒级），
   极端并发下可能有一次旧值读。TTL 兜底，不做「延迟双删」。
3. **分类列表整表缓存**：分类表很小（十几条），整表缓存比按 id 缓存更省事，代价是改任一分类要全量失效。
4. **热搜词 5 分钟内不反映最新搜索**：这是可接受的（热搜本来就是趋势指标）。
5. **Redis 不可用时的行为**：全部回源 DB，功能不降级、性能降级 —— 这是刻意的。

## 13. 本切片不做

- 商品列表缓存（§9）
- 本地 L1 缓存（Caffeine）—— 单机部署下 Redis 已经够快，多一层要处理两级失效
- 布隆过滤器 —— 空值缓存已能挡住重复的无效 id；布隆留到阶段 5「缓存穿透防护」再讲
- 缓存命中率指标上报（actuator）—— 阶段 4

## 14. 决策记录（2026-10-18 已确认并实施）

| 项 | 决策 | 理由 |
|---|---|---|
| 详情库存 | ~~A：整体缓存 60s~~ → **B：静态缓存 + 库存现读**（2026-10-30 修订） | 详情页用库存决定按钮可点性，退款回补后 60s 内会显示「已售罄」；改为现读后无需在写路径上失效缓存（§8） |
| 详情 TTL | **60s** | 缓存里还有销量（退款会回退），保持短 TTL；库存已现读，不再依赖 TTL |
| 分类 TTL | **30min** | 分类极少变动 |
| 热搜 TTL | **5min** | 依赖搜索日志词频，太短等于没缓存 |
| 商品列表 | **不做缓存** | 命中率极低、失效面覆盖全站（§9） |
| 后台详情 | **走 `detailFresh` 直查 DB** | 避免编辑到 TTL 内的旧数据 |
