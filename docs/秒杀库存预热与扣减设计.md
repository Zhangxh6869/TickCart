## 2. Redis key 设计

统一前缀 `seckill:`（与 `cache:` / `limit:` / `auth:` 区分，便于按前缀排查）。

| Key | 类型 | 内容 | TTL |
|---|---|---|---|
| `seckill:activity:{id}` | String(JSON) | 活动快照：productId/skuId/price/limitPerUser/endTime/status | `end_time + 1h` |
| `seckill:stock:{id}` | String | 剩余库存（**唯一权威**） | 同上 |
| `seckill:bought:{id}:{userId}` | String | 该用户已抢数量 | 同上 |
| `seckill:req:{id}:{userId}` | String | 防重复提交标记（PX 3s） | 3s |
| `seckill:result:{requestId}` | String(JSON) | 抢购结果（**B3 写**，B4 轮询） | 24h |

**为什么 TTL 都是 `end_time + 1h`**：活动结束后 1 小时内仍需处理「取消回补」「用户查结果」，
之后全部自动消失，不需要清理任务。`+1h` 而不是 `+5min`，是为了给超时关单（15 分钟）留余量。

**为什么 meta 也放 Redis**：抢购接口每请求都要校验活动状态与限购数。
若每次都查 DB，秒杀流量会直接把 `seckill_activity` 打穿 —— 预热时把快照写进 Redis，
抢购链路**全程不碰 DB**。

## 3. Lua 原子扣减

三段校验 + 两次扣减必须在同一个脚本里完成，否则并发下会超卖：

```lua
-- KEYS[1] = seckill:stock:{id}
-- KEYS[2] = seckill:bought:{id}:{userId}
-- ARGV[1] = quantity      ARGV[2] = limitPerUser
local qty   = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
  return -1                      -- 未预热 / 已过期
end

local bought = tonumber(redis.call('GET', KEYS[2]) or '0')
if bought + qty > limit then
  return -3                      -- 超过每人限购
end

if stock < qty then
  return -2                      -- 库存不足
end

redis.call('DECRBY', KEYS[1], qty)
redis.call('INCRBY', KEYS[2], qty)
return stock - qty               -- >= 0：成功，返回剩余库存
```

**返回码约定**（应用层据此映射业务异常）：

| 返回值 | 含义 | 接口响应 |
|---|---|---|
| `>= 0` | 成功，值为剩余库存 | 200 + `requestId` |
| `-1` | 未预热 | 503「活动尚未就绪，请稍后重试」 |
| `-2` | 售罄 | 409「已抢光」 |
| `-3` | 超限购 | 409「每人限购 N 件」 |

**为什么先校验限购、再校验库存**：两者都失败时，告诉用户「你买超了」比「卖光了」更准确 ——
前者是用户自己的问题，后者会让人以为还有机会。

## 4. 预热：三处触发，全部用 `SETNX`

```
上线时（changeEnabled → 1）  ─┐
应用启动时（扫 enabled=1 且 end_time>now）─┼→ 同一段 preload(activityId)
每 30s 扫描（start_time 在 30 秒内的）     ─┘
```

预热动作（一个事务/管道内完成）：

```
SET seckill:activity:{id} {metaJson} NX EX {ttl}
SET seckill:stock:{id}    {seckill_stock - sold_count} NX EX {ttl}
```

**为什么用 `NX`（不存在才写）而不是直接覆盖**：

重启时如果活动**已开始**、Redis 里已有扣减，用 DB 的 `stock - sold_count` 覆盖会把
「已扣但还没建单」的那部分**还回去**，直接造成超卖。

- Redis 数据还在（正常重启）→ `NX` 失败 → 保留 Redis 现值，正确。
- Redis 数据丢了（宕机/清库）→ `NX` 成功 → 用 DB 重建，此时 `sold_count` 可能略滞后，
  会有极小的超卖窗口，这是可接受的降级（文档写明）。

**`sold_count` 为什么能作为重建依据**：它是建单成功后原子累加的（B3 实现），
比「Redis 已扣数」保守，宁可少卖不可超卖。

## 5. 抢购接口契约

```
POST /api/seckill/{activityId}/order
Body: { "quantity": 1 }
Header: Authorization（必须登录）
```

处理流程（**全程不查 DB**）：

```
1. 读 seckill:activity:{id}（meta）
   ├─ 不存在        → 503「活动尚未就绪」
   ├─ status != 进行中 → 409「活动未开始/已结束」
   └─ quantity > limitPerUser → 409（提前挡，省一次 Lua）
2. SET seckill:req:{id}:{userId} {requestId} NX PX 3000
   └─ 失败 → 429「请求过于频繁，请稍后重试」（防连点/脚本）
3. 执行 Lua（§3）
   ├─ -1/-2/-3 → 对应异常（并释放 2 的标记）
   └─ >= 0 → 继续
4. 投递 MQ seckill.order（消息体见 §6）
   └─ 投递失败 → 立即回补 Redis（§7）并返回 503
5. 返回 { requestId, remainingStock }
```

**为什么第 2 步用 `SETNX` 而不是分布式锁**：这里只需要「同一用户 3 秒内只放一个请求进来」，
`SETNX` + TTL 就够；不需要可重入、不需要看门狗。见 §10 关于 Redisson 的说明。

## 6. MQ 消息体（B3 消费）

```json
{
  "requestId": "uuid",
  "activityId": 1,
  "userId": 2,
  "productId": 302,
  "skuId": 490,
  "quantity": 1,
  "seckillPrice": 9.90,
  "createdAt": "2026-10-19T16:40:00"
}
```

- 交换机/队列：`trade.exchange` + `seckill.order`（复用现有 exchange，新队列）。
- **消息里带 `seckillPrice`**：B3 建单时直接用这个价格快照，不再回查活动 ——
  即使活动在排队期间被改（理论上已禁止），也不会影响已抢到的人。
- B3 消费成功后再写 `seckill:result:{requestId}`，B4 轮询它。

## 7. 失败回补

| 失败点 | 处理 |
|---|---|
| MQ 同步投递异常 | **立即回补**：`INCRBY stock qty` + `DECRBY bought qty`，返回 503 |
| MQ confirm nack（异步） | 记 ERROR + 计数（A4 已有），**不自动回补** —— 需要补偿任务，见下 |
| 建单失败（B3） | 由 B3 回补，并写失败结果 |

**回补必须判存在**：

```java
if (Boolean.TRUE.equals(redis.hasKey(stockKey))) {
    redis.opsForValue().increment(stockKey, qty);
    redis.opsForValue().decrement(boughtKey, qty);
}
```

活动已结束、key 已过期时，`INCRBY` 会**凭空创建一个库存 key** —— 下一场活动如果复用了
同一个 activityId（不会，但脏数据可能），就会出现幽灵库存。判存在是必须的。

**异步 nack 不回补的理由**：nack 不代表消息一定丢了（可能只是确认超时），
自动回补会造成「既卖了又还了」的双重错误。正确做法是对账：
`Redis 已扣总数` vs `DB sold_count + 待消费数`，超出阈值告警。这是 B3/阶段 4 的事，
本轮只保证**同步失败能立刻还回去**。

## 8. 限流

抢购接口**单独配一条规则**，绝不复用 `product-read` 的 60/秒：

```yaml
- name: seckill-buy
  patterns: ["/api/seckill/*/order"]
  methods: ["POST"]
  dimension: USER
  permits: 5
  window-seconds: 1
```

5 次/秒是「防脚本」而不是「限流业务」：真正的削峰靠 Redis 原子扣减 + MQ，
限流只挡住明显的刷接口行为。**用户正常只点一次**，5 次足够容错。

## 9. 与 A2 缓存的关系（严禁共用抽象）

| | A2 商品详情缓存 | B2 秒杀库存 |
|---|---|---|
| 数据性质 | 读缓存，**可回源** | 写计数，**不可回源**（回源即超卖） |
| 失效方式 | TTL + 主动删 | **绝不主动删**，只在活动结束时自然过期 |
| 抽象 | `CacheService`（get-or-load） | 独立 `SeckillStockService`（只有 DECRBY） |

**不能复用 `CacheService`**：它的 `get(key, loader)` 在未命中时会回源 DB 并回填 ——
用在库存上等于「缓存没命中就把库存重置成 DB 值」，直接超卖。这条在阶段划分里已列为硬约束。

## 10. 关于 Redisson（需要你拍板）

阶段划分里 P2-9 写的是「无 Redisson 依赖 → B2 加秒杀兜底锁」。但实现设计下来，
**本切片没有必须用分布式锁的地方**：

| 原本担心的问题 | 实际解法 |
|---|---|
| 超卖 | Lua 原子扣减（单线程执行，天然串行） |
| 一人多单 | Redis 计数 + Lua 内校验 |
| 重复提交 | `SETNX` + 3s TTL（§5 第 2 步） |
| 预热并发 | `SET NX` 本身就是幂等的 |

**我的建议：B2 不引入 Redisson。** 理由是它在这个场景里只能带来额外依赖、一次额外 RTT，
以及「锁过期但业务没执行完」的新问题；而它擅长解决的问题（可重入、看门狗续期、公平锁）
秒杀都用不上。

**如果你希望保留 Redisson 作为技术演示**，我建议只用在一个点上：**预热互斥**
（多实例同时上线同一活动时，只让一个实例写 Redis）。这是唯一说得通的用法，
且用 `SETNX` 也能做，Redisson 只是写法更漂亮。

## 11. 验证方案

### 11.1 单元测试

| 用例 | 断言 |
|---|---|
| 预热写入 meta + stock，且用 `SET NX` | 第二次预热不覆盖已有值 |
| 未预热时抢购 | 抛 503 |
| 活动非进行中 | 抛 409，不进 Lua |
| Lua 返回 -2 | 抛「已抢光」 |
| Lua 返回 -3 | 抛「限购」 |
| 投递失败 | Redis 库存回补、`bought` 回退 |
| 回补时 key 已过期 | 不创建新 key（`hasKey` 判断生效） |

### 11.2 并发验证脚本 `scripts/verify-seckill-stock.mjs`

| 用例 | 期望 |
|---|---|
| 库存 100，500 个不同用户并发抢 | **恰好 100 成功**，400 个「已抢光」，Redis 剩余 = 0 |
| 库存 100，同一用户并发 50 次（限购 1） | **恰好 1 成功**，49 个「超限购/请求过于频繁」 |
| 活动结束后的抢购 | 409「已结束」 |
| Redis 剩余 vs `sold_count` | 差值为「已扣未建单」数，B2 阶段允许 > 0（消费者未实现） |

> B2 阶段没有消费者，`sold_count` 不会变。脚本要断言的是 **Redis 剩余精确为 0**，
> 而不是 DB 数字。
