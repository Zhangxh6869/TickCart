# A1 · 下单幂等与结算抢占设计

> 对应阶段：**3A / A1**（缺口 P0-1、P0-2、P2-10）
> 状态：**设计待确认**（涉及新增表，按 AGENTS.md 需开发者拍板后才能编码）
> 前置阅读：`TickCart项目阶段划分.md`「阶段 3 前置 · 高并发能力补齐（3A）」

---

## 1. 要解决的两个问题

| 编号 | 问题 | 现状代码 | 触发方式 |
|---|---|---|---|
| P0-1 | 下单无幂等 | `OrderService.create` / `createBuyNow` 无任何幂等键 | 用户连点两次「提交订单」、前端超时重试、网关重试 |
| P0-2 | 结算 TOCTOU | `OrderService:119` 读勾选 → `:136` 扣库存 → `:146` `deleteChecked` | 同一购物车两个并发请求 |

两者后果都是**重复建单 + 重复扣库存**。注意：库存扣减本身是原子条件 UPDATE（不会超卖），但「同一笔意图被执行两次」这件事没有任何机制拦截。

现有防护只有前端 `CheckoutView.submitting` 这个 UI 开关 —— 刷新页面、双端同时操作、脚本重放都能绕过。

## 2. 方案总览

```
POST /api/orders  (Header: Idempotency-Key: <uuid>)
  │
  ├─ 1 幂等占位  INSERT idempotent_record(scene,user_id,idem_key)
  │      └─ 唯一键冲突 → 回查（FOR UPDATE）→ 返回首次结果 / 409 处理中
  │
  ├─ 2 地址校验
  ├─ 3 读购物车 → 拆成「有效勾选」与「失效勾选」两组
  ├─ 4 抢占有效项  UPDATE cart_item SET deleted=1 WHERE id IN (…) AND deleted=0
  │      └─ 影响行数 ≠ 期望 → 409「购物车已被其他请求结算」
  ├─ 5 清理失效项（按 id，不校验行数，保持原行为）
  ├─ 6 扣库存（原子条件 UPDATE，已有）
  ├─ 7 建单 + 明细
  ├─ 8 回填幂等记录 biz_no = 订单号
  └─ 9 投递超时关单消息
```

**一个事务内完成 1~8**，任一步失败整体回滚（幂等记录一并消失 → 允许用户重试）。

## 3. 幂等键选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 客户端生成 UUID，放 Header | 实现最简；一个请求一次；不污染业务 DTO；业界标准（Stripe / IETF Idempotency-Key） | 需要前端配合 | **采用** |
| B. 服务端预发令牌（先 GET 换 token） | 服务端完全可控 | 多一次 RTT；要维护 token 生命周期与过期 | 不采用 |
| C. 业务指纹（userId+商品+数量 hash） | 前端零改动 | 会把「用户故意买两份同样的东西」误判为重复；换地址/换备注也无法区分 | 不采用 |

**Header 名**：`Idempotency-Key`（RFC 草案同名）。

**可选还是必填**：**可选**。
- 不传 → 退化为无幂等保护，记 WARN 日志。理由：现有 20+ 回归脚本与老前端都不传，强制必填会一次性打断所有验证链路，违背「每步可运行」。
- 新前端（`CheckoutView` / 详情页立即购买）一律传。
- Swagger 上标注「生产必须传」。

**键的作用域**：`(scene, user_id, idem_key)`。
- 带 `user_id` 是安全要求：否则猜到他人 key 就能读到他人订单号。
- 带 `scene` 是为了让秒杀（B3）复用同一张表。

## 4. 幂等表结构（待确认）

```sql
-- -----------------------------------------------------------------------------
-- 幂等记录表：同一 (scene, user_id, idem_key) 只允许存在一行
-- 与业务同事务写入：业务回滚则记录一并回滚，用户可重试
-- -----------------------------------------------------------------------------
CREATE TABLE `idempotent_record` (
    `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    `scene`      VARCHAR(32)     NOT NULL                COMMENT '业务场景：order.create / order.buyNow / seckill.buy',
    `user_id`    BIGINT UNSIGNED NOT NULL                COMMENT '用户ID（幂等键按用户隔离，防越权读取他人订单）',
    `idem_key`   VARCHAR(64)     NOT NULL                COMMENT '幂等键（客户端生成的 UUID）',
    `biz_no`     VARCHAR(64)     DEFAULT NULL            COMMENT '业务单号；非空即代表该次请求已成功完成',
    `expire_at`  DATETIME        NOT NULL                COMMENT '过期时间（清理任务按此删除）',
    `created_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_scene_user_key` (`scene`, `user_id`, `idem_key`),
    KEY `idx_expire_at` (`expire_at`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT '幂等记录表';
```

### 为什么没有 status 字段

常见写法是 `status`（处理中/成功/失败）三态。本方案**刻意不设**：

- 幂等记录与业务在**同一事务**里，事务未提交时该行对其他事务完全不可见 —— 不存在「别人看到处理中」的场景。
- 业务失败 → 事务回滚 → 记录消失 → 天然允许重试，不需要「失败」态。
- 因此对任何可见的行，`biz_no` 必然非空。**行存在 = 已完成**，一个字段就够。

代价：如果将来改成「先提交占位、再异步执行」（两阶段），需要补 `status`。当前不做，避免出现永远写不到的死字段（AGENTS.md 禁止冗余字段）。

## 5. 幂等执行流程

### 5.1 占位与命中

```java
// IdempotentService
public String claim(Long userId, String scene, String idemKey) {
    if (!StringUtils.hasText(idemKey)) {
        log.warn("下单未携带 Idempotency-Key，本次无幂等保护：userId={}, scene={}", userId, scene);
        return null;                       // 兼容旧调用
    }
    try {
        mapper.insert(record(userId, scene, idemKey, expireAt()));
        return null;                       // 占位成功，继续执行业务
    } catch (DuplicateKeyException e) {
        IdempotentRecord exist = mapper.selectOne(new LambdaQueryWrapper<IdempotentRecord>()
                .eq(IdempotentRecord::getScene, scene)
                .eq(IdempotentRecord::getUserId, userId)
                .eq(IdempotentRecord::getIdemKey, idemKey)
                .last("FOR UPDATE"));      // ★ 必须当前读，见 5.2
        if (exist == null) {
            throw BizException.conflict("请求处理中，请稍后重试");
        }
        if (exist.getBizNo() == null) {
            throw BizException.conflict("请求处理中，请稍后重试");
        }
        return exist.getBizNo();           // 幂等命中，回放首次结果
    }
}
```

### 5.2 两个必须写进注释的坑

**① 占位必须放在方法最前面（先于任何 SELECT）。**
MySQL RR 隔离下，一致性读的快照在**事务内第一次 SELECT 时**建立。如果先 `addressService.getOwned()` 查地址、再去占位，那么冲突后回查幂等记录用的仍是旧快照 —— 看不到并发事务刚提交的那行，`exist` 会是 null，直接误判成「处理中」。

**② 冲突回查必须用 `FOR UPDATE`（当前读）。**
即使顺序正确，加锁读也是双保险：当前读绕过快照，永远读到最新已提交版本。这一条也顺便把「同一 key 的并发请求」串行化了。

### 5.3 并发时序（同一 key，50 并发）

```
T1: INSERT 成功（持有唯一键锁，事务未提交）
T2..T50: INSERT 阻塞在唯一键上
T1: 扣库存 → 建单 → 回填 biz_no → COMMIT
T2..T50: 同时收到 DuplicateKey → FOR UPDATE 读到 biz_no → 返回同一订单号
```

结果：**1 笔订单，库存只扣 1 次，50 个响应里的订单号完全一致**。前端连点两次时表现为「两次都跳同一张订单详情」，符合预期。

## 6. 结算抢占改造

### 6.1 现状为什么危险

```java
CartSummary cart = cartService.list(userId);        // A 读
List<CartItemVO> checked = …                        // A 判定
for (… ) inventoryService.deduct(…);                // A 扣库存
Order order = saveOrder(…);                         // A 建单
cartService.deleteChecked(userId);                  // A 删「当前所有 checked」
```

两个并发请求 A、B 都读到同一批勾选项 → 各自扣库存 → 各自建单 → 最后 `deleteChecked` 把剩余全删。结果两笔订单、库存扣两次。

### 6.2 改成「按 id 精确抢占」

```java
// 3 读购物车，拆两组
List<Long> validIds   = checked.stream().filter(CartItemVO::isValid).map(CartItemVO::getId).toList();
List<Long> invalidIds = checkedItems.stream().filter(i -> !i.isValid()).map(CartItemVO::getId).toList();

// 4 抢占有效项：谁把这些行标记删除，谁才有资格建单
int affected = cartItemMapper.claimForCheckout(userId, validIds);
if (affected != validIds.size()) {
    throw BizException.conflict("购物车已被其他请求结算，请刷新后重试");
}

// 5 清理失效项（精确 id，不参与抢占校验，保持「下单后失效项也消失」的原行为）
if (!invalidIds.isEmpty()) {
    cartItemMapper.deleteCheckedByIds(userId, invalidIds);
}
```

```sql
-- CartItemMapper（自定义 SQL，绕过 MP 逻辑删除的自动拼接）
@Update("UPDATE cart_item SET deleted = 1 WHERE user_id = #{userId} AND deleted = 0 AND id IN (...)")
int claimForCheckout(@Param("userId") Long userId, @Param("ids") List<Long> ids);
```

### 6.3 为什么这样能拦住并发

- `UPDATE … WHERE deleted = 0` 是**当前读 + 行锁**。B 的 UPDATE 会阻塞在 A 持有的行锁上，A 提交后 B 重新求值条件 → `deleted` 已是 1 → 影响 0 行 → 抛 409。
- 抢占发生在**扣库存之前**，失败路径不碰库存行，锁竞争更小、失败更快。
- 不再调用 `deleteChecked(userId)`（那个方法按「当前 checked=1」删，会误删 B 请求期间新勾的其他商品）。

### 6.4 行为变化（需确认）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 下单成功后，勾选的**失效**商品 | 一起被删 | 仍被删（按 id 精确清理，见步骤 5） |
| 下单成功后，未勾选商品 | 保留 | 保留 |
| 下单过程中用户新勾选了别的商品 | 会被 `deleteChecked` 误删 | 不受影响 |
| 并发结算同一购物车 | 两笔订单 | 一笔成功，另一笔 409 |

唯一变化是「并发时的行为」和「不再误删」，正常单线程路径对用户完全一致。

## 9. 验证方案

### 9.1 单元测试（`OrderServiceTest` / 新增 `IdempotentServiceTest`）

| 用例 | 断言 |
|---|---|
| 同 key 串行调用两次 | 第二次返回同一订单号；`order` 表只多 1 行；SKU 库存只减 1 次 |

| 业务异常（库存不足）后同 key 重试 | 幂等记录已随事务回滚，重试可以正常成单 |

### 9.2 并发验证脚本（`scripts/verify-order-idempotent.mjs`）

```

   断言：50 个响应里订单号去重后只有 1 个；DB 该用户订单数 +1

② 20 并发 POST /api/orders，每次不同 key（模拟连点+重试混合）
   断言：1 个 200、19 个 409；订单数 +1；库存只减一次

③ buy-now 同 key 50 并发
```

## 10. 边界与已知限制

1. **崩溃窗口**：业务提交成功后、HTTP 响应丢失，客户端带同 key 重试 → 幂等命中，正确。若进程在 COMMIT 前崩溃 → 记录与订单一并回滚，重试会重新执行（「至少一次」语义），不会产生脏数据。
2. **不传 key 就没有保护**：这是刻意的兼容取舍，靠前端约定 + Swagger 标注约束。B 阶段秒杀接口会**强制**要求 key。
3. **锁等待**：同一 key 的并发请求会阻塞在唯一键上，直到首个事务提交。当前下单事务里含一次 MQ 投递，若 MQ 抖动会拉长持锁时间 —— 归 A4（publisher confirm / 异步化）解决，A1 不动。
4. **幂等记录不清理会无限增长**：加每日清理任务（仿 `SearchLogCleanupTask`），保留 24h。
