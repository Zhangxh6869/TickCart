# 用户管理（后台）功能设计

> 阶段 4 补全项。目标：把「`sys_user.status` 已能挡登录、但没有任何入口能改它」这个半截功能补成闭环。

## 1. 问题

| 层 | 现状 |
| --- | --- |
| `sys_user` | `role`(0 普通 / 1 管理员)、`status`(0 正常 / 1 禁用)、`@TableLogic deleted` 都在 |
| 登录校验 | `AuthService:453` 已生效，`status=1` → 403「账号已被禁用」 |
| 后台入口 | 无。`admin` 模块只有 `DashboardController` |

结论：运营要处置一个刷单账号，只能改库。这是功能缺口，不是锦上添花。

## 2. 范围（一次迭代）

### 2.1 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/users` | 分页；keyword 命中 username / nickname / phone / id，status 筛选，注册日期区间 |
| GET | `/api/admin/users/{id}` | 详情：基本信息（手机号明文）+ 订单统计 + 最近 5 单 + 收货地址（只读） |
| PUT | `/api/admin/users/{id}/status` | 启用 / 禁用；禁用时吊销该用户全部会话 |

权限沿用 `SecurityConfig` 的 `/api/admin/**` → `hasRole("ADMIN")`，无需改配置。

### 2.2 统计口径

- **订单数**：该用户全部订单（含已取消）—— 客服关心的是「这个人下过多少单」
- **已付款单数 / 累计消费**：`status IN (1 待发货, 2 待收货, 3 已完成)` 的 `pay_amount` 之和
  - 已退款（7）与退款中（6）**不计入**，否则「退了款还算消费」会误导运营
  - 不复用 `payment_record`：订单表本身有 `pay_amount`，一页 20 人只需一次 `GROUP BY`，避免 N+1
- **退款次数**：`refund_record` 按 `user_id` 计数，用于风控判断

### 2.3 禁用语义（关键）

禁用必须**立即生效**，不能只挡下次登录：

1. `revokeAllRefreshTokens` —— 刷新令牌作废
2. `tokenBlacklist.revokeAllIssuedBefore` —— 已发出的 access token 按签发时间作废

这两步登出/改密已在用（`AuthService:355-357`），抽成 `AuthService.revokeSessions(userId)` 复用，
避免在 admin 模块重写一遍令牌逻辑（写漏一步就是「禁用后还能下单」）。

## 3. 安全约束

| 约束 | 原因 |
| --- | --- |
| 不能修改自己的状态 | 防止把自己锁在门外，且后台只有 1 个管理员时无人能救 |
| 管理员账号（role=1）不支持禁用 | 同上；启用放开（无害） |
| 列表手机号脱敏 `138****8888` | 后台也是浏览器，截图外流是真实风险；详情页才给明文 |
| 不提供改密码 / 改角色 / 删除用户 | 后台能重置密码 = 客服可冒充任意用户；改角色是误提权入口；`@TableLogic` 删除会让历史订单悬空 |
| 禁用原因不落库 | `sys_user` 无对应字段，加字段属结构变更，需单独决策（见 §5） |

## 5. 刻意不做 / 待决策

1. **禁用原因**：需要给 `sys_user` 加字段（或独立操作日志表），属表结构变更，延后。
2. **用户画像**：客单价、复购率、活跃度等，等数据看板一起做。
3. **导出**：用户列表导出 Excel，暂无用例支撑。
