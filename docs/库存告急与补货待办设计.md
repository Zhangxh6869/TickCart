## 一、先分清两件事，否则会做重

「告急」有两个使用场景，需求和界面都不一样：

| | **A · 列表筛选** | **B · 补货待办** |
|---|---|---|
| 回答的问题 | 这个商品缺不缺货 | 今天先补哪些 |
| 行粒度 | 商品 | **SKU** |
| 判据 | 商品总库存 < 分类阈值 | SKU 库存 < 商品所属分类阈值 |
| 排序 | 用户选的（默认最近更新） | 固定：剩余比例升序 → 缺口降序 |
| 列 | 完整 7 列 | 图 / 名 / 规格 / 库存 / 阈值 / 缺口 |
| 能做什么 | 编辑、上下架、批量操作 | 就地改库存（改完自动消失） |
| 入口 | 筛选区一个 chip | 页面顶部横幅 → 抽屉 |
| 使用频率 | 偶尔（顺手找货时） | **每天开工第一件事** |

**B 是主，A 是副产品。** 只做 A 的话运营还是不知道「今天该干什么」；只做 B 也能成立，A 的价值在于「在完整列表上下文里处理某个告急商品」。

---

## 二、共同的地基：阈值只能有一处实现

两个功能都依赖「某分类的有效预警线」，所以都走 `StockWarnService.effectiveThresholds()`。

**禁止**在 SQL 里写 `COALESCE(c.stock_warn_threshold, parent.stock_warn_threshold, 10)`，原因有二：

1. 会变成两份实现。列表红标是 Java 算的，SQL 再算一遍，规则一有出入就出现「筛出 5 个、页面标红 3 个」；
2. 继承链在 SQL 里只能覆盖两层（自己 + 父级），出现三级分类就废了；Java 那边是沿 `parent_id` 一路向上，层级多深都行。

## 三、A · 列表筛选

### 3.1 接口

```
GET /api/admin/products?stockLow=true&page=1&size=12
```

`ProductQuery` 加一个 `Boolean stockLow`，Spring 自动绑定，Controller 不用改。

### 3.2 SQL 形态

阈值按取值归并成几组，拼成 OR 分支（20 个分类只有 4 种取值，所以只有 5 条分支）：

```sql
WHERE deleted = 0
  AND ( (category_id = 5  AND stock < 8)                    -- 鞋类
     OR (category_id = 16 AND stock < 3)                    -- 家电
     OR (category_id = 23 AND stock < 30)                   -- 食品生鲜
     OR (category_id IN (1,6,7,…) AND stock < 10)           -- 其余 16 个（继承全局）
     OR (category_id NOT IN (…)   AND stock < 10) )         -- 挂在已删分类上的兜底
```

关键点：

- **分支数 = 阈值取值种类数**（现在 4 种），不是分类数（20 个），也不是商品数（162 个）；
- 最后一条兜底不能省：商品挂在已删除分类上时前四条都匹配不到，会被整个漏掉；
- 分页和 `count(*)` 天然正确，因为它只是 WHERE 条件，和 `keyword LIKE` 同级。

### 3.3 前台必须挡住

`ProductQuery` 前后台共用，要在 `filterWrapper` 里用 `!onlyOnSale` 把住：前台（`onlyOnSale=true`）传了 `stockLow` 也不生效。否则商城端能靠筛选反推哪些商品快断货。

### 3.4 前端

筛选区加一个 chip「库存告急」，激活时 `query.stockLow = true`、`page = 1`、重新拉列表。激活后页头文案变成「共 N 个告急商品」。

### 3.5 成本

约 40 行后端 + 15 行前端，**无迁移**。

## 四、B · 补货待办

### 4.1 为什么是 SKU 级，不是商品级

现成的例子：某商品总库存 120，但 43 码是 0 件。

- 商品级判断：120 > 阈值 → 不告急 → **列表不会标红**；
- 但用户点进详情想买 43 码，买不到。

补货的实际单位是 SKU，所以待办必须落到 SKU。这也是为什么它不能简单复用列表的 `stockLow`。

### 4.2 接口

```
GET /api/admin/products/low-stock?limit=100

{
  "total": 4,                 // 全库告急 SKU 总数（不受 limit 影响）
  "outOfStock": 2,            // 其中已断货的数量（后端算，前端数 items 会偏小）
  "truncated": false,         // 是否因为扫描上限被截断
  "items": [{
    "productId": 126,
    "productName": "竞速跑步鞋 全掌回弹",
    "mainImage": "/img/shoes/shoe-10.jpg",
    "categoryId": 5,
    "categoryName": "鞋类",
    "skuId": 412,
    "specName": "尺码",
    "specValue": "43",
    "skuImage": "/img/shoes/shoe-10.jpg",
    "stock": 0,
    "threshold": 8,
    "shortage": 8,            // threshold - stock
    "remainRatio": 0.0        // stock / threshold，0 = 断货，1 = 刚好在线上
  }]
}
```

### 4.3 查询实现：两段式，不引入 Mapper XML

项目现在一个 XML mapper 都没有（`resources/mapper/` 是空目录，全是 MP wrapper）。为了一个 JOIN 去引入第一份 XML 不划算，改用两段式——**和 `randomPage` 取 id 到内存洗牌是同一个套路**，项目里已有先例。

```
① SELECT id, category_id, name, main_image FROM product
   WHERE deleted = 0 AND status = 1            -- 只算在售，下架商品不需要补货
   ORDER BY stock ASC LIMIT {scanLimit}
② SELECT * FROM product_sku WHERE product_id IN (①的全部 id) AND deleted = 0
③ Java：逐 SKU 判定 stock < threshold(该商品的分类) → 告急行
④ 排序 → 截断 limit
```

**注意不能先按「商品总库存」粗筛**（初稿的错误）：总库存 120、两个 SKU
（120 + 0）时总库存远高于阈值，粗筛会把这个断货 SKU 整个漏掉。
所以必须把所有在售商品的 SKU 都看一遍。

量级：162 个在售商品、383 个 SKU，两次查询、几百行内存，开销可以忽略。

**扫描上限**：加配置项 `tickcart.product.low-stock-scan-limit`（默认 2000）。在售商品超过上限时，先按 `stock` 升序取前 N 个再扫（最可能告急的优先），并返回 `truncated: true`。超限说明该换 SQL 聚合了，不是靠调大上限硬撑。

### 4.4 排序：按剩余比例，不是按缺口

```
remainRatio = stock / threshold     升序
  ↓ 相同
shortage = threshold - stock        降序
  ↓ 相同
productId                           升序（稳定）
```

**为什么不用缺口绝对值**：生鲜阈值 30、剩 5（缺口 25），家电阈值 3、剩 0（缺口 3）。按缺口排，断货的家电会排到生鲜后面——但断货显然更急。剩余比例跨品类可比，缺口只在同比例时做次级排序。

### 4.5 界面：横幅 + 抽屉

**横幅**（放在商品管理页页头下方，`total > 0` 才出现）：

```
⚠ 4 个 SKU 库存告急，其中 2 个已断货        [查看补货清单 →]
```

浅红底 + 左侧红条，不弹窗、不阻塞。

**抽屉**（640px，右侧）：

| 缩略图 | 商品名 / 分类 | 规格 | 库存 / 阈值 | 缺口 | 操作 |
|---|---|---|---|---|---|
| 图 | 竞速跑步鞋<br>鞋类 | 尺码 43 | **0** / 8 | 8 | 改库存 |

- 库存低于阈值的数字标红，0 件额外加「已断货」tag
- 点「改库存」变成行内输入框，失焦调已有的 `PUT /admin/skus/{id}/stock`
- **改完这一行淡出消失**，横幅数字同步减一 —— 因为库存不再低于阈值，它本来就不该留在待办里
- 空态：「当前没有库存告急的 SKU」

### 4.6 动作边界

只做「改库存」，**不做「标记已处理」**。

理由：补货到货后把库存录进去，这一行自然就不告急了，不需要额外状态字段。加一个「已处理」标记反而要维护「处理了但没补货」这种中间态，还得配定时过期清理——成本远大于收益。

> ★ **补货动作不是缺口，早已实现**：`PUT /api/admin/skus/{skuId}/stock?stock=N`
> → `ProductService.updateSkuStock`（校验非负 → 落库 → 从 SKU 重算商品汇总 → 失效详情缓存）。
> 曾因为只读设计文档就断言「只有看、没有做」而误判，后续别重蹈。

## 五、明确不做的三件事

1. **可售天数**（`库存 / 日均销量`）。数据上勉强可行（`t_order.pay_time` + `order_item.quantity` 能聚合近 7 天销量），但 `order_item.sku_id` 对**无规格商品存的是 0**，SKU 级口径不完整；而且 demo 库 172 单集中在 10-06~10-21，日均销量基本是 0，排序会失真。二期做的话要先补一个按天汇总的销量表。
2. **采购单 / 入库单**。那是另一条业务链路（供应商、到货、质检），不属于后台商品管理。
3. **告警推送**（站内信 / MQ 定时扫描）。需要「谁通知谁」的产品决策，而且现在的定时任务只有秒杀预热，加一条新链路要单独设计幂等与去重。

## 六、一个必须解释给运营的口径差异

列表的 `stockLow` 是**商品级**（总库存），补货待办是**SKU 级**。

所以会出现：**列表没标红，但待办里有它** —— 因为总库存 120 够，但 43 码断货了。

这不是 bug，是刻意的：

- 列表回答「这个商品整体缺不缺货」→ 决定要不要下架、要不要改价；
- 待办回答「具体哪个规格要补」→ 决定采购什么。

抽屉里要写一句说明，否则运营会当成数据不一致报 bug。

## 七、改动清单与落地结果

| 切片 | 内容 | 后端 | 前端 | 迁移 | 状态 |
|---|---|---|---|---|---|
| 1 | 待办接口 `GET /products/low-stock` | `LowStockItem` / `LowStockReport` VO + `ProductService.lowStock()` + controller + 6 个测试 | — | 无 | ✅ |
| 2 | 横幅 + 抽屉 | `LowStockReport.outOfStock` | 横幅 + 抽屉 + 就地改库存 | 无 | ✅ |
| 3 | 列表筛选 `?stockLow=true` | `ProductQuery.stockLow` + `groupByThreshold` + `applyLowStockFilter` + 2 个测试 | 筛选 chip | 无 | ✅ |

实际按 1 → 2 → 3 的顺序做（补货待办是主，筛选是副产品）。

**落地时新增的两点**（原设计没写）：

- `LowStockReport.outOfStock`：断货数必须后端算 —— `items` 会被 limit 截断，
  前端数出来的会偏小，横幅上「其中 2 个已断货」就不准了。
- 上下架成功后只静默刷新横幅（`loadLowStock()`），不重查列表 —— 补货待办只算在售商品，
  下架后它不该再出现，但不能为此牺牲「乐观更新不丢滚动位置」。

验证：后端全量 369 个测试通过；三个功能都在真实实例 + 浏览器上跑通
（横幅 1 个告急 → 抽屉改成 12 后自动消失 → 筛选 162 → 1 → 取消回到 162）。

## 八、风险与上限

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 内存扫描变慢 | 在售商品 > 2000 | 改 SQL 聚合（引入 XML mapper），或按 stock 升序只扫前 N |
| OR 分支膨胀 | 阈值取值种类 > 10 | 改用 JOIN 分类表 + COALESCE（那时继承层级也要定死最多两层） |
| 无规格商品显示 | 占位 SKU（`spec_value` 为空） | 规格列显示「默认」，不显示空白 |
| 前后端口径不一致 | 有人图省事在前端算阈值 | 前端只渲染 `stockLow` / `remainRatio`，不持有阈值 |
