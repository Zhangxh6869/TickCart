# TickCart 测试方案

> 状态：方案（待执行）
> 前置：Testcontainers 通路已验证跑通（`TestcontainersSmokeTest`，1 passed / 12.36s）
> 定位：以「验证系统真的没问题」为目标，按风险排序，不追求覆盖率数字

---

## 1. 出发点

### 1.1 现有资产的真实覆盖面

后端 33 个测试类、427 个 `@Test`，全部是 Mockito 单测；前端 0 测试；无 CI。

这 427 个用例覆盖的是**正常路径 + 分支判断**——给 `OrderService` 传一个不存在的 SKU，断言抛 `BizException`。这类测试有价值，但它们有个共同前提：**被测对象之外的一切都按 mock 的剧本走**。

### 1.2 盲区：三个被 mock 掉的假设

项目最核心的三套可靠性机制，恰好全部建立在「真实中间件的某个具体行为」之上，而这三条在 mock 里永远不会被证伪：

| 机制 | 依赖的真实行为 | mock 里长什么样 |
|---|---|---|
| 下单幂等 | MySQL 唯一键冲突后事务仍可继续，且 `FOR SHARE` 会阻塞到首个事务提交 | `DuplicateKeyException` 是手写 `throw`，`selectOne` 是 `thenReturn` |
| 防超卖 | Redis `SETNX` 不覆盖已有值 / 条件 UPDATE 在并发下恰好命中 N 次 | `RedisTemplate` 永远返回 `true` |
| 超时关单 | RabbitMQ 手动 ack + `basicNack(requeue=false)` 进死信 | `Channel` 永远 ack 成功 |

`IdempotentService.claim` 的注释里写着「MySQL 不会因单条语句失败而中止事务」——**这是一个数据库方言层面的假设**。如果它不成立，幂等机制整体失效，而 427 个单测一个都发现不了。

这就是集成测试的全部理由：**不是补覆盖率，是验证这些假设真的成立**。

### 1.3 三条原则

1. **按损失排序，不按覆盖率排序。** 超卖一次赔一笔钱，UI 错位只是难看，优先级差两个数量级。
2. **断言不变量，不是断言每一步。** 与其在 50 个测试里散落 200 个断言，不如定义 5 条「任何时刻都必须成立」的等式，每个场景结束统一校验一次。
3. **历史 bug 是最好的用例来源。** 修过但没写回归测试的 bug，等于没修——下一次重构就会回来。

## 3. 六道闸门

### G1 数据正确性：不变量断言

不写零散断言，定义 5 条等式，在任何测试场景结束后统一校验：

| 编号 | 不变量 |
|---|---|
| I1 | 对有规格商品：`product.stock == SUM(product_sku.stock WHERE deleted = 0)` |
| I2 | 下单后：Σ(SKU 库存减少量) == Σ(订单明细数量) |
| I3 | 取消 / 超时关单后：SKU 库存恢复到下单前水位 |
| I4 | 秒杀：`sold_count + 剩余库存 == 初始备货量` |
| I5 | 订单状态只允许单向流转，不存在 `CANCELLED → PENDING_SHIPMENT` 这类跃迁 |

实现成一个 `InventoryInvariantChecker`，在测试的 `@AfterEach` 里跑。**这是整个方案里性价比最高的一件东西**——R3 那个「两本账漂移」的 bug（`e0c9314`）如果有它，会在第一次下单时就被抓到，而不是等库存偏大几十件后才被发现。

I5 值得单独说：状态机的非法跃迁不会报错，只会让订单永久卡在某个状态。查一遍所有状态写入点，确认没有绕过状态机校验的直接 `setStatus`。

### G2 并发：必须真并发

所有并发用例统一用 `CountDownLatch` 同时放行，**不允许串行 for 循环假装并发**。

| 编号 | 用例 | 断言 |
|---|---|---|
| C1 | 同一 `idemKey` 并发 50 次下单 | 订单表恰好 1 条；其余 49 个响应要么回放同一单号，要么 409「请求处理中」 |
| C2 | 首个事务回滚后，第二个请求用同 key | 返回 409 而非 500；幂等记录不残留脏数据 |
| C3 | 库存 10，100 并发下单 | 成功恰好 10，失败 90；`product_sku.stock = 0` 且不为负 |
| C4 | 秒杀库存 10，100 并发抢 | 成功 10；`sold_count = 10`；I4 成立 |
| C5 | 同一用户并发提交结算 | 只有 1 次进入待支付 |
| C6 | 同一用户并发抢同一秒杀活动 | 只成功 1 次（`seckill:bought:*` 生效） |

C2 是最容易被忽略、也最能暴露真实问题的：`claim` 里的 `FOR SHARE` 在首个事务未提交时会阻塞，提交后能读到 `bizNo`；但如果首个事务**回滚**，行消失了，`replayOf` 返回 `null` → 走 409 分支。这个分支在单测里是 `when(...).thenReturn(null)` 硬造出来的，在真实数据库里是否真的会走到、会不会抛 `LockWaitTimeoutException`，只有真 MySQL 能回答。

**并发用例的副产品**：唯一键冲突在 InnoDB 下会产生间隙锁，高并发时可能死锁。C1 跑 50 并发就是在探这个雷。

### G3 异步与故障

| 编号 | 用例 | 断言 |
|---|---|---|
| A1 | 超时关单全链路：建单 → 投递 → 消费 | 订单 → `TIMEOUT_CLOSED`；库存回补；I3 成立 |
| A2 | 同一消息重复投递 2 次 | 只关一次单；库存只回补一次（幂等） |
| A3 | 消费者抛异常 | 消息进死信队列，不在原队列无限重投 |
| A4 | 支付回调重复通知 | 订单状态只流转一次；支付流水不重复 |
| A5 | 秒杀异步建单失败 | `SeckillResult` 对外可感知，不是无声失败 |

A2 是重点：`OrderTimeoutConsumer` 用 `basicNack(requeue=false)`，说明设计上不重投，但**消息中间件的 at-least-once 语义意味着重复投递一定会发生**（生产者重试、网络重连）。消费端必须有幂等兜底，而不是依赖「不会重复」。

**故障注入**（手工执行，记录行为即可，不写自动化）：

| 场景 | 期望 |
|---|---|
| Redis 不可用 | 秒杀降级为明确报错，不雪崩到数据库 |
| RabbitMQ 不可用 | 下单仍能成功（超时关单靠补偿任务兜底），不能阻塞主链路 |
| MySQL 主库慢 | 有超时，不是无限等待 |

### G4 权限与契约

| 编号 | 用例 |
|---|---|
| S1 | 用户 A 的 token 访问用户 B 的订单详情 / 地址 / 收藏 / 浏览记录 → 403 或 404（**不能是 200**） |
| S2 | 未携带 token 访问 `/admin/**` → 401 |
| S3 | 普通用户 token 访问 `/admin/**` → 403 |
| S4 | JWT 篡改 payload / 过期 token → 401 |
| S5 | 登录频控：连续错误密码触发图形码、超阈值锁号 |
| S6 | 短信频控：连发触发 429 |

S1 是电商最高危漏洞，也是最容易漏的——功能测试时你永远只用自己的账号登录。**每新增一个 `/api/**/{id}` 接口，就该有一条对应的越权用例。**

### G5 用户旅程（Playwright）

| 编号 | 链路 |
|---|---|
| E1 | 登录 → 搜索 → 商品详情 → 加购 → 结算 → 支付 → 订单列表可见 |
| E2 | 秒杀抢购：活动进行中 → 抢购成功 → 订单出现；库存耗尽后 → 明确的失败提示 |
| E3 | 后台：新建商品 → 上架 → 配秒杀活动 → 上线 → 发货 |

移动端用 Playwright 的设备模拟（iPhone 13）。**不追求 UI 全覆盖**——只跑这三条，目的是抓前后端契约断裂和路由/状态机问题，不是替代手工点测。

### G6 历史 bug 回归

把修过的 bug 逐条变成回归用例。已有清单：

| bug | 回归用例 |
|---|---|
| 软删 SKU 回补静默失效（`4d08aa0`） | 软删 SKU 后取消订单 → `restore` 命中 0 行时必须打 warn，且不污染 `product.stock` |
| `product.stock` 两本账漂移（`e0c9314`） | 下单 / 取消后 I1 成立 |
| `loadLatestPayments` 取错流水 | 已取消订单 + 后续新支付 → 订单详情展示的是「支付成功」那条 |
| 秒杀同 SKU 时间重叠 | 建第二场重叠活动 → 409（草稿之间允许重叠，上线时才拦） |
| 已结束活动改价 | → 409 |
| 商品下拉 `size=200` 截断成 100 | 拉全 162 个商品，断言 `records == total` |

这张表每修一个 bug 就加一行，是项目最有价值的长期资产之一。

## 4. 基础设施设计

### 4.1 容器与上下文

用 **singleton container 模式**（手动 `start()`，不用 `@Container` 注解），让所有集成测试类共享同一套 MySQL/Redis/RabbitMQ，避免每个类起一次容器（每次约 12s）。

```
AbstractIntegrationTest（基类）
  ├─ static MySQLContainer   → @ServiceConnection
  ├─ static RedisContainer   → 指定 database=1，与开发库隔离
  └─ static RabbitMQContainer → 独立 vhost
```

Flyway 在容器就绪后自动跑 20 个 migration（约 3s），每个测试类只跑一次。

### 4.2 数据准备与清理

- **不使用 `@Transactional` 回滚**：并发用例的事务回滚会让测试失去意义，MQ 的异步结果也看不见。
- 改为 `@BeforeEach` 显式清理：`TRUNCATE` 业务表（`t_order` / `order_item` / `cart_item` / `product` / `product_sku` / `seckill_activity` / `idempotent_record`）+ `FLUSHDB`（只清测试用的 db 1）。
- 造数用工厂方法（`aProduct().withSku(10).build()`），不要共享静态 fixture——测试间的隐式耦合是 flaky 的主要来源。

### 4.3 时钟问题（已查证，附成本账）

**先厘清一件事：不是所有 `LocalDateTime.now()` 都需要改。** 按用途分两类，只有一类需要时钟注入：

| 类型 | 用途 | 例子 | 能否靠造数据绕过 |
|---|---|---|---|
| 写时间戳 | 记录「这件事发生在什么时候」 | `order.setPayTime(now)`、订单号生成、`updatedAt` | 能（断言时忽略具体值） |
| 做时间判定 | 「现在是否落在某个区间内」 | `SeckillActivityStatus.of(activity, now)` | **不能** |

查证结果（2026-10-26）：

- **订单模块 9 处 `now()` 全是写时间戳**（`shipTime`/`payTime`/`cancelTime`/`finishTime`/订单号）→ 不用改。
  超时关单虽然看起来是时间问题，但它的判定是 `created_at` 字段 vs now，**造一条 `created_at = now - 31min` 的订单就能测**，不需要时钟。
- **真正做状态判定的只有秒杀模块 8 处**：
  `SeckillActivityService:111/141/185/197/211/273`、`SeckillBuyService:65`、`SeckillPreloadTask:65`。
- 且 `SeckillActivityStatus.of(activity, now)` 的 `now` **本来就是显式参数**，设计上已经留了口子——改动只是把调用处的 `LocalDateTime.now()` 换成 `timeProvider.now()`。

所以两个方案的真实差别不在「改 30 处 vs 不改」，而在**能测到什么**：

| 能力 | 方案 A（造数据） | 方案 B（Clock 注入） |
|---|---|---|
| 进行中的活动能抢 | ✅ `start=now-1h` | ✅ |
| 未开始 / 已结束不能抢 | ✅ `start=now+1h` / `end=now-1h` | ✅ |
| 库存扣减、超卖防护 | ✅ | ✅ |
| **边界瞬间**（`start=now+1s`，请求在 0.9s 与 1.1s 到达） | ❌ 造完数据时间就飘了 | ✅ `Clock.fixed` 精确控制 |
| **状态跨越那一刻**（Redis TTL 到期、`sold_count` 停止累加） | ❌ 只能 sleep 硬等 | ✅ 时钟直接跳过 |
| **预热窗口**（活动开始前 N 分钟触发） | ❌ 只能等到那个时刻 | ✅ |

**方案 B 的两个隐藏成本**（比调用点数量更值得注意）：

1. `SeckillActivityService` 构造器加依赖 → `SeckillActivityServiceTest` 42 条用例的构造调用要跟着改（机械改动，但不为零）。
2. **SQL 里的 `NOW()` 控制不了**：`SeckillActivityService:520` 的后台列表排序用了 `CASE WHEN start_time <= NOW() ...`。改了 Java 时钟后，前台说「已结束」、后台排序仍按真实时间算「进行中」——要口径一致，得把那条 SQL 的 `NOW()` 也改成 `#{now}` 传参。

**建议：分级走，不是二选一。**

- **P1 / P2 阶段（并发、异步）用方案 A**：这些用例只需要「进行中的活动」，造数据足够，零代码改动。别让时钟改造阻塞最有价值的测试。
- **只在确实需要测时间边界时，再对秒杀模块做方案 B**：8 处 + 一条 SQL + 42 条测试适配，属于可加性改造，不会白做。

判断标准很简单：**你会不会真的去断言「活动开始的瞬间」「Redis TTL 到期的瞬间」「预热窗口的触发点」**。会，就做 B；不会，A 就够，把时间花在并发和越权上。

### 4.4 并发工具

`ExecutorService(50)` + `CountDownLatch` 统一放行 + 收集所有 Future 的异常。断言「成功数 / 失败数 / 异常类型分布」，而不是只看最终数据库状态——**失败的原因对不对，和失败的数量对不对一样重要**。

### 4.5 异步等待

引入 `awaitility`（比手写 `Thread.sleep` + 轮询可靠）：

```java
await().atMost(Duration.ofSeconds(10))
       .untilAsserted(() -> assertThat(order.getStatus()).isEqualTo(TIMEOUT_CLOSED));
```

禁止 `Thread.sleep`——它既慢又不稳，是 flaky 的头号来源。

### 4.6 不变量检查器

```java
class InventoryInvariantChecker {
    void assertAll() {  // I1~I5 逐条校验
    }
}
```

在 `@AfterEach` 里无条件调用。任何场景跑完，账都必须是平的。

## 6. 判据：什么叫「测完了」

不是「跑通了」，而是这四条同时成立：

1. 5 条不变量在**所有**场景结束后都成立；
2. 每个历史 bug 都有对应回归用例；
3. 故障注入下系统行为符合预期（降级而非雪崩）；
4. 全量套件连续跑 3 次结果一致（无 flaky）。

---

## 7. 反 flaky 纪律

并发 + 异步测试天生容易 flaky，必须提前立规矩：

- 不用 `Thread.sleep`，用 `awaitility`；
- 不依赖固定端口（Testcontainers 随机端口）；
- 断言不依赖日志顺序、不依赖集合遍历顺序；
- 每个测试自建数据，不共享静态 fixture；
- **连跑 3 次都绿才算过**，一次绿可能是运气。

## 8. 测试有效性验证（变异测试）

测试通过不代表测试有效——它可能根本没断言到关键点。对最关键的几条做手工变异：

| 变异 | 期望 |
|---|---|
| `stock >= n` 改成 `stock > n` | C3 必须失败 |
| 去掉 `replayOf` 的 `FOR SHARE` | C2 必须失败 |
| `basicNack(requeue=false)` 改成 `requeue=true` | A3 必须失败 |
| 去掉 `adjustProductStock` 调用 | I1 必须失败 |

**测试抓不住变异 = 这条测试是假的。** 这一步花不了多少时间，但能证明测试真的有防护力，而不是一堆自我感觉良好的绿色对勾。

## 附：环境注意事项

1. **Docker API 版本**：Docker Desktop 29+ 要求最低 API 1.40，Testcontainers 1.19.x 默认 1.32 → 无 error-message 的 400（伪装成「找不到 Docker」）。已在 `pom.xml` 的 surefire 中固化 `api.version=1.43`。
2. **Ryuk 镜像**：`testcontainers/ryuk:0.6.0` 从 docker.io 拉取超时，需从 `docker.m.daocloud.io` 拉取后 tag 回原名。
3. **跑测试前先停后端**：`mvn test` 与 `mvn spring-boot:run` 争用 `target/` 文件锁。
