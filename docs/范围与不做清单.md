# 范围与「不做」清单

> 状态：**已定稿（2026-11-02，开发者决策）**
> 用途：明确哪些能力是**刻意不做**，而不是「漏了」。后续迭代、链路体检、代码评审时
> 看到这些项**不再重复提出**；确实要重新打开，先看本文的「重新考虑的条件」。
> 关联：`TickCart项目阶段划分.md`、`docs/退款售后功能设计方案.md`、`docs/E2E库存累积与退款缺口.md`

---

## 0. 为什么要单独写一份

2026-11-02 的全链路体检里，我把「评价体系」「消息通知」「优惠券」等列成了缺口。
这些能力本身确实是电商标配，但**本项目是秒杀商城的技术作品，不是要交付给真实商家的系统**：
交易 / 库存 / 秒杀 / 售后这条主链路的正确性才是评分点，横向铺功能只会稀释深度。

因此这份文档的作用是：**把「不做」变成一个明确的、有理由的结论，而不是一个悬着的待办。**
悬着的待办会反复出现在体检报告里，浪费讨论；明确的「不做」只需要维护一次。

## 1. 不做清单

| # | 项 | 为什么不做 | 重新考虑的条件 |
|---|---|---|---|
| 1 | **评价体系**（评分 / 晒单 / 商品详情评价区 / 订单完成去评价） | 只影响「社会证明」这一层展示，不触及交易与库存正确性；且需要新表 + 图片上传 + 审核，投入产出比在作品定位下最低 | 若项目转为真实运营，或面试方明确问「评价怎么防刷」 |
| 2 | **仅退款后的库存手动回补入口** | 属于已知取舍（`RefundService` 注释已写明：仅退款时货已发出，凭空加回库存就是超卖的源头）。补货接口 `PUT /api/admin/skus/{skuId}/stock` 已存在，真出偏差可由管理员直接改库存 | 出现「库存对不上但无法判断原因」的真实工单 |
| 3 | **部分退货**（一个订单退其中几件） | 见 `docs/退款售后功能设计方案.md` 决策 6：退款单与订单一对一，部分退货要把 `refund_record` 拆成明细级，牵动 `active_key` 唯一索引、库存回补时点、金额分摊三处 | 有真实商家场景，或面试深挖「多件订单只退一件怎么算钱」 |
| 4 | **优惠券**（领取 / 使用 / 下单抵扣） | 会污染订单金额口径（`total_amount` / `pay_amount` / 退款金额取支付流水），而金额链路刚在退款 P0/P1/P2 里收口 | 若要做营销玩法，且愿意重做一遍金额快照与退款口径 |
| 5 | **真实支付沙箱**（微信 / 支付宝） | 模拟支付是**最终形态**，与短信 Mock 的决策一致：不接真实网关，回调形态已按真实渠道预留（`/api/payments/callback/{payNo}`），换真实渠道只需替换 `PaymentService` 的适配层 | 项目要真收钱 |
| 6 | **消息通知**（站内信 / 短信通知 / 推送） | 订单状态变化不主动告知，用户需自己刷新「我的订单」。属于体验层，不影响数据正确性；且短信通道目前只服务验证码，扩成业务通知要新增频控与模板管理 | 前置依赖（发货物流单号）已于 2026-11-02 补齐（见 §3），做通知**不再缺内容**；要不要做只取决于愿不愿意投体验层 |
| 7 | **发票** | 与评价同理，纯合规向功能，作品定位下无展示价值 | 真实运营 |
| 8 | **首页轮播 / 广告位** | 阶段 1 页面清单里列过「轮播」，实际未做。首页现有「吸顶搜索 + 分类栏 + 商品流」已能承载浏览入口，轮播需要额外的广告位管理后台 | 若要做运营位（需要后台配置 + 跳转规则） |
| 9 | **基础监控**（Actuator / Prometheus / Grafana） | 阶段 5 原清单项。当前可观测性靠日志 + 压测报告已够用，接 Prometheus 需要额外容器与看板，属于运维投入 | 要长期在线运行 |

## 2. 更正：阶段 5 并非「全未做」

2026-11-02 体检报告里曾把阶段 5 整体记为未完成，这是**错的**。逐项核对如下：

| 阶段 5 条目 | 实际状态 | 证据 |
|---|---|---|
| 优惠券 | ❌ 不做 | 见 §1 第 4 项 |
| 真实支付沙箱 | ❌ 不做 | 见 §1 第 5 项 |
| 首页 / 详情缓存优化 | ✅ **已完成** | `CacheService`（Cache-Aside）+ `docs/商品缓存设计.md`；详情缓存 `withoutStock` + `applyFreshStock` |
| JMeter / ab 压测留档 | ✅ **已完成** | `docs/秒杀压测方案.md`、`docs/秒杀压测报告.md`、`scripts/bench-seckill.mjs` |
| 基础监控 | ❌ 不做 | 见 §1 第 9 项 |
| 缓存穿透 / 击穿防护 | ✅ **已完成** | `CacheService`：空值标记防穿透 + 短锁防击穿 + 故障降级（`docs/读放大与可靠性收尾设计.md`） |

> 结论：阶段 5 的**技术项已全部落地，剩余项已全部转为「不做」**，该阶段可以关闭。

## 3. 曾经的缺口（**已全部补齐**，留档备查）

这两项在 2026-11-02 的链路体检里被判为「真实缺口，不是取舍」，当天已全部实现并提交，
**不再属于待办**。保留在此只为留一条「当初为什么算缺口」的判断依据 ——
半年后再看，能分清「本来就没打算做」和「做过但后来放掉了」。

| 项 | 当初的判断依据 | 现在的状态 |
|---|---|---|
| **发货物流单号** | `t_order` 无 `express_company` / `tracking_no`，`OrderService.ship()` 不接收任何参数，用户侧「待收货」查不到物流；而退货退款反倒有 `returnCompany` / `returnTrackingNo`，属不对称。且**数据从来没被采集过**，越晚补历史订单越补不回来 | ✅ **已实施**（`f216e92`，迁移 V25）。`t_order` 加两列（可空），新增 `ship(orderNo, ShipRequest)` 重载，后台单笔发货改弹窗录入，商城订单详情展示 + 复制单号；批量发货仍不采集单号 |
| **未映射路径返回 500** | `GlobalExceptionHandler` 只有 `Exception` 兜底，`NoResourceFoundException` 掉进去被当成未知故障：返回 `50000` + ERROR 堆栈。前端接口拼错会被误判成「服务挂了」，日志噪音也会淹掉真故障 | ✅ **已实施**（`faaebff`）。新增 `handleNoResourceFound` → 404 / `40400`，日志降为 WARN。被鉴权拦住的未知路径**仍返回 401**（有意：不让人用 404/401 的差异探测路径是否存在） |

> 落地细节（含实测数据）见 `.workbuddy-ai/memory/2026-11-02.md`；
> 字段定义见 `docs/数据库设计说明.md` 的 `t_order` 一节。

## 4. 维护约定

- 本清单**只增不删**。某项将来真做了，把该行改成「✅ 已实施（commit）」并保留原理由，方便回溯为什么当初判为不做。
- 新增「不做」项时，必须同时填「为什么不做」与「重新考虑的条件」—— 只写「不做」的条目，半年后没人知道原因。
- 链路体检、代码评审、需求讨论时，凡命中本清单的项**直接跳过**，不占讨论时间。
